title: "Give Ari access to another service with MCP or an API"
sidebarTitle: "Connect an MCP server or API"
description: "Connect an MCP server or an API so Ari can look things up or act in another service live, such as a bank balance in Mercury or issues in Linear; control which tools Ari may use; and have Ari save a nightly sync of a service's data into your Model."
---

Connect an MCP server or an API when you want Ari to look something up or act in another service while you chat. For example, Ari can read today's balance in Mercury, your open issues in Linear, or an exchange rate. Ari calls the service live each time it needs it, and nothing is copied into your Model unless you ask Ari to save a sync setup.

An MCP server or an API does not replace an integration. An integration syncs a source's history into your Model every night; an MCP server answers questions about right now. [How connected data reaches your Model](/concepts/connected-data#integrations-and-mcp-servers-do-different-jobs) explains the difference.

If the service has no MCP server and no API definition, or it signs in with a username and password, Ari can fetch its data once a day with a saved script instead, as long as the service signs in with direct web requests and not through a separate single sign-on provider or a browser check. See [Bring in data from a source that has no integration](/guides/connect-other-sources#bring-in-data-from-a-source-that-has-no-integration).

## Before you start

- You need permission to manage connections. Someone without it sees **A workspace admin must connect this service.**
- For an MCP server: the service's MCP address, and a sign-in to the service or a token. Many common servers are in the catalog with their address filled in.
- For an API: an API key, unless the API needs none, and an OpenAPI 3 or Swagger 2.0 definition, as JSON or YAML, for an API that is not in the catalog.
- MCP servers and APIs use no plan slot, with or without a sync setup.

## Connect a service

<Tabs>
  <Tab title="Ask Ari">
    Name the service and what you want from it:

    > Connect Mercury's MCP server so you can read our bank balances.

    Ari reads the provider's official documentation and posts a card titled **Connect [service]**. The card shows the service's logo, its address, how it signs in, such as **MCP token** for a server that takes a token, or **API key** or **No sign-in required** for an API, and a **Provider documentation** link. Select **Connect**. A service that uses OAuth opens its sign-in window; one that takes a token or key shows a secure field on the card. A service that needs more than one secret, such as a bearer token and an `AccessKey` header, shows one more secure field for each, labeled with the header's name, and a field left blank is refused with **The [name] field is required.** What you type there goes to cfo.ai's connection service, not to Ari or the chat. Never paste a key into a chat message.

    Before Ari offers a Connect card for a server that signs in with OAuth, it checks whether the provider accepts cfo.ai as an app. When the provider signs in only apps registered with it in advance, Ari says so in the chat instead of posting a card that would fail; a check that cannot finish within ten seconds still offers the card.

    The card reads **Connecting…**, then **Checking connection…**, then **Connected** for an MCP server or **Connection added** for an API. Ari then checks that the tools or endpoints answer before it relies on them. **Connection added** means the specification loaded, not that the API answers, so Ari checks access with a read before relying on it, and for an API that takes a key that read also shows whether the key works; the card says **Ari will check access before using this connection.** If an MCP server's sign-in fails or you cancel it, Ari learns what went wrong in the same chat and can suggest what to try next. When an API's definition has parts cfo.ai cannot use but at least one usable operation, the connection imports the usable operations, and Ari's result lists the skipped ones with their reasons; a definition with no usable operation is refused instead, with the message listed in [Connection statuses and actions](/reference/connection-statuses#messages-about-mcp-servers-and-apis).
  </Tab>

    <Steps>

      </Step>

        For an API, **Add API** asks for a **Display name**, the **Authentication** (**Bearer token**, **API key header**, **Basic authentication**, or **No authentication**), the **API key**, and the **OpenAPI specification**, as a **Specification URL** or with **Paste JSON**. The address may start with `http://`: cfo.ai fetches the definition at its `https://` address and never over plain HTTP. A specification that declares several servers also needs the **Base URL** under **Advanced**.

        When the definition loads, the dialog's title changes to **API connected**, counts the operations it imported, and lists the ones it could not import or kept without a response schema, each with its reason; [Connection statuses and actions](/reference/connection-statuses#messages-about-mcp-servers-and-apis) lists those labels. **Done** or **Esc** closes the dialog.
      </Step>

**Add with Ari** on the same tabs opens a chat that starts the Ask Ari path, and the connection picker closes once the chat is open. While the workspace cannot use AI, the button is off and a line under it reads **Add with Ari is unavailable.** with the reason, such as **This workspace is out of AI usage.** **Add manually** still works.

### Rippling's MCP server

Add Rippling's server with **Add manually**. The dialog shows a **Rippling setup** note with three requirements:

- Copy your Remote MCP server URL from **IT → My IT → MCP connectors → Rippling MCP**.
- Ask a Rippling admin to assign you access in **IT → MCP Gateway → Rippling MCP → Access assignments**.
- Make sure your company has an active Rippling AI trial or subscription, or its tools return no data.

### NetSuite's MCP server

NetSuite accepts cfo.ai's sign-in only after a NetSuite administrator has allowed cfo.ai's redirect URI, the address NetSuite sends you back to. When the address is not yet allowed, the connection form reads **The provider must allow cfo.ai's redirect URI https://app.cfo.ai/integrations/mcp/callback before you can connect.**, and Ari receives the same address. Give it to your NetSuite administrator, who creates an integration record under **Setup → Integration → Manage Integrations → New** with **Authorization Code Grant**, **Public Client**, and **Dynamic Client Registration** checked, **NetSuite AI Connector Service** as the only OAuth 2.0 scope, that exact address as the **Redirect URI**, and every token-based authentication and client credentials box cleared. Once the record is saved, select **Retry** or **Connect** in cfo.ai and sign in with a role that is not Administrator and has the **MCP Server Connection** and **OAuth 2.0 Access Tokens** permissions. Ari can walk you and your administrator through these steps in the chat.

What Ari reads through NetSuite's MCP server follows the NetSuite role you signed in with. NetSuite leaves out the records and transaction types that role cannot view, and it reports no error, so a role without access to journals returns totals that omit them. NetSuite's report tool selects by transaction date and subsidiary. It has no accounting-period filter, so it cannot select by the period a transaction posted to. When a total Ari read this way does not match NetSuite, check the role's permissions and the dates first.

## Choose what Ari may do

Each tool of an MCP server, and each endpoint of an API, has a permission:

| Permission | What Ari does |
| --- | --- |
| **Allow** | Uses it without asking |
| **Ask first** | Asks you to approve each call. See [Answer Ari's questions and approve its actions](/guides/approve-ari-actions). In a Trigger run, scheduled or started with **Run now**, nobody can approve, so a tool or endpoint on **Ask first** does not run; see [What a run cannot do on its own](/concepts/automation#what-a-run-cannot-do-on-its-own). |
| **Block** | Never uses it |

A new MCP server starts with every tool on **Ask first**. A new API starts by method: reads (`GET` and `HEAD`) on **Allow**, deletes on **Block**, and every other call on **Ask first**. When Ari asks and you choose **Always allow**, that tool stays on **Allow** for the whole workspace.

Ari can also call a path the API's specification leaves out. A read (`GET` or `HEAD`) of such a path runs without asking, unless you have set one of the API's listed reads to **Ask first** or **Block**, in which case Ari asks first. A delete of such a path never runs, and any other call to one asks you first; in a Trigger run, nobody can approve, so it does not run. A call that waited for your approval is listed on the connection page's **Endpoints** afterward, where you can set its permission, and **Always allow** on its card allows that exact path only. Updating the specification removes those added paths and their permissions unless the new specification includes them.

To change them, open the service's connection page: select its row in the sidebar, or select **Manage** on the service in **Settings → Connections** or on the **MCP** or **API** tab. The page's **Available actions** section groups an MCP server's tools as **View information** and **Change or delete**, and its **Endpoints** section groups an API's endpoints as **Read endpoints** and **Write/delete endpoints**. One button sets them for you:

- For an MCP server, **Reset permissions**: **View information** tools to **Allow**, and **Change or delete** tools to **Ask first**.
- For an API, **Auto-classify**: reads to **Allow**, writes to **Ask first**, and deletes to **Block**.

When Ari calls a write tool and the answer is lost on the way back, it does not repeat the call on its own. Check the other service before you ask Ari to try again.

## Copy a service's data into your Model every night

To keep a service's data in your Model, rather than look it up live, ask Ari for a sync setup:

> Save a daily sync of our Mercury account balances into the Model.

Ari picks one tool or endpoint, saves a call to it that only retrieves records, and runs it. Each night the sync copies the results into your data, and a saved query brings them into your Model as Variables and Dimensions, like an integration. The tool or endpoint must be set to **Allow**. You can give it its own daily time, as with any connection; see [Refresh data](/guides/refresh-data#change-when-a-connection-refreshes).

The service's page lists its setups under **Syncs**, each **Enabled** or **Paused**, with when it last synced. When a sync brought data in and no saved query reads it yet, the page reads **No queries yet** and offers **Set up queries with Ari** to people who can edit the connection; others see **Data synced. Someone with access can set up queries with Ari.** To stop one, ask Ari to remove it; the data it already copied stays. A service with a sync setup still uses no plan slot. [How imported data loads](/reference/imported-data#sync-setups-for-mcp-servers-and-apis) lists the sync types and limits.

When a server limits the rate of requests it accepts (HTTP 429), the sync waits and asks for the same page again on its own. When a page of an MCP sync fails for good, Ari's report in the chat names the connection, the page that stopped, and what stopped it. When the server changes a tool a setup uses, the setup stays **Enabled** when its saved request still fits the new definition, and otherwise reads **Paused** while Ari's background worker repairs it; [How imported data loads](/reference/imported-data#sync-setups-for-mcp-servers-and-apis) has the rule. [Connection statuses and actions](/reference/connection-statuses#messages-about-mcp-servers-and-apis) lists each cause, the wait rules, and its next step.

## Change a connection's name, address, or authentication

When a service changes its address, or you set up its authentication the wrong way, change the saved connection instead of disconnecting and adding it again. The connection keeps its ID, its tools, its tool permissions, and its sync setups. This applies to a connection you added with a key or token. A connection that signs in through the provider takes a new name only; when its sign-in breaks, use [Reconnect an MCP server](#reconnect-an-mcp-server) instead.

<Tabs>
  <Tab title="Ask Ari">
    Name the connection as Ari lists it and say what to change:

    > Change the Light API connection so the key is sent as the Basic username.

    Ari changes the name, provider name, address, and authentication type of a connection you added with a key or token, and only the name of one that signs in through the provider. A new key or token goes through the secure form Ari hands you, never through the chat: a card headed **Edit** followed by the connection's name, whose **Review changes** button opens the form, and nothing is saved until you submit it.
  </Tab>
  <Tab title="By hand">
    In **Settings → Connections**, open the service's **…** menu and select **Edit configuration**. Change the fields you need and save. To replace a key, type it in **Replacement API key**; leave that field blank to keep the saved one. An API connection with more secrets than its key asks for each of them again when you change the **Base URL** or the **Authentication**; renaming the connection, or replacing only its key, keeps them as they are. A connection that signs in through the provider takes a new name only. Every field and its messages are listed in [Settings](/reference/settings#connections).
  </Tab>
</Tabs>

## Reconnect an MCP server

When a server's row in **Settings → Connections** reads **Reconnect required**, select **Reconnect** and sign in to the provider again. The connection and its sync setups stay as they are, and the new sign-in replaces the saved one when it completes. A row that reads **Access expired · renewal on next use** needs nothing from you; cfo.ai renews the sign-in the next time it uses the server.

## Finish a sign-in that did not complete

When a server reads **Waiting for you**, or its sign-in state reads **Sign-in incomplete**, select **Finish setup** on its row in **Settings → Connections**, in its details, or on its card in the sidebar. It starts a new sign-in and replaces the unfinished attempt, and the sign-in finishes even if the cfo.ai tab that started it reloads before the provider sends you back. [Connection statuses and actions](/reference/connection-statuses#statuses-for-mcp-servers-and-apis) lists the statuses, what the page the provider returns you to says, and what to do when the browser blocks the provider's window.

## Disconnect a service

In **Settings → Connections**, open the service's **…** menu and select **Disconnect**, or open the service's connection page and select **Remove connection**; both do the same. cfo.ai warns **Ari will no longer be able to use this server's tools until you reconnect.**, or for an API, **Ari will no longer be able to use this API until you reconnect it.**

## If something goes wrong

- **The provider must allow cfo.ai's redirect URI https://app.cfo.ai/integrations/mcp/callback before you can connect.** The provider has to allow that exact address first; trying again does not help until its administrator does. For NetSuite, see [NetSuite's MCP server](#netsuites-mcp-server).
- **This provider signs in only apps registered with it in advance.** The server cannot be connected with OAuth. When Ari can check the provider first, it tells you this before offering a Connect card. Use a token if the provider offers one.
- **Reconnect this source to continue.** The saved sign-in no longer works. Sign in to the server again.

[Connection statuses and actions](/reference/connection-statuses#messages-about-mcp-servers-and-apis) lists every message.

title: "Create and update formulas as an agent"
description: "Save formulas through visible Table Block targets with edit_table_blocks, preview a write with dry_run, and verify the exact resulting Model values."
---

A saved formula belongs to its Variable. When the user selects a visible row, column, or cell, the saved Table Block provides the target that resolves the correct Variable and scope. Every model formula is written through `edit_table_blocks`.

## Shape a call as one action block

`edit_table_blocks` has several actions: `create`, `update`, `reshape`, `copy`, `delete`, `set_time_rollup`, and `update_calendar`. Fill exactly one block named for the action and put that action's fields inside it. The `scenario` field sits beside the block and applies to it.

## Write through the saved table

First read the table with `inspect_table_blocks` to obtain the visible row and column references:

```json
{ "read": { "target": "Operating Plan" }, "scenario": "Main" }
```

Then send the related formula edits together in one `update`. Pass the same `scenario` to the read and the write so they resolve the same saved table. A row with no Date scope takes `formula`; a row that runs across time takes `default_formulas` with an `actuals` entry, a `forecast` entry, or both.

```json
{
  "scenario": "Main",
  "update": {
    "target": "Operating Plan",
    "row_updates": [
      {
        "rows": ["Gross Profit"],
        "default_formulas": {
          "actuals": { "formula": "Revenue - `Cost of Goods Sold`" },
          "forecast": { "formula": "Revenue - `Cost of Goods Sold`" }
        }
      }
    ]
  }
}
```

The server derives the Variable, cell address, formula range, and write permissions from the visible target. Copy references from the inspection result, such as `Gross Profit#3f2`, instead of inventing IDs, positions, or range identifiers. Use `clear_formula: true` in place of `formula` to remove the rule the row owns for that range.

## Create a visible derived row

A new Variable can be defined and placed on an existing saved Table Block in the same change. `structure.insert` names the side, the new Variable, and its rule:

```json
{
  "scenario": "Main",
  "update": {
    "target": "Operating Plan",
    "structure": {
      "insert": [
        {
          "side": "rows",
          "node": {
            "variable": "Gross Margin",
            "default_formulas": {
              "forecast": { "formula": "iferror(`Gross Profit` / Revenue, 0)" }
            }
          }
        }
      ]
    }
  }
}
```

To start a new table instead, use `create` with the complete `rows` and `columns`:

```json
{
  "create": {
    "name": "Margin analysis",
    "rows": [
      {
        "variable": "Gross Margin",
        "default_formulas": {
          "forecast": { "formula": "iferror(`Gross Profit` / Revenue, 0)" }
        }
      }
    ],
    "columns": [{ "time": "MONTH" }]
  }
}
```

The saved row makes the calculation visible, inspectable, and available for follow-up.

### Create several dependent tables in one call

When a build needs more than one table and a later table's formulas name Variables an earlier table declares, put the tables in a `tables` list inside one `create` instead of one call per table. The tables save in list order in one change, so a formula in the second table can name a Variable the first table declares. Two entries that name the same new `page` share it. Each entry carries its own `name`, `page`, `rows`, `columns`, and settings; `scenario` and `dry_run` sit on the request and apply to every entry.

```json
{
  "create": {
    "tables": [
      {
        "name": "Workforce assumptions",
        "page": "Workforce",
        "rows": [{ "variable": "Hours per Month", "formula": "160" }],
        "columns": [],
        "window": { "granularity": "NO_GRANULARITY" }
      },
      {
        "name": "Roster",
        "page": "Workforce",
        "rows": [{ "dimension": "Employee", "items": ["E-1", "E-2"] }],
        "columns": [{ "variable": "Monthly hours", "formula": "`Hours per Month`$" }]
      }
    ]
  }
}
```

The response holds one receipt per table, in list order, and every table shares one `change_log_id`. A refusal of any table refuses them all and names the table.

### A new dated row gets a time rollup

A rule on a month row governs month cells only; quarter, half-year, and year cells read the Variable's time rollup. A `create` or `insert` row may name `rollup` (`SUM`, `LAST`, or `AVERAGE`). When it names none and the table's periods are at the Model's base grain, the save writes the rollup the request implies, at every grain coarser than the base, for Actuals and Forecast: `SUM` for a number with no aggregation or with `SUM` or `COUNT`, `LAST` for `aggregation_function: LAST`, and none for a timeless `formula`, `format: PERCENTAGE`, a non-number, or any other aggregation. A row created on a table whose periods are quarters or years, or on a table without Date, gets no implied rollup. The receipt states them in one `default_rollup` issue and does not list them as `rollups` or count them as `default_formulas`. A ratio row created without `format: PERCENTAGE` gets `SUM`, so its year cell adds monthly ratios; `set_time_rollup` or a named `rollup` corrects it.

A `default_formulas` rule written through a table whose periods are coarser than the base grain, such as a yearly table in a monthly Model, is saved at that coarser grain, and the receipt warns: the year cells compute the rule whatever their month cells hold, and the month cells do not read it. Write the rule on a row of a base-grain table, or in a `variables` entry, when it should govern the base periods.

### A breakdown's totals are written for you

When a table breaks a Variable down, `child_defaults` on the deepest axis row is the rule for the lines, saved on the line's full path. The save then gives every coarser level the tables show a default that sums the level beneath it, one ordinary rule per level, and the receipt lists them: "Revenue's level defaults, which add up its [Customer, Line, Product] lines at each level the tables show: saved Revenue[Customer, Product], Revenue[Product] and Revenue." A value set on any row reaches every total above it. A rule an author writes at a level replaces the default there, and a default edited into other text stays with its author. The sums exist only while a line rule claims the lines: clearing the line rule removes the sums left in its range. See [How cfo.ai chooses a formula](/formulas/core-concepts/how-cfoai-chooses-a-formula#breakdown-totals-add-up-the-rows-beneath-them).

### Add members and write their values in one call

An `update` adds the members that `dimensions[].add_items` or `replace_items` names before it resolves `values` and `cell_updates`, so one call can add `E9` to Entity and write `["E9", 42]` in `values`. A `create`, or an update that adds rows, can also fill a Mapping column on the rows it adds: a Department cell on a new employee row saves the one quoted item, `"Sales"`, a new item joins the Dimension's list, and a value that is not one item is refused before anything saves, naming the cell. Cells of one lookup save in one mapping write, so filling 400 Departments costs about the same as filling one.

When a write changes a shared mapping row, the receipt's `shared_mapping_changed` notice names the first changed row and its item before and after, and counts the rest: "The shared mapping changed: EMP-001's Department moved from Engineering to Operations, and 3 more rows changed. Other tables and periods that use it can also change." A first assignment reads "is now Sales", and a cleared cell "was cleared; it was Sales". Every table that reads the mapping is recalculated in the background after the call returns; `inspect_dimension_mappings` lists them.

### A timeless formula on a dated row is refused the same way everywhere

`formula` and `clear_formula` write a Variable's timeless rule. A `create` writes it for a Variable it makes, and an `update` writes it on an undated row or column. A dated row's rules are `default_formulas.actuals` and `default_formulas.forecast`, which create and update both accept; create and update refuse a timeless `formula` on a dated row with the same sentence. A `child_defaults` clear on create goes to the same planner an update uses, so a child that owns no rule reports `unchanged`.

## A member-list axis has no formula to edit

`formula` and `clear_formula` edit the rule of a calculated value: a Variable, a Dimension shown as a value through its mapping or formula, or the Variable that encloses a Dimension breakdown. An axis that only lists a Dimension's members has no calculated value, so a formula edit aimed at it is refused with a reason instead of a resolution error. The reason says that `dimensions` `add_items`, `remove_items`, `replace_items`, and `rename_items` edit saved membership, that a retained breakdown edits its enclosing Variable's rule, and that a formula which generates a source-linked Dimension's members has no authoring operation in the tool: the person writes it from the Dimension's label-row menu in a table, **Edit dimension formula**.

## Save a Variable's rule without a table

When the requested rule has no visible table target, name the Variable in a `variables` entry instead. No table `target` is needed:

```json
{
  "scenario": "Main",
  "update": {
    "variables": [
      {
        "target": "Bookings",
        "default_formulas": { "forecast": { "formula": "last(`Bookings source`)" } }
      }
    ]
  }
}
```

The rule is saved at the Variable with one Date term at the Model's base grain, the same address a plain row on a base-grain table writes. A later `row_updates` write on a table that places the Variable edits this rule instead of adding a rival. The same entry accepts settings such as `data_type`. Member edits on a Dimension still name a table that shows it.

## Filter the members an axis shows

`members` on a `row_updates` or `column_updates` entry is the saved member filter of the selected axis, in one of two forms. A list of member names replaces the filter and may name `empty:None`, the rows with no value; `[]` clears it. A string is a condition on the Dimension, evaluated over its members to narrow the current saved selection, so a member the saved list already leaves out stays out. `Region not in {"West"}` keeps every named member but West; the empty member has no value, so a comparison on it is unknown, and a null check inside `where` is what keeps it: `Region where (Region = null or not (Region in {"West"}))`. A member row such as `Total[West]` names its axis. `hidden` on the same entry hides or shows the saved axis the selection belongs to, so `hidden: true` on a member row hides every member of that level.

## Edit an address that holds several saved rules

A table edit names an address: the Variable, its condition, and its formula range. Imports and older writes can leave more than one saved rule at one address. An exact `$[...]` rule outranks an inheriting `[...]` rule at its grain, and among rules of the same form the newest save wins, so cells read one rule: the newest exact rule when one exists, otherwise the newest inheriting rule. A `row_updates`, `child_defaults`, or `cell_updates` write at such an address edits the rule the cells read and deletes the older copies of the same form in the same change. The receipt names each deleted copy: "This write also deleted an older copy of a Forecast rule that Advertising carried at this address: `1` at `[Vendor in any, Date.Month in any]`. No cell read a deleted copy, so no value changed." An exact rule and an inheriting `[...]` rule at the same grain are not copies. The write edits the exact rule, keeps the inheriting one, and names it in the receipt.

A table read marks a default that has older copies with the `duplicate_default_formula` issue, which counts the copies and says that a write to the default deletes them. The default itself is shown as `defined here` and writable.

## Set where a source's rows sit on the calendar

Where an imported source's rows sit on the calendar is one fact about the source, and a `sources` entry on `update` or `create` states it once. The `target` is the query reference a read prints under `sources`, and `preferred_time_property` is one of the source's date columns. The write saves that column on every Variable and Dimension of the source in the same change; a `variables` or `dimensions` entry in the same request that sets its own `preferred_time_property` wins for that property. A column that is not a date column of the source is refused, naming the columns that are. An `update` that carries only `sources` needs no table target.

```json
{
  "update": {
    "sources": [{ "target": "CRM Deals Monthly Export", "preferred_time_property": "synced_month" }]
  }
}
```

## Declare a mapping in the create that reads it

A `create` whose rules read a mapped Dimension can declare the mapping in the same call instead of calling `edit_dimension_mappings` first. A `dimensions` entry takes `keys`, `items`, and `catch_all` as `edit_dimension_mappings` `map` takes them. The mapping is written in the same change before the rows, so a rule such as `` sum(`Income Statement Amount`[`P&L Line` = "Revenue"]) `` resolves in this call, and the table, the Dimension, its items, and its rows commit together. The receipt's `items` entry for the Dimension carries the mapping's facts: `keys`, `rows_created`, `rows_updated`, `target_items`, and `catch_all`. A refusal on either side saves nothing.

```json
{
  "create": {
    "name": "Historical P&L",
    "page": "P&L",
    "dimensions": [
      {
        "target": "P&L Line",
        "keys": ["GL Account Name"],
        "items": { "4000 - Subscription Revenue": "Revenue", "5000 - Hosting Costs": "Cost of Revenue" },
        "catch_all": "Unclassified"
      }
    ],
    "rows": [
      {
        "variable": "Total Revenue",
        "default_formulas": { "actuals": { "formula": "sum(`Income Statement Amount`[`P&L Line` = \"Revenue\"])" } }
      }
    ],
    "columns": [{ "time": "MONTH" }]
  }
}
```

## Set a table's window and grain

`window` is the table's own date range and grain. On a `create` it holds `start`, `end`, and `granularity`: a dated table names its grain, such as `MONTH`, and a timeless table names `NO_GRANULARITY`, as the example above does. On an `update`'s settings the range is `{"type": "ABSOLUTE", "start": …, "end": …}`. `start` and `end` accept a plain calendar date such as `2026-02-01` as well as a full timestamp, and create and update save the same window for either spelling. `{"inherit": true}` clears the table's own window. `update` with `grain` moves the table's Date columns to that grain, so a monthly table asked for `QUARTER` shows quarter columns and the receipt reports the moved Date column; a table whose Date header shows two grains at once, such as Year above Month, is refused a new grain.

A `values` write names each Date column by the start of its period at the table's grain. On a table with yearly columns, `2024-01` writes the 2024 cell; `2024-02` is refused as a date inside a YEAR period, and the refusal names the spelling that works.

Dated inputs in `values` or `cell_updates`, and the periods a `readback` selects, leave the table's saved display window unchanged. A report that must show a requested start and end needs `window` set on the same call, or the table keeps showing its old range with the new months outside it; a readback of selected months proves those cells, not the displayed range.

## Write in a Scenario

`scenario` defaults to the Scenario the person is viewing, which can change between turns. When a call that saved something omits it, the receipt says which Scenario the write used: a table receipt carries a `scenario_warning` issue and an `edit_variables` receipt carries a warning, such as "No scenario was named, so this call used `Breakeven Plan#4c1`, the scenario the person is viewing. The scenario in view can change between turns." When nothing is in view the sentence names Main. A refusal, a dry run, or a call that saved nothing carries no sentence.

A Scenario stores only what differs from the Scenario it branched from. A cell write in a child Scenario that repeats the value the cell already reads from its parent stores nothing: the edit's outcome is `unchanged`, and a `formula_warning` says the Scenario already reads this value from its parent, so the cell keeps following the parent and changes when the parent changes. A different value is saved as the Scenario's own and holds through the parent's later edits.

## Delete a Variable or Dimension

`delete` with a `target` alone removes the whole table and the objects homed there. `delete` with a `variables` or `dimensions` list removes only the listed objects. When other formulas, blocks, or settings still read one of them, the delete is refused and lists what reads it, until `force: true` accepts that those references break. `force` on the delete covers every listed entry; `force` on one entry covers that entry alone, so a call can force some entries and not others. `update` entries do not take `force`.

## A rule belongs to its Variable

A create row that names an existing Variable reuses it, and rows match names without regard to case, so `Deferred revenue` reuses `Deferred Revenue`. The receipt's `items` entry for a reused object carries `home`, the table it was first created on, when that table exists and is readable, and `rule: "replaced"` when this create replaced a rule the object already had, in Main or in the Scenario being edited.

Formula names match case exactly. A formula that names `` `Deferred revenue` `` when only `Deferred Revenue` exists is refused with the object it matches: "`` `Deferred revenue` `` matches the existing `` `Deferred Revenue` `` (names match without case); formula names match case exactly, …". A reference field and formula text accept the same spelling of a namesake: the short suffix a readback prints, such as `Currency#3` beside `Currency#8`, names the object it prints for, and a suffix of three or more hex digits is checked against the object's retained identity, so a reference issued for a deleted object never moves to a new namesake. A backticked name that no object carries, such as `` `Amount#3c2` ``, reads as the reference it quotes. In a table row or column, backticks still mark a literal new name.

Giving an existing Variable new `default_formulas` while placing it on another table rewrites the rule every table reads. The receipt says so when the rule it replaced was a formula: it names that formula and the address the Variable carried it at. Writing a value over a plain number, quoted text, date, or `null` states no replaced rule; the committed edit's `previousText` carries the old value instead. Placing a Variable without new defaults leaves its existing rule alone.

## Preview before you write

`dry_run: true` on an `update`, `create`, or `reshape` validates structure, references, and formula syntax without writing, and returns `valid`, `warnings`, and `model_effects`. A table write is atomic on its own: the whole change saves or none of it does.

## Verify the saved result

Ask for a readback in the same write with `readback.rows` and `readback.columns`, or read the affected Table Block afterward. Check the intended Scenario, representative dates and segments, formula origins, and the actual numeric result.

When the receipt carries warnings, read them before moving on. They report rules that compute to zero, rules that tie with an existing rule, and shared rules the write replaced. See [Formula errors and troubleshooting](/formulas/formula-reference/formula-errors-and-troubleshooting).

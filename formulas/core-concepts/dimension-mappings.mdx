title: "Map one Dimension's items to another"
sidebarTitle: "Dimension mappings"

A **Dimension mapping** is a one-way lookup that assigns items from one or more source Dimensions to an item in a target Dimension. A common example is grouping general-ledger accounts into a reporting category, such as mapping account `5001` to `COGS`.

## Choose a direction

Mappings only go one way: pick the shared, canonical Dimension as the **target**, and map each source Dimension into it. If you have GL accounts from two different entities that need to land in the same reporting structure, map each entity's Account Dimension into the same target separately — don't try to map the target back to a source, since a mapping that creates a cycle is refused.

## Create a mapping

Ask Ari to map specific items, for example, "Map account 5001 to COGS and 6001 to Payroll." A rule for an item that already has a mapping updates that item's existing rule.

Mapping rules have no effective dates: a rule applies in every period. A Dimension whose items come from a formula cannot also be a mapping target, and a mapping always names fixed items; it cannot compute the target item. Ari can also declare a mapping inside the same request that creates the table whose formulas read it, so the table, the Dimension, and its rows save together.

## When a plain pair isn't enough

Some rows need a real condition instead of a simple equality, like a set of accounts ("8001 or 8002 maps to Other Income"). Ask Ari to write these as a condition instead of a pair; Ari carries this through into the same formula-style logic used elsewhere in the Model. A rule that spans more than one key at once, such as Account together with Company, needs no condition: Ari matches the pair of items directly.

## Set a catch-all

Every target Dimension can have one **catch-all**: the target item used when no explicit mapping rule matches. Ask Ari to set or clear it. Without a catch-all, an unmatched source item remains unmapped.

## Remove mappings

Ask Ari to:

- **Unmap** specific rows, leaving the rest of the lookup untouched.
- Remove an entire lookup when a source stops feeding into a target altogether.

Removing rows or a lookup keeps the Dimension items themselves; only the assignments go. Each mapping change saves every row it names or none of them.

## See what's already mapped

Ask Ari to read a target Dimension's mappings. It reports every lookup feeding that target, each with its keys, row count, and the pairs, ready to hand back for an edit. It also lists every visible table the mapping affects, whether the table shows the mapped items, groups by them, or calculates from them, so you can see where a change would show up. Long lookups come back in pages.

## Change a mapped item in a table

In a Table Block whose column shows a mapped Dimension, selecting a cell opens a picker with a **Search \[Dimension] items** field. Picking an item saves that row's assignment in the mapping, so every table that reads the mapping changes with it. The table cannot create a lookup, set a catch-all, or remove rows; ask Ari for those.

Renaming a Dimension item, whether you rename it on a table or Ari renames it, also renames it in the mapping's assignments and in formulas that compare against it, in one change that one undo reverses. Ari's rename receipt says how many mapping rows and formulas moved with it.

## Share one Dimension across accounting sources

Two accounting sources often carry the same categories, such as Entity and Currency on QuickBooks Online, Xero, and Rillet statements, or Vendor on two general-ledger queries. When a new accounting query publishes for the first time, cfo.ai joins each of its text or number Dimension columns to an existing compatible Dimension: the same provider, integration, column name, type, and aggregation. When several qualify, it joins the one that the most sources already feed; when two are tied on that count, it joins the older one. So a Currency Dimension shared by three queries wins over a standalone one from one query, and when you split a Dimension by hand, every piece still qualifies and the same rule picks among them. It does not matter whether a built-in template, Ari, or you wrote the query's SQL. Later syncs never regroup, so a Dimension that stayed separate stays separate, and dates and amounts are never combined.

Ask Ari to combine or split Dimensions yourself:

- **Combine** unions compatible source Dimensions into one target, keeps each item's exact label, and rewrites the formulas and table axes that read the others. Nothing is saved on a refusal.
  - It needs matching types and aggregation, and a Dimension that reads its column's first value cannot join one that reads the last value.
  - Amounts are always refused. A chart, manual segment, or Scenario override is refused when it reads a retired Dimension and cannot be rewritten safely.
  - A combined Dimension that reads each source's latest value keeps every source's own filters and dates, so a table filtered to one Entity shows that Entity's latest vendor.
  - Canvas blocks do not stop a combine. Their code and datasets are left as they are, and Ari's receipt lists every Canvas block in the Scenario that may read a retired Dimension so Ari can review and repair them. The list is conservative, because Canvas code can build references dynamically, so a listed block is not proof that it broke.
- **Split** turns a combined Dimension back into one Dimension per source column. The original keeps its first source. Amount formulas stay as they are, so a breakdown may no longer add up to its parent total; Ari warns about that.

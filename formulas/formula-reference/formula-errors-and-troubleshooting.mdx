---
title: "Formula errors and troubleshooting"
description: "Troubleshoot invalid formulas, missing references, unexpected totals, date mismatches, formula ranges, and calculation errors."
---

Start with the problem you can see, then check the formula's expression and scope.

## Ari refused to save the formula

A formula you type in a table always saves, even when it is unfinished; the cells show an error code until you fix it. See [Save, cancel, and fix errors](/getting-started/build-by-hand#save-cancel-and-fix-errors). A formula that Ari or a connected agent writes is checked before it is saved, and the write is refused when it has one of these problems. Check for:

- A missing parenthesis or quote
- A Variable name that needs backticks
- A Variable that does not exist in the selected Scenario.
- An unsupported number of function arguments
- A formula range on a formula without Date scope.
- A name that matches an existing Variable only without regard to case. Formula names match case exactly, so a formula naming `` `Deferred revenue` `` when the Variable is `Deferred Revenue` is refused, and the refusal names the Variable it matches.

## A Dimension's member list cannot take a formula

A table axis that only lists a Dimension's members has no calculated value, so a formula written to it has nothing to edit. Ari reports this as a reason rather than an error: edit the Dimension's membership instead, or write the rule on the Variable the breakdown belongs to. The formula that generates a Dimension's members from a connected source is written by a person, not by Ari: right-click the Dimension's label row in a table, or choose **[Dimension] dimension settings** from one of its items, and choose **Edit dimension formula**.

## A table edit was not saved

A value or formula you type into a table saves after the editor closes. When the server refuses it, the cell returns to its old value and a notice says why and what to do next, for example **These cells come from an integration. Change the value in the source system.** See [When a change is not saved](/getting-started/build-by-hand#when-a-change-is-not-saved) for every notice.

## A Variable cannot be found

Use the name shown in cfo.ai. If the name contains spaces or punctuation, wrap it in backticks. If several Variables share the name, use the short disambiguator offered by the editor or Ari.

## The result is unexpectedly high

The formula may be selecting several values and summing them. Review lookups that use `in any`, sets, or `where`. Use an explicit aggregation when the intended result is an average, median, minimum, maximum, count, standard deviation, first value, or last value.

## The formula works in one segment but not another

Check whether:

- A segment-specific formula overrides the default
- The referenced Variable exists in both segments
- An absolute reference should be a current-segment reference, or the reverse
- The table uses a different segmentation

## The formula works in Actuals but not Forecast

Check the formula range, Date scope, Date grain, Scenario, and Last close. A formula assigned to Actuals or Forecast must include Date in its scope.

## A date lookup returns no value

Confirm that the Date grain and value format match. A monthly lookup should use `Date.Month` and a value such as `"2026-01"`.

A Dimension filled from a source can hold timestamps rather than plain dates, such as one member per sync at `2026-07-01 00:00:00+00`. Where you write a date decides what it matches:

- As a lookup key, such as `` amount_usd$[synced_month = date(2026, 7, 1)] `` or `` amount_usd$[synced_month = `Snapshot Month`$] ``, a date selects the member at midnight of that day, as long as every member of the Dimension comes from its source rows. A Dimension with its own member list or formula keeps exact matching.
- In a rule's condition, the part that says which cells the rule applies to, a date never equals a timestamp member, so `[synced_month = date(2026, 7, 1)]` reaches no cell.

Date text such as `"2026-07-01"` reaches the member at that instant in both places, and `` synced_month.Month = startofmonth(`Snapshot Month`$) `` compares two dates, so it is true for every member that falls in the Snapshot Month.

## Ari changed only some formulas

Depending on the operation, a batch can apply valid changes while rejecting invalid ones, or reject the whole batch when all changes must succeed together. Ask Ari which changes were applied, fix the reported issue, and verify the resulting values.

## Ari saved the formula but reported a warning

When Ari saves a rule through a table, the receipt can carry warnings about rules that saved correctly but will not do what the wording suggests. Ask Ari to read them back if a number looks wrong right after a change. The common ones are:

- **An imported Variable read in Forecast months.** A Variable loaded from a connection has values only through **Last close**. A rule that reads it in Forecast months reads 0 there, or an empty value when the Variable holds dates or text. The warning names the Variable and the rule that reads it, so you can find and move or replace that rule.
- **A constant that matches no Dimension item.** A condition such as `Step = "Committed"` saves, but when the item is spelled `Committed out` it matches nothing and every cell it reaches reads 0, or an empty value for a date or text Variable. The warning says the condition selects none of the Dimension's items, states the items' kind and how that kind is matched, and shows one or two of them so you can match the exact spelling. For a Dimension of timestamps it explains that `date(y, m, d)` is a date value and that `[Dimension].Month` is each member's month as a date; a date used as a lookup key at a member's midnight is not warned about, because it selects that member. When a set such as `Step in {"Committed out", "Expected in"}` names some items that exist and some that do not, the warning names each value that matches nothing. A Dimension whose items were added by hand, with no source table behind it, is checked the same way.
- **Two rules that tie.** Two saved rules that name the same number of Dimensions and pin the same number of items compete for the same cells, and the more recently saved one wins. Saving either again flips the result. The warning names the rule the new one ties with.
- **A shared rule that was replaced.** A rule belongs to its Variable, so giving a Variable a new default while placing it on another table rewrites the rule every table reads. The warning names the rule it replaced. See [A rule belongs to its Variable](/dashboards/build-and-format-tables#a-rule-belongs-to-its-variable).
- **A read that lands on the generated default.** A plain reference keeps every coordinate of the cell it runs in, Date included. A monthly Payroll rule that reads `` `Annual Wage` `` reads it at Employee × Date.Month, and an input saved once per employee with no Date is not there, so the read gets 0 in every month, or an empty value for a date or text input. The warning names the read, where it landed, and the absolute spelling that reaches the input, such as `` `Annual Wage`$[Employee = this.Employee] ``.
- **What the first Forecast month read.** When the written rule reads a prior period, an imported source, or a Variable with no value there, the receipt adds a note stating what the rule computed in the first Forecast month and what each read returned, for example "First forecast month: `Headcount`'s rule computes 3 in 2026-09 (Last close 2026-08-31). There it read `Headcount` (offset -1 month) = 0 (no rule or input there: the generated zero); `Hires` = 3 (a rule or input)." A roll-forward that starts from an empty last Actuals month shows up here instead of several steps later.
- **A rule saved at a coarser grain.** A default written through a table whose periods are years, in a monthly Model, is saved at year grain. The warning says the year cells compute it whatever their month cells hold, and that the month cells do not read it.
- **Which Scenario the write used.** When the call named no Scenario, the receipt says which one it used, the one you were viewing, because that can change between turns.

A receipt also states rules the save wrote for you: the time rollup a new monthly row gets (`SUM`, or `LAST` for a balance), and the level defaults that make a breakdown's totals add up the rows beneath them. See [How aggregation works](/formulas/core-concepts/how-aggregation-works#default-time-rollup) and [Breakdown totals add up the rows beneath them](/formulas/core-concepts/how-cfoai-chooses-a-formula#breakdown-totals-add-up-the-rows-beneath-them).

One case is refused instead of warned: a numeric aggregate such as `sum` or `max` over a text or date operand, for example `max(synced_month$)` on a date Dimension. Use `first`, `last`, or `count` for a value that is not a number.

## A table axis has thousands of items

Placing a Dimension with more than about 1,000 items on a table's rows or columns is allowed, but the write reports how many items the axis carries and that every entry on the other axis is calculated for each of them. Use a filter to show the items you need when the table becomes slow.

## A table cannot date an imported source

A Table Block that shows a Variable from an imported source by period needs to know which of the source's columns dates its rows: a date column the source contributes to the Model's Date, or a date column saved as the preferred time column of the Variables read from it. When the source has neither, the table stops calculating and reports:

```text
Source "Payroll" (6077cf1b-…) has no date column to read it by. Give the source a date column, or set one of its date columns as the preferred time property ("Dated by") of the variables read from it.
```

Tell Ari which column dates the rows, and Ari saves it as the source's preferred time column, or add a date column at the source and sync again. A read that does not depend on Date still answers, such as `last` over the source's rows in a table with no Date axis. Ari receives the same message when it reads the table, so it can name the source to fix.

## A date or text cell nobody filled in reads empty

A Variable cell that no rule or input covers reads a default, and the default depends on the Variable's type. A number reads 0, so sums and roll-forwards over a Salary nobody entered keep working. A date or text Variable reads an empty value, written `null` in a formula, so an End Date entered only for people who left is empty for everyone else, and `` if(`End Date` = null, 1, 0) `` marks the people still employed without a placeholder date far in the future.

Two things follow from an empty value:

- A comparison with it, such as `` `End Date` < date(2030, 1, 1) ``, is itself empty, so `if` takes its false branch.
- A prior-period read such as `` `End Date`[-1] `` is empty where the earlier period was never set.

The default applies per formula range. An imported Variable with no saved rule reads its source column in Actuals and the default in Forecast months. See [Test for an empty value](/formulas/formula-guides/use-conditional-logic#test-for-an-empty-value).

## A division returns an error

Division by zero produces a calculation error. Guard the divisor or provide a fallback:

```text
iferror(`Gross Profit` / Revenue, 0)
```

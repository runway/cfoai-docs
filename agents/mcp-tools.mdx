The cfo.ai MCP server publishes 40 tools: Ari's public product tools plus three MCP-only tools, `list_orgs`, `inspect_chats`, and `edit_chats`. Two of the 40, `inspect_comments` and `edit_comments`, are listed but refuse every call; see [What the server does not publish](#what-the-server-does-not-publish). This page describes the server, each tool, and the conventions every call follows. To connect a client, follow the [Agent instructions](/agent-instructions).

## Server

| Fact | Value |
| --- | --- |
| Address | `https://api.cfo.ai/mcp`. `https://api.cfo.ai/mcp/v2` serves the same tools; use `/mcp` for new connections. |
| Transport | Streamable HTTP, stateless. Each request authenticates and selects its workspace on its own, and the server neither issues nor requires an `Mcp-Session-Id`. |
| Sign-in | OAuth. A person approves the client in a browser, and the client sends the token it receives in the `Authorization` header. The protected resource metadata is at `https://api.cfo.ai/.well-known/oauth-protected-resource/mcp`, and clients register themselves through dynamic client registration or a client ID metadata document. |
| API keys | None. cfo.ai issues no API keys or access tokens to copy; every client signs in as a person and acts as that person. |
| Instructions | The server sends cfo.ai's modeling instructions when a client connects. |
| Tool list | Fixed for each server process. The tool list carries a five-minute private cache hint, and the server advertises `listChanged: false`. When a client's definitions are stale, refresh its tool list or start a new conversation. |
| Request size | A request body holds at most 1 MiB. A larger one is refused with **The MCP request is too large.** |
| Batches | JSON-RPC batch requests are refused with **JSON-RPC batches are not supported.** |
| Rate limit | 60 calls a minute for each tool, per user and workspace; `list_orgs` has no limit. A call past the limit fails with **rate limit exceeded for** followed by the tool name. |

## Published tools

A tool marked read-only never changes saved state. The **Actions or fields** column lists a multi-action tool's blocks; for a single-purpose tool it lists the fields it takes directly.

### Tables, formulas, and mappings

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_table_blocks` | Read-only. Lists saved tables, reads cells with their formulas and sources, compares a table with an earlier saved state, and reads Variables, Dimensions, and their items. A `variable` or `dimension` read without `target` lists every one you can read as a short entry, and `contains` narrows the listing by name; see [Find a Variable or Dimension by name](/agents/read-formulas#find-a-variable-or-dimension-by-name). A `list` reads one Scenario; without `target` or `page` it also carries `other_scenarios`, each other Scenario the user can read that holds saved tables the listed Scenario does not, with `tables_not_in_this_scenario` counting them, or `[]` when none does. `read.rows`, `read.columns`, `compare.rows`, and `compare.columns` accept one selector as a plain string as well as a list. A day or month that matches no column of a coarser table selects the period that contains it, such as Q4 for December, and a note names the requested date, the period returned, and its grain; an exact match wins, and a date two periods contain stays ambiguous. A `read` follows the table's saved choice to hide empty items, and a selector for an item the table hides is refused with the item, its Dimension, and the rule or saved filter that hides it, so a hidden row is not reported as missing. A row or column selector that names a period outside the saved window is refused with the saved window and a pointer to `list`, which reports other tables' windows; the refusal proposes no change to the table. A `period_range` that reaches past the window is not refused: it returns the periods inside the window with a `read_note`, as described under [Results](#results). In an `edit_table_blocks` `cell_updates` entry the same range is refused whole; see [Write values into dated columns](/agents/write-formulas#write-values-into-dated-columns). A `list` entry summarizes the saved table under `summary`: `rows` and `columns` count its top-level entries, `first_rows` names up to five rows, and `window` is its saved window; a table that places a Variable or Dimension you cannot read keeps its summary and carries `layout_problem` **This saved table includes a property you cannot read.** `read.rows` and `read.columns` also take predicates over each item's own value, such as `` Invoice where `Days overdue` > 0 `` beside item attributes such as `Employee where Employee.Department = "Engineering"`, for a Variable stored once per item; a Variable whose value varies by month, including through a default formula that reads monthly inputs, or by another Dimension is refused, and a period refusal returns the complete filter with an example month from the table's window, the read's Last close month when it falls inside it. A `next.after` cursor passed back beside the Scenario it was issued for continues even when the two spellings differ, such as `Base` beside a cursor that names `Base#52f`, when both name one Scenario at the read's saved version; a different Scenario is still refused. A `variable` read that names a Dimension, or a `dimension` read that names a Variable, is refused as `invalid` with **[name] is a [kind].** and the read that shows it; nearby-name suggestions cover both kinds and hand-added items, naming their Dimensions, and a missing breakdown row names up to three tables that break the Variable down by that Dimension. | `list`, `read`, `compare`, `variable`, `dimension`, `items`, `bounds` |
| `edit_table_blocks` | Creates, updates, reshapes, copies, or deletes saved tables in one atomic change each. A `create` puts the table on an existing Page named by `page`, or on the Page in view; it creates no Page, and a missing one is refused with a pointer to `edit_pages`. A saved table has no row count of its own; one write resolves at most 10,000 operations. Writes to one Page's tables in a Scenario run one at a time, as do all creates and cell writes, and a write not committed by its time limit saves nothing. Table settings cover what a person sets by hand: a `style` with `scale` (thousands, millions, or billions), `negativeNumbers` (`MINUS` shows -1,250 and `PARENTHESES` shows (1,250), in every number format at the cell's decimals and scale; where no scope of the table sets it, the workspace display from `edit_org` `negative_numbers` applies, and without one negatives show `MINUS`), and text `color`, a Dimension's `color`, each column's `width` and `pinned` in `column_updates`, and `formula_width` and `row_header_width`, all widths at least 100 px. `row_totals_at_bottom`, on an `update` or under `settings` in a `reshape` layout, saves where each row group's total shows: `true` shows a label-only heading above each expanded group's details and a Total row below, nested groups included, a collapsed group shows one total row, and Excel exports follow it; `false` keeps totals above details. Reads return it under `presentation.row_totals_at_bottom`. Writes every model formula, and sets time rollups and the Scenario's calendar. A `create` with a `tables` list saves them in one change, and a formula, a `variables` settings entry, or a `dimensions` settings entry in any table names what any table of the list declares, whatever the order. `remove_items` deletes a member together with its rows on every table and the formulas whose condition selects only it, and the receipt's `members` counts them as `removed_rows` and `removed_rules`. `row_updates` takes `label`: a Dimension mapped from the rows' Dimension and shown as a field column, such as Name beside Employee ID rows, so each row shows its Name while its Employee ID stays its identity; `{"inherit": true}` shows the members again. A Dimension not mapped from the rows' Dimension, or one without a field column on the table, is refused with the candidates, and reads name the saved label; a `label` naming a mapped field whose column the table does not show adds that column in the same write, and a table whose rows hold Variables refuses it, because Variables take one axis. `dimension_display` on an `update` saves **Display as** for each named Dimension on the table, `PILL` or `PLAIN_TEXT`, for every viewer; a Dimension not on the table is refused, and reads return the saved choices under `presentation.dimension_display`. A `delete` of Variables, Dimensions, or both needs no `target`: each one uses its own table, or the only readable table that shows it, one that no readable table shows is deleted without a table, several matches need `target`, and the receipt names the tables; the whole deletion saves together or not at all, and still needs `force` to confirm. An `add_dimension_items` entry placed `under` a parent with business items stays under that parent, with no model-wide membership; an item added with no such parent is model-wide, an existing model-wide item keeps that scope, and the receipt reports `scope` and `shown_at`, the parent paths the table shows it under. A `members` list or condition on a row or column replaces the whole saved filter, so a condition replaces a fixed list and a list replaces a condition, `[]` clears it, and omission or `null` keeps it. An item name in `members` matches exactly first; when no exact item exists, surrounding spaces are trimmed to find one. A numeric item matches by value, so `96`, `96.0`, and `9.6e1` select the same employee ID in reads, filters, and cell writes, while a text item still needs its exact text; a `create` finds imported and formula-computed numeric items as well as manual ones. A cell value must fit the Variable's type: a number for a number Variable, a string for text, date, and UUID, a boolean or exactly 0 or 1 for a Boolean, and `null` for any; one value of the wrong type refuses the whole write, naming the cells by row and column label and noting that `variables` with `data_type` can change the type in the same write. A read reports mismatches already saved under `literal_type_mismatch`, with a count and up to five samples; a person's edit in the app still saves as typed. A formula save, or a row insert, also warns when a formula on a row reaches the lines under it without reading their Dimension, so each line would show the row's whole amount, such as **In Main, Revenue's rule also reaches the P&L Account lines under each TEAM; it does not read P&L Account, so each line shows its TEAM's whole amount.** Copying a `list` result's pins and column widths into an `update` is accepted when they match the saved values and refused when they differ, with `column_updates` as the one writer for them; an explicit `show_empty_members` wins over a copied value. A table with `columns: []` and Variable rows, with or without business breakdowns, needs `window.granularity: NO_GRANULARITY` and shows one **Value** column; `list` returns that layout in a form `create` and `update` accept. In a `create` with a `tables` list, an invalid layout gets one explanation at its own position, such as `/create/tables/1`. A create, reshape, or structural insert that leaves a Variable in two or more rows or columns of the table, where it had fewer, reports it under `duplicate_placements` with `before`, `after`, and each placement's ref, rows and columns inherited from the parent Scenario included; the repeats save as requested, and a rename or formatting write adds no notice. A new numeric currency row takes its currency code from its formula inputs when every Variable input shares one code, else from the table's other money rows when they share one, else from a code at least 90% of the workspace's coded numeric Variables use; a workspace with no saved code keeps the USD display, and any other unresolved case refuses the whole write, listing the workspace's codes and the Variables and inputs without one, and accepts `variables[].currency` with the same new names. Replacing the whole item list of a Dimension that gets its items from imported data is refused with **dimension "[name]" gets items from imported data; replace_items is unavailable. add_items and remove_items support manually added items**. | `create`, `update`, `reshape`, `copy`, `delete`, `set_time_rollup`, `update_calendar` |
| `inspect_dimension_mappings` | Read-only. Lists the mappings a reporting Dimension owns, or reads one lookup chosen by its exact source keys. `pairs` and a row's `item` hold fixed items only; a row whose mapped value a formula calculates carries `formula` in place of `item`, written with Dimension names, such as `$[Practice = "Group"].Practice`, so a count of the items a Dimension maps to counts real items and a pair copied back into `edit_dimension_mappings` `map` never saves formula text as an item. A lookup whose rows all map to formulas reports `"pairs": {}`. `catch_all` is a fixed item as its item, or a calculated fallback as a formula in Dimension names. A row whose mapped value or condition reads a Variable or Dimension the user cannot read is counted in `unreadable_rows` and not shown, so no name the user cannot read appears; the `edit_dimension_mappings` receipts (`catch_all` and the removed rows) apply the same check. | `target`, `keys`, `limit`, `after`, `scenario`, `as_of_point` |
| `edit_dimension_mappings` | Maps items of source Dimensions to a reporting Dimension's items, sets or clears the catch-all, removes rules or lookups, and combines or splits compatible source Dimensions. A removal that leaves no lookup on the target also removes its catch-all, since a fallback is the item for records no lookup row matches; the receipt lists it under `removed`, reads `catch_all` back as null, and warns once. A removal that leaves another lookup keeps it, and `catch_all` can still set a fallback before the first `map`. `map` takes `replaces_keys`, the source fields of one existing lookup to replace in the same save, so title and department can take over from employee ID without a saved state in which neither lookup exists; the save replaces the lookup's rules together or saves nothing, other lookups and the fallback stay, and `replaces_keys` that names no lookup on the target is refused. A `combine_dimension` rewrites the formulas and tables that read the removed Dimensions and changes no Canvas block. Its receipt lists the Canvas blocks to look at under `canvas_repairs`, each with `target`, `scenario`, and exactly one mark. `repair_needed: true` marks a block whose saved state or configuration, which includes its datasets, form, and code, holds a removed Dimension's ID, a `Name#hex` reference to it, or its display name as a whole word; the name is searched only when the kept Dimension has a different name. `not_checked: true` marks a block that holds none of these and whose code can send Ari a request (`startAriChat`, `askAri`, or `prepareScenario`); that request's text is built when the code runs and was not read. A chart that matches nothing and sends no request is left out, because chart code reads a Dimension only through a dataset, which saves the Dimension's ID. Blocks you cannot read are left out, and an empty list means nothing matched. The receipt's `warning` states these rules; read a listed block with `inspect_canvas_blocks` and change it with `edit_canvas_blocks`. | `map`, `unmap`, `catch_all`, `clear_catch_all`, `drop_mapping`, `combine_dimension`, `split_dimension` |

### Pages and Canvas blocks

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_pages` | Read-only. Reads the page tree, each Page's blocks in order, saved table settings, and reusable references. Each Table block in a `read` carries its saved `layout` (`rows`, `columns`, and `settings` in the shape `edit_table_blocks` `create` and `reshape` take, with each axis's filters, Date groupings, roles, and children, and the names of the formula ranges `settings.formula_breaks_hidden` hides), its `signature`, and its `presentation`. When the table places a Variable or Dimension you cannot read, all three are left out and `layout_problem` reads **This saved table has structure that cannot be represented safely: it shows a property this read cannot name.** Each Page in a `list` or `read` carries `created_by`, from its first saved change: the workspace member's `display_name` and `kind`, `is_current_actor`, and, when Ari made the Page, `ari_chat` as `this_chat` (this conversation, its task steps and background imports included) or `another_chat`. `kind` is `unknown` when the record names no member, and a Page made before change logs recorded the chat has no `ari_chat`. A `read` with `include_text` returns the Page's own prose as `markdown`, with each live block in place as a marker such as `[TABLE block: Name#a1b]`, and the Page's `document_revision`, which `edit_pages update_text` takes to refuse a stale edit. | `list`, `read` |
| `edit_pages` | Creates, renames, moves, shares, and deletes Pages; sets page icons and date ranges; adds and edits Text blocks; reorders and removes blocks; creates share links. A Page date range sets the window of every table, chart, and Canvas dataset on the Page; a Canvas dataset whose window is `pinned` keeps its own. A `move` renumbers only the sibling Pages the user can edit; a sibling they cannot read, or can read but not edit, keeps its saved place. When two such fixed siblings leave no room for the requested position, or the position would put the Page below a fixed sibling that has no saved position, the move is refused with **the requested position is not available with your page access**. A Page whose read access was removed after the call resolved it is refused with **page [id] is not available with your page access.** and nothing is renumbered. An `update` that moves a Page under a new parent follows the same rules. A Page whose parent a Scenario deleted, such as a subpage Main added under a Page the Scenario removed, is a top-level Page in that Scenario. `update_text` with a Text block target replaces that block; with a Page reference as `target` it replaces the Page's own prose from `markdown` or `text`, keeping every embedded block marker once, in its saved order and nesting, since `reorder_blocks` and `delete_block` own the blocks. A Text block holds no table. `add_text`, `update_text` on a Text block, and the initial `text` of a `create` refuse a Markdown table with **text blocks cannot contain a markdown table**. `add_text` and `update_text` also refuse a `content` document that holds a `table`, `tableRow`, `tableHeader`, or `tableCell` node at any depth, with **text blocks cannot contain a [node type] node**. Nothing saves, and the hint says where the table belongs: **A table of model variables or dimensions is a table block (edit_table_blocks; inspect_table_blocks with action variable or dimension lists them), and a table of ad-hoc values that are not modeled is a Canvas block (edit_canvas_blocks).** Prose that only mentions a table, or contains a `|`, is accepted. Prose around an unchanged marker can change as much as it likes; the live block stays. A refusal names the first marker that is wrong and lists the markers in their saved order: a marker whose count differs from the saved page, `page Markdown contains 0 occurrences of "[TABLE block: Revenue#a]"; the saved page contains 1; saved marker order: [...]`; one that `appears in the text but not as its own block, so the live block would be lost`, such as a marker inside a sentence or a code block; one that `would repeat the live block`; or one that `is out of order (position 2, saved position 1); page-text edits keep live blocks in their saved order`. A change to how blocks nest is refused with `the page's embedded blocks must keep their saved nesting; page-text edits change prose`. Pass the inspected `document_revision` to have the edit refused when the prose or block membership changed since that read: **The page's prose or block membership changed since the supplied document_revision was read.** Identical Markdown changes nothing. A `delete` of a Page that holds blocks, sent without `force`, saves nothing and answers with the Page's blocks, the Variables and Dimensions the deletion would remove, and the formulas and blocks elsewhere that would break; a Variable or Dimension still shown on another table survives, and its references are not counted. A completed Page, table, or block deletion labels the references it broke, an empty list meaning the check found none, with unreadable ones as a count and an oversized list cut to an omitted-entry count. Confirmation refusals and completed deletions of Pages, tables, charts, Canvas blocks, Variables, and Dimensions also name the user's own Triggers whose instructions name what is removed, with their owner, under `dependent_schedules`, and `dependent_schedules_omitted` counts the ones a full result left out; only the user's own Triggers are checked, paused ones included, and a Trigger that names the object in plain prose rather than a quoted name or `Name#hex` reference is not listed. | `create`, `update`, `move`, `share`, `create_share_link`, `delete`, `add_text`, `update_text`, `delete_block`, `reorder_blocks` |
| `inspect_canvas_blocks` | Read-only. Reads selected Canvas blocks: saved source and its `source_hash`, `copy_owner` (which Scenario's copy of the content the block shows), dataset layouts and Scenario bindings, display state, position, revision, and references. `include_source: false` returns each block without its source, for a read that needs only the datasets and settings. Each `dataset_layouts` entry is the `edit_canvas_blocks` `datasets` entry that saves it, `{name, scenario, layout, window}`, or carries `layout_problem` when a Canvas write cannot declare the saved layout; see [Read saved Canvas blocks](/agents/canvas-blocks#read-saved-canvas-blocks). | `target`, `page`, `scenario`, `as_of_point`, `source_offset`, `include_source` |
| `edit_canvas_blocks` | Creates a Canvas block on a Page, or changes one. A whole `source` on an `update` names `based_on`, the `source_hash` of the read or write it was written from, and saves only while the saved source still has that hash; see [Change a saved block](/agents/canvas-blocks#change-a-saved-block). | `create`, `update` |
| `inspect_canvas_library` | Read-only. Finds Canvas components and templates, and reads their instructions and props. | `list`, `read` |
| `validate_code_blocks` | Read-only. Renders up to 8 saved Canvas blocks in a browser and reports errors, warnings (including **Design:** findings that name an element, what was measured, and the fix; see [What `validate_code_blocks` reports](/agents/canvas-blocks#what-validate_code_blocks-reports)), what each chart plotted, guide anchors, and, on request, a screenshot: the full Canvas, a fixed `desktop-opening` or `phone-opening` view with an independent design assessment billed to the workspace, or a measured `viewport`. `top` starts the full Canvas or `viewport` image lower in a block taller than one image, and `click` names one control, such as a tab, to click once before the image is taken. | `target`, `scenario`, `visual_review` |

### Scenarios and history

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_scenarios` | Read-only. Reads Scenarios, their owners, Snapshots, and descendant trees. | `list`, `read`, `subtree` |
| `edit_scenarios` | Creates, renames, snapshots, merges, or deletes Scenarios. `create` makes a regular Scenario on Main, or, with `based_on` naming another Scenario, a copy of it: a regular Scenario with the same base that holds that Scenario's own changes, so later changes to the shared base show in both and edits to one stay in it. With `based_on` naming a Snapshot, the copy is an editable Scenario on Main that starts equal to the Snapshot, the edits saved in it since the pin included. The copy saves only what differs from Main when it is made and follows Main afterwards: a formula that matched Main changes when Main changes it, a table added to Main appears in the copy, and a table deleted from Main leaves the copy together with the copy's own values in it. Only the Snapshot stays pinned, so keep the Snapshot when the pinned state must outlast a change to Main; a Snapshot still cannot be snapshotted again. `delete` refuses a Scenario that has children with **scenario cannot be deleted while it has child scenarios**, and a Snapshot is a child of the Scenario it was taken from. A Snapshot is a pinned, editable copy: changes flow neither from its source into it nor from it back to the source, so a `snapshot` result names the source, and a Page, Canvas, table, or mapping save into a named or currently viewed Snapshot adds one reminder that the source does not receive the edit. | `create`, `rename`, `snapshot`, `merge`, `delete` |
| `inspect_history` | Read-only. Reads the changelog, the net difference between two points in time, and what a Scenario would merge into its parent. For a Scenario with a parent, `changes_between_points` lists the Scenario's own edits in `changes` and counts the changes it shows only because its parent or an ancestor made them over the same range in `inheritedChanges`, with `parentLayerId`, `count`, and `resources` by resource type; the parent's own diff over the same points lists them. Main's diff has no `inheritedChanges`, and a Scenario's `changelog` still lists the entries it inherited from Main. | `changelog`, `changes_between_points`, `scenario_summary`, `read` |
| `edit_history` | Undoes or redoes changes, or reverts a Scenario to a past changelog entry. Each operation returns its new changelog entry and the action that reverses it. Undo and redo restore only the fields the listed entries changed, so later edits to a record's other fields stay; when a later entry edited one of the same fields, the call answers `error_kind: conflict` with `Nothing changed: reversing changelog entry [N] would replace later edits: changelog entry [M] changed the [fields] of [record].` and saves nothing. | `undo`, `redo`, `revert` |

### Connected data

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_integrations` | Read-only. Reads saved connections with their readiness and safe next action, the integration catalog (provider integrations, and under `mcp_servers` and `apis` every hosted MCP server and API cfo.ai connects, each with its `display_name` and a `description` of what it provides; a `query` or `category` read adds each match's category, endpoint or base URL, authentication kind, and documentation link), permitted API endpoints, connection-link progress, ingestion status, sync setups, saved API and MCP settings (admins only), saved queries, and ingestion jobs. `query_results` runs one saved query and returns its rows without adding data to the Model; it runs in Snowflake for every connection, a file upload included, which is where the query's loads run. It reads a `linked` connection, and also a `relink_required` one, whose sign-in lapsed but whose synced tables stay in the warehouse: that read carries `saved_data`, with `connection_status`, `last_synced_at` (when the newest completed sync finished, or `null`), and a `detail` sentence saying the rows are what earlier syncs saved, and the connection row reports `warehouse_readable: true`. A file upload's connection row reports `warehouse_readable: true` once its current file has finished loading, before a saved query has imported it. While the file is still loading, or when its load failed, the row reports `warehouse_readable: false` with a `warehouse_readable_reason` that begins **the uploaded file's rows are not readable yet**. A connection in any other status (`pending`, `partially_linked`, `failed`, `disconnected`) answers `ok: false` with `error_kind: blocked`, **[Connection] is [status], and a warehouse read accepts a connection that is linked, relink_required, or COMPLETED.** followed by **No completed sync is recorded for it.** or **Its last completed sync finished at [time].**, the fields `connection`, `connection_status`, and `last_synced_at`, and a `hint` naming the `edit_integrations` action that accepts the connection: `request` continues a `pending` or `partially_linked` authorization, and `relink` opens a new sign-in for a `failed` or `disconnected` one. While a sync is under way, a read of a whole connection counts the rows its saved queries have already published in the model under `materialized` and `materialized_rows`; a read of one run reports only that run. `outcomes` also lists the user's own recent sign-ins to this MCP server. `sync_setups` for an MCP server carries `sync_page`, which states how one sync page calls the server and its 45-second allowance. `sync_setups` for one source also carries `ingestion_connection`, one sentence that says whether the source already has the ingestion connection its setups load through, or whether its first saved setup creates one, which is exempt from the plan's integration limits, and in that case whether the workspace can add it now or the plan refuses it and why. A QuickBooks Online connection row carries `accounting_basis`, `cash` or `accrual`; a row without it has synced on accrual and reads the company's preference at its next sync. A catalog entry for a Fivetran file store carries `loads`, which says how the store's files reach cfo.ai: Box, Dropbox, and SharePoint copy every file in the chosen folder as it is, for Ari to list and read; OneDrive loads each tabular file, one table per file or worksheet; the bucket, server, and mailbox stores load every file matching the setup's pattern into the connection's one table, archives included; and files in other formats, such as PDF and Word documents, are not synced by a store that loads rows. A completed query job and an ingestion summary carry `conversion_notes` in two cases: when timestamp values lost fractional seconds beyond milliseconds, naming each column and its count, the published precision staying milliseconds; and when a date column holds dates before 1900 or after 2299, which month, quarter, and other period formulas leave out, one note per column with the count, one example (the source text when it is at most 256 bytes, else the date) and that example's 1-based row in the query result: **[untrusted_source_data] Found 1 date in column "Due Date" with unsupported calendar periods, including "10/30/3036" at source result row 7. Formulas that read this column by month, quarter, or another period leave these rows out. Exact-date filters can still match them. The source values were not changed.** A failed import adds no note, and each completed import reports only its own. A `jobs` read without `job` lists the newest raw jobs and the newest query jobs, most recent first: up to 100 of each kind, as many as fit one result. `limit` sets the most jobs of each kind, so `limit: 1` returns the newest raw job and the newest query job. A list that leaves jobs out carries `truncation`, whose `shown` and `total` count both kinds together; `total` is stated only when the read loaded every matching job, so it is absent when a kind reached the 100-job bound. The list has no `next`: narrow it with `status`, `kind`, or `query` to reach older jobs. `limit` beside `job`, `task_limit`, `task_after`, or a `tasks` value other than `none` is refused with **limit bounds a list of jobs, and this read returns one job; task_limit bounds a raw job's task page**. `jobs` pages a raw job's tasks with `tasks`, `task_limit`, and `task_after`. ### Ari chats

Two MCP-only tools let a client hand a question to Ari instead of calling tools itself. A chat a client starts is an ordinary Ari chat, with the same agent, billing, memory, and Skills, and the person can open it in the cfo.ai web app, where its entry in the chat list carries an **MCP chat** mark.

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_chats` | Read-only, MCP only. `list` returns the user's chats in this workspace, most recently updated first, each with its `ref`, `state` (`running`, `idle`, `needs_response`, or `error`), a busy flag, and its `resource_uri`. `read` returns one bounded page of a chat: the user's messages, Ari's last message in each turn, the questions and plans Ari waits on, cards that only the web app can answer as `waiting_in_app` items, and delivered files. | `list` (`status`, `title_query`, `limit`, `cursor`), `read` (`target`, `after`, `before`, `wait_seconds`, `steps`) |
| `edit_chats` | MCP only. `create` starts a chat with a message in the Scenario `_context.scenario` names. `send` adds a message to a chat, and also answers Ari's questions and approves a plan. `stop` ends the running turn; `drop_waiting` also deletes messages not yet sent. `update` renames, archives, or restores a chat. Turns bill the workspace like chats in the app. | `create` (`message`), `send` (`target`, `message`, `delivery`, `request_id`), `stop` (`target`, `drop_waiting`), `update` (`target`, `title`, `archived`) |

- **Reads are bounded.** `steps` chooses how Ari's tool work shows. `none`, the default, folds each turn's tool steps and the notes between them into one `steps` item with their count. `summary` shows one item per step. `full` adds each step's input and result, cut at 4,000 characters. A page holds at most 40 items and about 48 KB. A read without a cursor keeps the newest items and returns `older` to page back; a read with `after` keeps the oldest and returns `next`.
- **Waiting for Ari.** `create` and `send` return at once with `next`: the exact `inspect_chats` `read` call that waits, up to 50 seconds through `wait_seconds`, while the chat is busy. A read of a chat that is still busy returns another `next`. A client that sends a progress token gets a progress notification each second it waits, naming what Ari is doing. To hear when a turn starts or ends instead of waiting, subscribe to the chat's `resource_uri`, `cfoai://orgs/{org_id}/chats/{chat_id}`, on the MCP 2026-07-28 `subscriptions/listen` stream, and read the chat's newest page with `resources/read`. The older `resources/subscribe` is refused.
- **While Ari works.** `delivery` on `send` is `steer` by default, which ends the running turn after its current step and starts the next turn with the message; the work in progress carries into that turn with its saved progress, and the message is read as an addition to it unless it cancels or replaces it. `queue` waits for the turn to end. `request_id`, a UUID the client makes, makes a repeated `send` a `no_op` that returns the same `message_id`.
- **Limits.** A `create`, or a `send` to a chat that is not busy, is refused when 5 of the user's chats in the workspace are already busy. Only the chat's owner can read or write it. Approval buttons, email **Send** buttons, confirmations, and sign-ins work only in the web app: give the person the `chat_url` the result carries. An MCP read does not mark the chat read in the web app.

Every tool except `list_orgs` also accepts these two fields at the root. The server removes them before the tool runs.

| Field | Meaning |
| --- | --- |
| `org_id` | The workspace, by ID or slug. Optional when the user belongs to one workspace. See [Choose the workspace](#choose-the-workspace). |
| `_context` | What the person is working on, all optional: `scenario` (a Scenario name or reference as `inspect_scenarios` returns it; the Main Scenario when omitted), `page` (a Page reference as `inspect_pages` returns it), `timeZone` (such as `America/New_York`), and `utcOffset` (such as `-04:00`). Names and references only: the tools never return the IDs behind them, so a Page's UUID is read as a Page name and matches nothing. A value that names nothing, or several things, is refused before any tool runs, whether or not that tool reads `_context`; the refusal starts with the field, such as `_context.page:`, keeps any candidates the lookup found, and names the tool that lists valid values. Send `timeZone` or `utcOffset` when relative dates matter. Any other key, including the retired `layerId` and `pageId`, is refused with **_context must contain only scenario, page, timeZone, and utcOffset**. |

### The Scenario a call uses

Most model tools take `scenario`, by name or returned reference. `"Main"` names the base Scenario whatever name the workspace stores for it, and the id that Page and block links print after `?layer=` is accepted too; a stored name wins, so a Scenario literally named Main keeps its own meaning. When a call omits `scenario`, the tool uses the Scenario in view: the one `_context.scenario` names, or Main when `_context` names none. Pass `scenario` on every write so the target does not depend on context. [Create and update formulas](/agents/write-formulas#write-in-a-scenario) quotes the sentence a table write adds when `scenario` was omitted.

The server resolves `_context.scenario` again on every call and keeps no Scenario between calls. After a Scenario is deleted, a call that still names it in `_context.scenario` is refused before any tool runs, so no later call reads or writes its parent in its place: name a Scenario that exists, or leave `_context.scenario` out to use Main. When an `edit_scenarios` `delete` removes the Scenario its own `_context.scenario` names, the receipt adds a `scenario_warning` that names the deleted Scenario and, when the user can read it, its parent, and ends **Writes require a named scenario until it is restored.**

## Shape each call as one action block

A tool with several actions takes exactly one block named for the action, with that action's fields inside it. There is no flat `action` field.

```json
{ "read": { "target": "Operating Plan", "rows": ["Revenue"] }, "scenario": "Main" }
```

- Each tool's input schema says, in its description, which blocks exist and which fields sit beside them: "Fill exactly one action block: list, read. Fields beside the block apply to it: as_of_point, scenario."
- An empty block selects an action that needs no fields, such as `{"list": {}}`. A block set to `null` counts as not filled.
- Fields beside the block apply to it: `scenario` on most model tools, `as_of_point` on `inspect_pages` and `inspect_scenarios`, `validate` on `edit_canvas_blocks`, `target` on `edit_dimension_mappings`, and `idempotency_key` on `edit_memory`. A block that takes such a field also accepts it inside; when both places carry it, the two values must match.
- Single-purpose tools take their fields directly at the root, as the table above shows. `notify_user` takes an `email` block, a `slack` block, an `in_app` block, or several of them.
- The schema root is a plain object, so every client can see the blocks. The rule that exactly one block is filled is enforced when the call runs.
- Unknown fields and retired request shapes are refused before anything runs. Nothing is translated from an older shape.

### Refusals for a wrong shape

A refused call changes nothing. Its message names the problem without repeating any value you sent.

| Mistake | Message |
| --- | --- |
| No block filled | `no action block is filled; the call takes exactly one of [...]` |
| Two blocks filled | `the call takes exactly one action block; [...] are filled` |
| A flat `action` field | `action "read" is the read block; the fields of that action belong inside it: {"read": {"target": ...}}` |
| `action` inside a block | `the read block takes no action field; the block name selects the action` |
| A block that is not an object | `read must be an object holding that action's fields` |
| A root field that is not a block | `<name> is not an action block; the blocks are [...]` |
| A field the block does not take | `<field> is not a field of the <block> block` |
| A beside-field inside a block that does not take it | `<field> belongs beside the <block> block, not inside it` |
| The same field beside and inside, with different values | `<field> is <value> beside the <block> block and <value> inside it; a call carries one <field>, in either place` |
| A value of the wrong type or shape | `<path> received <what>; it accepts <what>`, such as `/sections/0 received a string of 9 characters; it accepts an object whose section is one of …`. At an action's root, the path reads `the input`. |

A shape is described by type: a string by its length, an array by its item count, an object by up to 8 of its key names, and a number, boolean, or null by its type.

The refusal arrives with `isError: true` and this structure:

```json
{
  "error": {
    "code": "invalid_input",
    "message": "the call takes exactly one action block; [\"list\" \"read\"] are filled",
    "transient": false,
    "validation": {
      "issues": [{ "path": "", "code": "invalid_value", "message": "..." }],
      "accepted_fields": ["..."],
      "required_fields": ["..."],
      "truncated": false
    }
  },
  "state_changed": "no"
}
```

`validation` lists at most 20 issues; `truncated` is true when there were more. `accepted_fields` lists the chosen block's own fields plus the fields beside it.

## Choose the workspace

`list_orgs` takes no input and returns the workspaces the user can use through MCP:

```json
{ "orgs": [{ "org_id": "4127", "name": "Example Co", "slug": "example-co", "role": "admin" }] }
```

Pass a returned ID or slug as `org_id` on later calls. A number, or a string of digits, always names a workspace ID; anything else is read as a slug.

| Situation | Answer |
| --- | --- |
| `org_id` omitted, one workspace | That workspace is used. |
| `org_id` omitted, several workspaces | `org_id is required: you belong to <n> cfo.ai workspaces — pass one of [<ID> (<name>), …] (or call list_orgs)` |
| `org_id` omitted, no workspace | `no org_id supplied and you are not a member of any cfo.ai workspace` |
| A workspace the user is not a member of, or a slug that matches none | `you do not have access to this workspace`. Unknown and inaccessible workspaces get the same answer. |
| A numeric `org_id` that is not a positive whole ID | `a numeric org_id must be a positive whole cfo.ai workspace ID; pass slugs as strings`, or for zero `org_id must be a positive numeric cfo.ai workspace ID` |
| `org_id` neither a string nor a number | `org_id must be a string or number` |

## References and links

- Selectors accept readable names, returned references, or IDs, unless a field says it takes less. Copy references from inspection results instead of building IDs.
- A returned reference has the form `Name#hex`, such as `Revenue#a1b`. The suffix is a prefix of the object's identity, at least three hex digits, and unique among objects of its kind when the result was written. Later creates can lengthen it; an older reference keeps resolving while it stays unique, and a fresh inspection carries the current form. A reference also keeps resolving after its object is renamed, when exactly one object of its kind carries the suffix and the written name is one that object carried: `Gusto#940` names the connection now called `Acme Payroll#940`, and `Completion and final validation#6ca` names a text block after an `update_text` changed its first line, with or without a page named. A suffix with a name the object never carried is refused as not a reference, with the object's current reference. Scenario and Page references follow the same rule: `Plan#725` names the Scenario since renamed `Plan - No Series A#725`, and `SA26-18a#50c` names a Page after `edit_pages` `update` renamed it, in `edit_pages`, `inspect_pages`, and the `page` a table `create` names. `Main` with the base Scenario's suffix names the base Scenario. A table row or column reference, such as `Acquisition mix · R006-1#6e4`, keeps selecting its coordinate in reads and writes after the Variable it shows is renamed, when the written name is one the Variable carried and the digits select one coordinate; the same digits with a name the Variable never had are refused with `does not match a saved coordinate`.
- Words written in front of a whole reference, such as `Original Headcount#78e`, read the object the reference at the end names, when the longest run of its trailing words that any object under those digits ever carried is that object's own name. A shortened name such as `checks#1d5`, or text with no space before the name, is still refused with the object's reference as the candidate.
- A reference whose name only a hidden object carried, such as a deleted table, a table saved only in another Scenario, or one outside your access, is `not_found` with no candidate, even when one visible object shares its digits: **"Original vendor spend#72f" names no object this lookup can see. The one visible object under its suffix has no record of that name. Under that suffix the name belongs only to objects this lookup cannot see, such as a deleted object, one saved only in another scenario, or one outside this lookup's access.** The visible object's own references, including one issued before a rename, still resolve.
- A suffix with no name before it, such as `#199`, never binds an object. When exactly one live object of the requested kind that you can read carries those digits, the `not_found` answer gives that object's current reference as its one candidate: **"#199" is not a reference: it is a suffix with no name before it, and that suffix belongs to one table_block. A reference is an object's name and its suffix together.** When the digits belong to no readable object of that kind, or to more than one, the answer offers no candidates: **No table_block named "#199" was found. "#199" is a suffix with no name before it, and it does not belong to exactly one table_block this lookup can read.** Tables, charts, Canvas blocks, Pages, saved queries, connections, Variables, and Dimensions answer this way; Scenarios keep the plain not-found answer. A read that names several targets keeps the answer beside the targets it read: `inspect_pages` `read` lists it in `unresolved_answers`, `inspect_pages` `list` in `unresolved_page_answers` next to `unresolved_page_names`, and an `inspect_table_blocks` `list` in its `unresolved` notice under `answers`, each entry with `target` (the token as written), `message`, `candidates`, and the refusal's `hint`; when some answers do not fit one result, the tokens left out are listed in `unresolved_answers_omitted`, `unresolved_page_answers_omitted`, or `answers_omitted`.
- A name that is ambiguous or matches nothing is refused with `error.candidates` when alternatives are known: each with `display_name`, `ref` to pass back, `kind`, and, when ranked, `score` and `match`. A Variable or Dimension edit whose bare name two objects share lists their references, such as `Net Income#abcd1` and `Net Income#abcd2`, when the saved identity proves which object each names; a layout name whose suffix matches current objects, such as `Total OpEx#6c6`, is refused with the current references under that suffix, each labeled variable or dimension, with the requested kind first. A Date candidate's `display_name` carries its grain, such as `2027-01, YEAR grain` beside `2027-01, MONTH grain`, because columns of different grains print the same label. In a table read rolled up to a coarser `grain`, it also names the saved axis the period comes from, such as `2027-01, YEAR grain, from the saved QUARTER axis` beside `2027-01, YEAR grain, from the saved MONTH axis`. When a table saves a year axis beside a month axis and a `YEAR` read shows the same year twice, a period selector such as `2027` or `FY2027` selects the column the table saves at that grain, the one the Page shows; two candidates that differ in Variable, item, or Dimension, or two rolled-up copies with no axis saved at the read's grain, stay ambiguous, and a `#suffix` that matches two columns keeps its refusal.
- A table's saved rows and columns print the same reference in a layout `list`, in a read whose calculation did not finish, and in a calculated `read`, so a reference copied from any table result selects its row or column in the next read.
- A result names each object with `ref`, the selector to pass back, and `url`, the address that opens it in cfo.ai.
- A write also returns a resource link for each thing it created or changed, described "Open in cfo.ai" and meant for the user. End your reply with the link a tool returned, exactly as printed; a link you assemble yourself will not open.

## Results

Every result is JSON text. A result that is a JSON object also arrives as `structuredContent`. A `validate_code_blocks` call with `visual_review` also returns the render as image content. An MCP call has no chat to save that picture in, so its `visualReview` carries `fileError` and no `file`; see [What `validate_code_blocks` reports](/agents/canvas-blocks#what-validate_code_blocks-reports).

### Write receipts

A write receipt opens with a shared head. Tool-specific sections sit beside it.

| Field | Values |
| --- | --- |
| `status` | `applied`: everything asked for is saved. `partially_applied`: some items are saved; `items` says which. `rejected`: nothing is saved because the request or every item was refused. `no_op`: nothing is saved because saved state already matched. `blocked`: nothing is saved because a dependency or a rule refused the write. |
| `state_changed` | `yes`, `no`, or `unknown` |
| `counts` | `requested`, and when nonzero `created`, `reused`, `applied`, `skipped`, `rejected`, `unchanged`, and `unknown` |
| `items[]` | One entry per requested item, in request order: `ref`, `display_name`, `status` (`created`, `reused`, `applied`, `skipped`, `rejected`, `unchanged`, or `unknown`), and `reason` when it did not land |
| `readback` | `status`: `complete`, `partial`, or `unavailable`, with `reason`. A write whose readback is unavailable still saved. A write that read nothing back carries no `readback` at all: a table, Variable, or Dimension delete, a rollup or calendar edit, and other edits of saved state. Those receipts report `coverage.values: "not_evaluated"`, except a rollup or calendar edit that saved nothing because the saved state already matched, which keeps `not_needed`. |
| `warnings[]` | `code`, `message`, and `ref`: things the saved write will not do as asked |
| `error` | Present exactly when `status` is `rejected` or `blocked` |

An item whose status is `unknown` may or may not have landed. Read current state before you repeat it.

### Refusals and failures

- A refusal carries `error` with `code`, `message`, `transient`, and, when known, `candidates` and `hint`, beside `state_changed`. Codes include `ambiguous`, `not_found`, `invalid`, `blocked`, `conflict`, `stale_target`, `selection_too_wide`, `file_too_large`, `result_unavailable`, and `browser_validation_unavailable`.
- `result_unavailable` reads **The call's outcome is unavailable. Read current state before repeating a write; repeating it could apply it again.**
- A `not_found` for a name or `Name#hex` reference that only a removed connection or a deleted table carried says so, with the day in UTC: `"Stripe#aa9" named a connection that was removed from this workspace on 2026-10-05.` or `"Vendor breakdown" named a table that was deleted on 2026-08-12.` The table fact appears only when you could read that table just before it was deleted. A Scenario reference whose suffix belongs to a removed Scenario says `"Disposable#a17" named a scenario that was deleted on 2026-10-19.` or `merged into its parent scenario`, only for a user who could see that Scenario just before it was removed. Any `candidates` are objects that exist now, and the `hint` says each is a different object.
- A table or mapping write that PostgreSQL rolls back for a deadlock is retried once by the server after 50 to 100 milliseconds; a second deadlock returns a `blocked` refusal that says the write saved nothing, with `transient: true`, so the same call can be sent again.
- A result with `ok: false` and an `error_kind` is an answer, not a crash. Use its message and `hint` to choose the next call.
- Refusals and fully rejected writes arrive with `isError: true`. A write that saved some items stays a success, with each item's status.
- `transient: true` means the same call can succeed later without changes. A failure that knows whether it is retryable adds `Transient: true.` or `Transient: false.` to its text and `{"error": {"message", "transient"}}` to its structured content. Apart from the one deadlock retry above, the server never retries for you.

## Pagination and truncation

A list cut short carries `truncation` and, when it can continue, `next`:

- `truncation.by` says what cut it: `response_budget` (the next item did not fit one result), `count_limit` (the page reached the `limit` you set, or the most items the read loads, such as 100 jobs of each kind in an `inspect_integrations` `jobs` list), `row_limit`, or `depth`.
- `truncation.shown` counts what came back, and `truncation.total`, when counted, what the selection matched. No `truncation` means the result is complete.
- `next` holds the values that continue the read. Pass a cursor back unchanged, with the same tool, action, target, filters, and snapshot. An `inspect_table_blocks` cursor passed back beside a Scenario spelled differently from the cursor's own, such as `Base` beside `Base#52f`, still continues when both name one Scenario at the read's saved version.

| Tool and action | Page size | Continue with |
| --- | --- | --- |
| `inspect_pages` `list` | `limit`. Without it, every page summary that fits one result; `truncation.total` counts all pages. | `next.after` as `after`, with the same `scenario` and `target` |
| `inspect_pages` `read` | No paging. A read larger than one result leaves out its largest parts whole and marks each one; see [A page read larger than one result](#a-page-read-larger-than-one-result). | — |
| `inspect_scenarios` `list` | `limit`. Without it, every visible Scenario that fits one result. | `next.after` as `after` |
| `inspect_history` `changelog` | At most 100 entries per read; `limit` takes up to 100. Without it, as many of those as fit one result. | `next.before` as `before` |
| `inspect_history` `changelog` with `search` | Each read searches up to 1,000 entries, newest first, and reports how many it read in `entries_searched`. | The `before` value the result carries |
| `inspect_table_blocks` `list` | `limit` up to 500. Without it, every table that fits one result. | `next.after` as `after` |
| `inspect_table_blocks` `read` and `compare` | `limit` up to 500 grid rows; default 500. Parents and descendants count separately. | `next.after` as `after`; it binds the table, selection, Scenario, and snapshot |
| `inspect_table_blocks` `items` | `limit` up to 500 items; default 500. | The last item's text as `after`, including an empty string |
| `inspect_table_blocks` `variable` and `dimension` with `target` | `limit` up to 100 saved formula definitions per page; default 100. A larger `limit` is refused with **a read with target returns at most 100 saved formula definitions per page; limit is 101**. | `next.after` as `after`, with the same `target` |
| `inspect_table_blocks` `variable` and `dimension` without `target` | `limit` up to 500 entries per page; default 500. | `next` as the next call's input, unchanged: it holds `contains`, `scenario`, `as_of_point`, `after`, and `limit` |
| `inspect_dimension_mappings` | `limit` rows per lookup. Without it, every row of each lookup, or as many per lookup as fit one result. Each lookup's `row_count` is its true total. | That lookup's `next` as `after`, with the same `keys` |
| `inspect_canvas_blocks` | A selection larger than one result is cut short. See [Canvas blocks for agents](/agents/canvas-blocks#read-saved-canvas-blocks). | `next` holds the arguments that read the rest |
| `inspect_integrations` `jobs` list | `limit` jobs of each kind, newest first. Without it, up to 100 of each kind, as many as fit one result. `truncation.total` counts both kinds and is stated only when the read loaded every matching job. | None. Narrow the list with `status`, `kind`, or `query`. |
| `inspect_integrations` `queries` with one `query` | As many of the query's Variables and Dimensions as fit one result. The query's `properties_truncation` gives `shown` and `total`. | `next.properties_after` as `properties_after`, with the same `query` and Scenario. Refused when the query's list changed after that page. |
| `inspect_integrations` `jobs` task pages | `task_limit`. Without it, every task that fits one result. | `next.job` as `job` and `next.task_after` as `task_after`, with the same `tasks` filter |
| `inspect_integrations` `query_results` | `limit` up to 100 rows per read; without it, 100. The result holds as many of them as fit one result, with `offset` naming the first row shown. `total_rows` counts every row on the first read only. | `next.offset` as `offset`, with the same `query`. A saved statement whose outermost `SELECT` ends with `ORDER BY` pages in that order. Without one, each page sorts the rows by every output column, nulls last, before it skips to `offset`, so pages neither repeat nor skip rows, though rows equal in every column can trade places. When Snowflake rejects that sort, the read runs once more without it, and `order` says that pages can repeat or skip rows. |

A table `read` that selects rows, columns, or periods, limits `depth`, continues from `after`, or stops early returns `partial: true` at its root. `coverage.delivery` says whether the response reached the end of that selection, and `coverage.calculation` whether its values finished calculating. A `period_range` that reaches past the table's window returns only the periods inside the window and adds one `read_note` issue that counts and lists the requested periods left out and names the window: `13 of the 20 requested periods are not in this read (2025-02 through 2026-01, 2026-09): they are outside the table's window, 2026-02 through 2026-08.` A table that saves no valid dates names the default window instead. The note appears on a table with one Date axis at month, quarter, or year grain.

A changelog entry larger than one page keeps its place in the list. Without `include_details`, it comes back with an empty `changes` list and no `blocks` list, and `changes_truncation` and `blocks_truncation` beside them count what each list held. With `include_details`, it keeps every change, and a result larger than the allowance is replaced whole by the allowance marker.

### A page read larger than one result

An `inspect_pages` `read` that fits one result returns every block in full. A larger read fits itself, and it never returns part of a block or part of a Page's text:

- It leaves out the largest parts first, by size, until the read fits. A part is one block's settings and text, or one Page's own `markdown` on a read with `include_text`.
- A block left out stays in `blocks` with its `display_name`, `ref`, `type`, `createdAt`, `updatedAt`, and `guide_targets`, plus `detail_omitted_bytes`, the bytes left out. To read a table left out this way, pass its `ref` as `target` to `inspect_table_blocks` `list`.
- A Page whose own text is left out carries `markdown_omitted_bytes` and no `markdown` or `document_revision`.
- Each Page with a part left out carries `truncation` with `by: "response_budget"`, `shown` for its blocks returned in full, and `total` for its blocks. There is no `next`.
- When the block lists alone are larger than one result, every Page in the read returns `blocks: []` with `block_counts`, its block count by type such as `{"TABLE": 2990, "TEXT": 10}`, `blocks_omitted_bytes`, and a `truncation` whose `shown` is 0. Reading that Page alone returns the same counts; no call lists its blocks.
- One read names at most 50 Pages.


## Read the Model at an earlier point

`inspect_pages`, `inspect_table_blocks` (every action except `bounds`), `inspect_canvas_blocks`, `inspect_dimension_mappings`, and `inspect_scenarios` take `as_of_point`. Without it they read the current state. It holds exactly one point type:

| Point type | Meaning |
| --- | --- |
| `change_log_id` | One of the workspace's changes, as a write receipt or `inspect_history` reports it. The snapshot is the Model right after that change. Change ids are numbered across all workspaces, so an id between two of this workspace's changes can belong to another workspace. It accepts the ID as an integer or as a string of digits, as do `before_change_log_id` on `inspect_table_blocks` `compare`, `at_change_log_id` on `edit_scenarios` `snapshot`, and `change_log_ids` and `to_change_log_id` on `edit_history`. Results print the ID in either form. |
| `timestamp` | An exact instant in RFC 3339 with a time zone, supplied by the user, the context, or a tool result. |
| `calendar_boundary` | `unit` (`day`, `week`, `month`, `quarter`, or `year`), `offset` (0 this period, -1 the previous, 1 the next), and `boundary` (`start` or `end`), in the user's time zone from `_context`, or UTC without one. Weeks start on Monday. Use it for "yesterday" or "last month". |
| `relative_duration` | `amount`, `unit` (`minute`, `hour`, `day`, or `week`), and `direction` (`ago` or `from_now`), from server time. A day is 24 hours and a week seven days. |

A `change_log_id` the workspace does not have is refused with `not_found`: `as_of_point.change_log_id: no change with id <n> exists in this workspace. Change ids are numbered across all workspaces, so an id between two of this workspace's changes can belong to another workspace.`, with the hint `This workspace's changes are the ids its write receipts and inspect_history report.` and, when one exists, `Its latest change before <n> is <m>.`

`inspect_history` `changes_between_points` takes a `start` point and an optional `end` point, which may also be `latest: true`. A `change_log_id` there resolves to the workspace's latest change at or before it. The range is the response's own `startChangeLogId` and `endChangeLogId`, so the parent's `changes_between_points` over the same points lists what a child Scenario's `inheritedChanges` counts.

## Safety annotations

Each tool carries standard MCP annotations, which clients use to decide which calls need the user's approval:

- `readOnlyHint: true` on every `inspect_*` tool, `inspect_chats` included, `validate_code_blocks`, and `list_orgs`.
- `openWorldHint: true` on tools that can reach outside cfo.ai, notify a person, send an invitation, or change an outside integration: `edit_pages`, `edit_triggers`, `edit_profile`, `edit_integrations`, `edit_team`, `edit_org`, `call_connected_api`, `notify_user`, and `validate_code_blocks`.
- `destructiveHint: false` only on `notify_user`. Every other write keeps the MCP default, which treats it as possibly destructive.

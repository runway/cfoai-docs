The cfo.ai MCP server publishes 41 tools: Ari's public product tools plus three MCP-only tools, `list_orgs`, `inspect_chats`, and `edit_chats`. Two of the 41, `inspect_comments` and `edit_comments`, are listed but refuse every call; see [What the server does not publish](#what-the-server-does-not-publish). This page describes the server, each tool, and the conventions every call follows. To connect a client, follow the [Agent instructions](/agent-instructions).

## Server

| Fact | Value |
| --- | --- |
| Address | `https://api.cfo.ai/mcp`. `https://api.cfo.ai/mcp/v2` serves the same tools; use `/mcp` for new connections. |
| Transport | Streamable HTTP, stateless. Each request authenticates and selects its workspace on its own, and the server neither issues nor requires an `Mcp-Session-Id`. |
| Sign-in | OAuth. A person approves the client in a browser, and the client sends the token it receives in the `Authorization` header. The protected resource metadata is at `https://api.cfo.ai/.well-known/oauth-protected-resource/mcp`, and clients register themselves through dynamic client registration or a client ID metadata document. |
| API keys | None. cfo.ai issues no API keys or access tokens to copy; every client signs in as a person and acts as that person. |
| Instructions | The server sends cfo.ai's modeling instructions when a client connects. |
| Tool list | Fixed for each server process. The tool list carries a five-minute private cache hint, and the server advertises `listChanged: false`. When a client's definitions are stale, refresh its tool list or start a new conversation. |
| Request size | A request body holds at most 1 MiB. A larger one is refused with **The MCP request is too large.** |
| Batches | JSON-RPC batch requests are refused with **JSON-RPC batches are not supported.** |
| Rate limit | 60 calls a minute for each tool, per user and workspace; `list_orgs` has no limit. A call past the limit fails with **rate limit exceeded for** followed by the tool name. |

## Published tools

A tool marked read-only never changes saved state. The **Actions or fields** column lists a multi-action tool's blocks; for a single-purpose tool it lists the fields it takes directly.

### Tables, formulas, and mappings

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_table_blocks` | Read-only. Lists saved tables, reads cells with their formulas and sources, compares a table with an earlier saved state, and reads Variables, Dimensions, and their items. A `variable` or `dimension` read without `target` lists every one you can read as a short entry, and `contains` narrows the listing by name. A `variable` entry states the Variable's own `format` and `currency`, and `currency` narrows a `variable` listing to the currency-format Variables shown in one currency; see [Find a Variable or Dimension by name](/agents/read-formulas#find-a-variable-or-dimension-by-name). A `list` reads one Scenario; without `target` or `page` it also carries `other_scenarios`, each other Scenario the user can read that holds saved tables the listed Scenario does not, with `tables_not_in_this_scenario` counting them, or `[]` when none does. `read.rows`, `read.columns`, `compare.rows`, and `compare.columns` accept one selector as a plain string as well as a list. A bare day selects a date Dimension's item saved on that day, when no exact name matches: `2018-01-31` selects the row printed `2018-01-31 00:00:00+00`, as does `Employee ID[2018-01-31]`. A timestamp still selects only its own item, a month selects no day, and a day that two rows hold, such as a direct row and a row nested under a region, is refused as `ambiguous` with both rows listed; `edit_table_blocks` `cell_updates` selectors follow the same rule. A selector may lead with a parent row's or column's reference and name an item beneath it, such as `Software#57e[CA Sales Tax]`: the reference selects the parent, and the item is matched only among the rows or columns under it. On a read, a date column selector whose reference suffix matches nothing, such as `2026-08#dead`, selects the column its date names and adds a `read_note`, **columns selector "2026-08#dead" had a stale reference; resolved to 2026-08 by date label**; a write still refuses that selector. A day or month that matches no column of a coarser table selects the period that contains it, such as Q4 for December, and a note names the requested date, the period returned, and its grain; an exact match wins, and a date two periods contain stays ambiguous. A `read` follows the table's saved choice to hide empty items, and a selector for an item the table hides is refused with the item, its Dimension, and the rule or saved filter that hides it, so a hidden row is not reported as missing. A row or column selector that names a period outside the saved window is refused with the saved window and a pointer to `list`, which reports other tables' windows; the refusal proposes no change to the table. Two selections that reach past the window are not refused and return the periods inside the window with a `read_note`, as described under [Results](#results): a `period_range`, and, on a table whose columns start with one Date axis at month grain or coarser, period labels such as `2026-07` listed beside a selector that does select a column. In an `edit_table_blocks` `cell_updates` entry the same range is refused whole; see [Write values into dated columns](/agents/write-formulas#write-values-into-dated-columns). A `list` entry summarizes the saved table under `summary`: `rows` and `columns` count its top-level entries, `first_rows` names up to five rows, and `window` is its saved window; a table that places a Variable or Dimension you cannot read keeps its summary and carries `layout_problem` **This saved table includes a property you cannot read.** `read.rows` and `read.columns` also take predicates over each item's own value, such as `` Invoice where `Days overdue` > 0 `` beside item attributes such as `Employee where Employee.Department = "Engineering"`, for a Variable stored once per item; a Variable whose value varies by month, including through a default formula that reads monthly inputs, or by another Dimension is refused, and a period refusal returns the complete filter with an example month from the table's window, the read's Last close month when it falls inside it. A predicate may also start from a Variable the axis shows, such as `` `Team Personnel Costs` where `Business Unit` = "New products" ``, which selects only that Variable's rows or columns; see [Select rows and columns](/agents/read-formulas#select-rows-and-columns). A `next.after` cursor passed back beside the Scenario it was issued for continues even when the two spellings differ, such as `Base` beside a cursor that names `Base#52f`, when both name one Scenario at the read's saved version; a different Scenario is still refused. A `variable` read that names a Dimension, or a `dimension` read that names a Variable, is refused as `invalid` with **[name] is a [kind].** and the read that shows it; nearby-name suggestions cover both kinds and hand-added items, naming their Dimensions, and a missing breakdown row names up to three tables that break the Variable down by that Dimension. | `list`, `read`, `compare`, `variable`, `dimension`, `items`, `bounds` |
| `edit_table_blocks` | Creates, updates, reshapes, copies, or deletes saved tables in one atomic change each. A `create` puts the table on an existing Page named by `page`, or on the Page in view; it does not create the Page it names, and a missing one is refused with a pointer to `edit_pages`. The one Page a create can make is the Model's shared page, when a mapping it declares creates its target Dimension; see [Declare a mapping in the create that reads it](/agents/write-formulas#declare-a-mapping-in-the-create-that-reads-it). A `page` name that two or more Pages share is refused with the count and each Page's own reference, which `page` accepts: `page name "Forecast" matches 2 pages; references that each select one of them: "Forecast#7e9", "Forecast#019"`. A saved table has no row count of its own, and one write has no limit on the cells, rows, or columns it changes; the 1 MiB request size bounds what one call can send. A write that lays out many changes checks the server's memory as it goes, and is refused before it saves when memory is low, with a message that starts **table edit stopped after laying out [n] changes: server memory was low.** and ends **Nothing was saved**. Writes to one Page's tables in a Scenario run one at a time, as do all creates and cell writes, and a write not committed by its time limit saves nothing. Table settings cover what a person sets by hand: a `style` with `scale` (thousands, millions, or billions), `negativeNumbers` (`MINUS` shows -1,250 and `PARENTHESES` shows (1,250), in every number format at the cell's decimals and scale; where no scope of the table sets it, the workspace display from `edit_org` `negative_numbers` applies, and without one negatives show `MINUS`), and text `color`, a Dimension's `color`, each column's `width` and `pinned` in `column_updates`, and `formula_width` and `row_header_width`, all widths at least 100 px. `signColors` in a `format` colors each shown number by its sign and follows the value: `NEGATIVE_RED`, `NEGATIVE_RED_POSITIVE_GREEN`, or `NEGATIVE_GREEN_POSITIVE_RED`. A number that shows as zero is not colored. Within its scope the rule replaces variance colors, and its color replaces a text `color`. `NONE` turns off a broader scope's rule; `{"inherit": true}` clears it on an update, and `null` clears it in a layout node's `format`. Set it once on the table's `format`, or on a row, column, or cell; it is not copied onto cells, and a read states the resolved rule on each row as `style.signColors`. `item_filter`, on an `update`, limits every cell of the table to chosen items of Dimensions that are not on its rows, columns, or a breakdown: an object from a Dimension's name or reference to a list of item names. `{}` clears the filter, and `[]` for a Dimension removes that Dimension. With one item for each Dimension, cells show and save that item; with several, each cell is their read-only total, and a cell write is refused with **this table's item filter keeps several items of a dimension, so each cell is their total, which takes no formula**. The table needs a column, and a date Dimension or a Dimension the table shows is refused, such as **item_filter key "Region" is a dimension this table's rows or columns show**. A `reshape` does not take the field. Reads return it under `presentation.item_filter`, `{}` when no filter applies. `row_totals_at_bottom`, on an `update` or under `settings` in a `reshape` layout, saves where each row group's total shows: `true` shows a label-only heading above each expanded group's details and a Total row below, nested groups included, a collapsed group shows one total row, and Excel exports follow it; `false` keeps totals above details. Reads return it under `presentation.row_totals_at_bottom`. `open_row_depth`, on an `update` or under `settings` in a `reshape` layout, saves **Rows open to**: how many row levels below the top rows start open for every viewer. `0` shows only the top rows, and `1` also shows their child rows. Rows a viewer opens or closes stay that way in their browser, and without the setting each row keeps its own default. `{"inherit": true}` deletes the Scenario's own depth, so the table follows the Scenario it inherits from. A `create` does not take the field. Reads return it under `presentation.open_row_depth`, absent when the table saves no depth. `open_column_depth`, on an `update` or under `settings` in a `reshape` layout, saves **Columns open to**: how many levels of column groups start open for every viewer. `0` starts every column group collapsed, so each group shows the columns it shows while collapsed, such as its total, and `1` opens the top level of groups. Column groups a viewer opens or closes stay that way in their browser until the saved depth changes, and without the setting each group keeps its own default. `{"inherit": true}` deletes the Scenario's own depth, so the table follows the Scenario it inherits from. A `create` does not take the field. Reads return it under `presentation.open_column_depth`, absent when the table saves no depth. `fixed_scenario`, on an `update` or a `reshape`, or under `settings` in a `reshape` layout, saves the Scenario the table always shows on its Page, whatever Scenario the Page is open in, by name or `inspect_scenarios` reference. The Page then shows that Scenario's copy of the table, its layout, values, and formulas, and an edit reaches that copy with `scenario` set to it. `""` shows the Page's Scenario again, and `{"inherit": true}` restores the parent Scenario's choice. A save that would make the table show a Scenario you cannot read, such as an inherited choice, is refused with **This save would make the table show a scenario this caller cannot read. A setting this call did not send can name it, such as a fixed scenario inherited from the parent scenario.** A value that names no Scenario you can read is refused with **fixed_scenario "[value]" is not a scenario this caller can read**. A call that would leave the table fixed to a Scenario other than the call's own may set `fixed_scenario` and nothing else; with any other edit it is refused, because it would edit a copy the Page does not show: **after this call the table is fixed to [Scenario]: its page shows that scenario's copy of the table, and edits made on the page save there. This call edits the table's copy in [the call's Scenario], which its page does not show. A call that sets fixed_scenario, with only target, scenario, readback, based_on, include_edit_rules beside it, changes which copy the page shows.** When the refused call set `fixed_scenario` itself, the message ends by naming its other edits, such as **This call also sets page.** A `create` and a `copy` do not take the field. Reads return the choice under `layout.settings.fixed_scenario` and under `presentation.fixed_scenario`, absent when the table shows its Page's Scenario; a `read` shows the copy in the Scenario it reads, so a read in the fixed Scenario shows what the Page shows. A write's `readback` reads the copy the Page shows: the fixed Scenario's copy when you can read that Scenario and the table in it and it holds a copy, and the write's Scenario otherwise; `readback.also` tables are read in the write's Scenario. A read, readback, or `readback.also` entry of a table fixed to a Scenario other than the one read carries one `read_note` that names both copies; see [Validate and verify](/agents/validate-and-verify). `presentation.fixed_scenario_problem` reads **The scenario this table is fixed to is unavailable.** when you cannot read that Scenario or it was deleted, and the Page then shows no values for the table. Writes every model formula, and sets time rollups and the Scenario's calendar. A `create` with a `tables` list saves them in one change, and a formula, a `variables` settings entry, or a `dimensions` settings entry in any table names what any table of the list declares, whatever the order. `remove_items` deletes a member together with its rows on every table and the formulas whose condition selects only it, and the receipt's `members` counts them as `removed_rows` and `removed_rules`. An `update` with `rules` replaces saved formulas named by their `Rule#` references, any number of them in one change, and keeps each one's condition and range, or deletes them with `clear_formula: true`; see [Replace a saved formula and keep its scope](/agents/write-formulas#replace-a-saved-formula-and-keep-its-scope). `row_updates` takes `label`. On a row that shows a Variable, or a Dimension shown as a mapped value, it is text: the row's own name on this table, one line of at most 200 characters, with `{"inherit": true}` to show the Variable's name again; references, selectors, and writes keep the Variable's name, and a table read prints `label` beside the row's Variable. On a row that lists a Dimension's items, it is a Dimension mapped from the rows' Dimension and shown as a field column, such as Name beside Employee ID rows, so each row shows its Name while its Employee ID stays its identity; `{"inherit": true}` shows the members again. A Dimension not mapped from the rows' Dimension, or one without a field column on the table, is refused with the candidates, and reads name the saved label; a `label` naming a mapped field whose column the table does not show adds that column in the same write, and a table whose rows hold Variables refuses it, because Variables take one axis. `row_updates[].breakdown` on an `update` replaces one saved row's own breakdown and can create the Dimensions it names; see [Variables and Dimensions as rows](/agents/table-view-grammar#variables-and-dimensions-as-rows). `dimension_display` on an `update` saves **Display as** for each named Dimension on the table, `PILL` or `PLAIN_TEXT`, for every viewer; a Dimension not on the table is refused, and reads return the saved choices under `presentation.dimension_display`. `summary_columns_hidden` on an `update` saves **Hide totals** for every viewer: a map from a saved column that has a level nested under it, such as Department when Month is nested under Department, by name or inspected reference, to `true` (each of its groups hides its summary column while expanded) or `false` (shows it). A collapsed group always shows its summary column, and the summary function is unchanged, so `summary: NONE` hides nothing. A key that names a saved row, or a column with no level nested under it, is refused, as is one column given both `true` and `false`; a `reshape` does not take the field. Reads return the hidden columns by reference under `presentation.summary_columns_hidden`, where `{}` means none. A `delete` of Variables, Dimensions, or both needs no `target`: each one uses its own table, or the only readable table that shows it, one that no readable table shows is deleted without a table, several matches need `target`, and the receipt names the tables; the whole deletion saves together or not at all. A `delete` of a table, Variables, or Dimensions needs no `force`: one call deletes even when formulas or other blocks still read what it removes, the field is still accepted and changes nothing, and the receipt reports what the delete left reading a deleted object; see [Delete a Variable or Dimension](/agents/write-formulas#delete-a-variable-or-dimension). An `add_dimension_items` entry placed `under` a parent with business items stays under that parent, with no model-wide membership; an item added with no such parent is model-wide, an existing model-wide item keeps that scope, and the receipt reports `scope` and `shown_at`, the parent paths the table shows it under. When the breakdown the item joins saves a fixed list of items that leaves it out, the same write adds the item to that list, on this table only; see [Add items and write their values in one call](/agents/write-formulas#add-items-and-write-their-values-in-one-call). A `members` list or condition on a row or column replaces the whole saved filter, so a condition replaces a fixed list and a list replaces a condition, `[]` clears it, and omission or `null` keeps it. An item name in `members` matches exactly first; when no exact item exists, surrounding spaces are trimmed to find one. A numeric item matches by value, so `96`, `96.0`, and `9.6e1` select the same employee ID in reads, filters, and cell writes, while a text item still needs its exact text; a `create` finds imported and formula-computed numeric items as well as manual ones. A cell value must fit the Variable's type: a number for a number Variable, a string for text, date, and UUID, a boolean or exactly 0 or 1 for a Boolean, and `null` for any; one value of the wrong type refuses the whole write, naming the cells by row and column label and noting that `variables` with `data_type` can change the type in the same write. A read reports mismatches already saved under `literal_type_mismatch`, with a count and up to five samples; a person's edit in the app still saves as typed. A formula save, or a row insert, also warns when a formula on a row reaches the lines under it without reading their Dimension, so each line would show the row's whole amount, such as **In Main, Revenue's rule also reaches the P&L Account lines under each TEAM; it does not read P&L Account, so each line shows its TEAM's whole amount.** Copying a `list` result's pins and column widths into an `update` is accepted when they match the saved values and refused when they differ, with `column_updates` as the one writer for them; an explicit `show_empty_members` wins over a copied value. A table with `columns: []` and Variable rows, with or without business breakdowns, needs `window.granularity: NO_GRANULARITY` and shows one **Value** column, and blank `{"space": true}` rows may separate its Variables; `list` returns that layout in a form `create` and `update` accept. In a `create` with a `tables` list, an invalid layout gets one explanation at its own position, such as `/create/tables/1`. A create, reshape, or structural insert that leaves a Variable in two or more rows or columns of the table, where it had fewer, reports it under `duplicate_placements` with `before`, `after`, and each placement's ref, rows and columns inherited from the parent Scenario included; the repeats save as requested, and a rename or formatting write adds no notice. A new numeric currency row takes its currency code from its formula inputs when every Variable input shares one code, else from the table's other money rows when they share one, else from a code at least 90% of the workspace's coded numeric Variables use; a workspace with no saved code keeps the USD display, and any other unresolved case refuses the whole write, listing the workspace's codes and the Variables and inputs without one, and accepts `variables[].currency` with the same new names. Replacing the whole item list of a Dimension that gets its items from imported data is refused with **dimension "[name]" gets items from imported data; replace_items is unavailable. add_items and remove_items support manually added items**. | `create`, `update`, `reshape`, `copy`, `delete`, `set_time_rollup`, `update_calendar` |
| `inspect_dimension_mappings` | Read-only. Lists the mappings a reporting Dimension owns, or reads one lookup chosen by its exact source keys. `pairs` and a row's `item` hold fixed items only; a row whose mapped value a formula calculates carries `formula` in place of `item`, written with Dimension names, such as `$[Practice = "Group"].Practice`, so a count of the items a Dimension maps to counts real items and a pair copied back into `edit_dimension_mappings` `map` never saves formula text as an item. A lookup whose rows all map to formulas reports `"pairs": {}`. `catch_all` is a fixed item as its item, or a calculated fallback as a formula in Dimension names. A row whose mapped value or condition reads a Variable or Dimension the user cannot read is counted in `unreadable_rows` and not shown, so no name the user cannot read appears; the `edit_dimension_mappings` receipts (`catch_all` and the removed rows) apply the same check. | `target`, `keys`, `limit`, `after`, `scenario`, `as_of_point` |
| `edit_dimension_mappings` | Maps items of source Dimensions to a reporting Dimension's items, sets or clears the catch-all, removes rules or lookups, and combines or splits compatible source Dimensions. A removal that leaves no lookup on the target also removes its catch-all, since a fallback is the item for records no lookup row matches; the receipt lists it under `removed`, reads `catch_all` back as null, and warns once. A removal that leaves another lookup keeps it, and `catch_all` can still set a fallback before the first `map`. `map` takes `replaces_keys`, the source fields of one existing lookup to replace in the same save, so title and department can take over from employee ID without a saved state in which neither lookup exists; the save replaces the lookup's rules together or saves nothing, other lookups and the fallback stay, and `replaces_keys` that names no lookup on the target is refused. Every write that adds, replaces, or removes a mapping input is checked against the inputs it leaves, and a refused write saves nothing. On the rows of one imported source, a lookup stops competing when another lookup that applies there is keyed by all of its keys and more; it becomes that lookup's fallback. A date key counts with its grain, so Invoice Date by month and by day are different keys. When two inputs of the target still compete there, the calculation would refuse the target, so the write is refused: **"[name]" would have inputs keyed by [keys] and [keys] that both apply to rows of the same imported source, so the calculation refuses it.** When the user can read every key, the refusal adds **The calculation accepts both lookups together when a lookup keyed by [keys] also applies to that source.**, and a `map` adds **In edit_dimension_mappings map, replaces_keys names the existing lookup's keys, here [keys], and removes that lookup in one change.** An input with a key the user cannot read is named **at least one dimension this user cannot read**, and the refusal then leaves out each sentence that would name those keys. So two lookups keyed by Team and by Class on one imported source save when a lookup keyed by Team and Class also applies there, and removing that wider lookup is refused. A write is also refused when a Dimension that reads the changed one calculated before the write and would not after it: **Changing "[name]" affects "[name]", which takes values through it and calculated before this change. After this change, that dependent dimension would have inputs keyed by [keys] and [keys] that both apply to rows of the same imported source, so the calculation refuses it.** Two `map` calls sent at the same moment can each create what they need: a `map` that creates its target Dimension, and waited while another write made the Model's shared page or that same Dimension, is run again by the server and saves. A `map` that finds its missing target already created by another call needs write access to that Dimension, as a `map` into any existing Dimension does. A write that waited never replaces a rule another call saved meanwhile with a different item; it is refused with **another call saved the rule [rule] on [Dimension] as change [n] while this call waited for its turn; this call would replace it, so nothing was saved**, while new rows and a row that maps to the same item still save. A database failure answers with what the call saved, never with the database's own message: **the database failed before this call saved anything, so nothing was saved**, or **this mapping change was saved as change [n]; reading it back for this answer then failed in the database, so this answer carries no receipt**. A `combine_dimension` rewrites the formulas, table layouts, and saved items that name the removed Dimensions, and changes no Canvas block. A saved item is a manually added item, or a saved item path that pairs items of several Dimensions. Each saved item moves to the kept Dimension; when the kept Dimension already holds the same item, the two become one, and a table that showed either shows it once. A moved item path leaves a table where its record already has another parent. The combine is checked only against what the call's Scenario shows, so nothing a Scenario built on it saves refuses it. In the call's Scenario it is still refused while a saved item names more than one of the combined Dimensions, or names one through a reference pinned to a Scenario: **a saved item names more than one of the dimensions being combined, which as one dimension it would name twice, or names one through a reference pinned to a scenario, and this change cannot rewrite it (…)**, or, for several, **saved items name more than one of the dimensions being combined, which as one dimension each would name twice, or name one through a reference pinned to a scenario, and this change cannot rewrite them (…; …)**. The refusal names every such item the user can read: a manually added item as **the manually added item "Acme" of "Contacts#44c"**, and a saved item path with its items and the tables that show it; one the call's Scenario inherits adds **in scenario "[name]"**. When it can name nothing, it reads **a saved item names a dimension being combined in a way this change cannot rewrite**. A chart, a table's display setting, or a table's comparison or drill-in setting that names a removed Dimension also refuses the combine there, with **names the dimension, and this change rewrites only formulas, table layouts, and saved items**. Each Scenario built on the call's Scenario rewrites the formulas, table layouts, saved items, and time choices it saves itself, in the same save, where the user may edit them. A row there that the combine cannot rewrite, or that the user may not edit, stays as it was. The receipt's `kept_references` lists each such row, and each item path that left a table, with `scenario` and `reference`, a sentence that names the row and says why it stayed. It lists only rows the user can read, and it is an empty list when nothing stayed. A Snapshot is not rewritten. The receipt also lists the Canvas blocks to look at under `canvas_repairs`, each with `target`, `scenario`, and exactly one mark. `repair_needed: true` marks a block whose saved state or configuration, which includes its datasets, form, and code, holds a removed Dimension's ID, a `Name#hex` reference to it, or its display name as a whole word; the name is searched only when the kept Dimension has a different name. `not_checked: true` marks a block that holds none of these and whose code can send Ari a request (`startAriChat`, `askAri`, or `prepareScenario`); that request's text is built when the code runs and was not read. A chart that matches nothing and sends no request is left out, because chart code reads a Dimension only through a dataset, which saves the Dimension's ID. Blocks you cannot read are left out, and an empty list means nothing matched. The receipt's `warning` states these rules; read a listed block with `inspect_canvas_blocks` and change it with `edit_canvas_blocks`. | `map`, `unmap`, `catch_all`, `clear_catch_all`, `drop_mapping`, `combine_dimension`, `split_dimension` |

### Pages and Canvas blocks

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_pages` | Read-only. Reads the page tree, each Page's blocks in order, saved table settings, and reusable references. Each Table block in a `read` carries its saved `layout` (`rows`, `columns`, and `settings` in the shape `edit_table_blocks` `create` and `reshape` take, with each axis's filters, Date groupings, roles, and children, and the names of the formula ranges `settings.formula_breaks_hidden` hides), its `signature`, and its `presentation`. ### Ari chats

Two MCP-only tools let a client hand a question to Ari instead of calling tools itself. A chat a client starts is an ordinary Ari chat, with the same agent, billing, memory, and Skills, and the person can open it in the cfo.ai web app, where its entry in the chat list carries an **MCP chat** mark.

| Tool | What it does | Actions or fields |
| --- | --- | --- |
| `inspect_chats` | Read-only, MCP only. `list` returns the user's chats in this workspace, most recently updated first, each with its `ref`, `state` (`running`, `idle`, `needs_response`, or `error`), a busy flag, and its `resource_uri`. `read` returns one bounded page of a chat: the user's messages, Ari's last message in each turn, the questions and plans Ari waits on, cards that only the web app can answer as `waiting_in_app` items, and delivered files. | `list` (`status`, `title_query`, `limit`, `cursor`), `read` (`target`, `after`, `before`, `wait_seconds`, `steps`) |
| `edit_chats` | MCP only. `create` starts a chat with a message in the Scenario `_context.scenario` names. `send` adds a message to a chat, and also answers Ari's questions and approves a plan. `stop` ends the running turn; `drop_waiting` also deletes messages not yet sent. `update` renames, archives, or restores a chat. Turns bill the workspace like chats in the app. | `create` (`message`), `send` (`target`, `message`, `delivery`, `request_id`), `stop` (`target`, `drop_waiting`), `update` (`target`, `title`, `archived`) |

- **Reads are bounded.** `steps` chooses how Ari's tool work shows. `none`, the default, folds each turn's tool steps and the notes between them into one `steps` item with their count. `summary` shows one item per step. `full` adds each step's input and result, cut at 4,000 characters. A page holds at most 40 items and about 48 KB. A read without a cursor keeps the newest items and returns `older` to page back; a read with `after` keeps the oldest and returns `next`.
- **Waiting for Ari.** `create` and `send` return at once with `next`: the exact `inspect_chats` `read` call that waits, up to 50 seconds through `wait_seconds`, while the chat is busy. A read of a chat that is still busy returns another `next`. A client that sends a progress token gets a progress notification each second it waits, naming what Ari is doing. To hear when a turn starts or ends instead of waiting, subscribe to the chat's `resource_uri`, `cfoai://orgs/{org_id}/chats/{chat_id}`, on the MCP 2026-07-28 `subscriptions/listen` stream, and read the chat's newest page with `resources/read`. The older `resources/subscribe` is refused.
- **While Ari works.** `delivery` on `send` is `steer` by default, which ends the running turn after its current step and starts the next turn with the message; the work in progress carries into that turn with its saved progress, and the message is read as an addition to it unless it cancels or replaces it. `queue` waits for the turn to end. `request_id`, a UUID the client makes, makes a repeated `send` a `no_op` that returns the same `message_id`.
- **Limits.** A `create`, or a `send` to a chat that is not busy, is refused when 5 of the user's chats in the workspace are already busy. Only the chat's owner can read or write it. Approval buttons, email **Send** buttons, confirmations, and sign-ins work only in the web app: give the person the `chat_url` the result carries. An MCP read does not mark the chat read in the web app.

### The Scenario a call uses

Most model tools take `scenario`, by name or returned reference. `"Main"` names the base Scenario whatever name the workspace stores for it, and the id that Page and block links print after `?layer=` is accepted too; a stored name wins, so a Scenario literally named Main keeps its own meaning. A plain name in `scenario` that is no visible Scenario's exact name still selects the one Scenario whose name is the same once case is ignored and each run of spaces and punctuation reads as one separator, so `Close - Test` selects `Close -Test`. The result of that call, a read included, then carries a `scenario_warning` under `warnings` that names the Scenario selected: **No available scenario is named exactly "Close - Test". The name selected Close -Test#e89 by a comparison that ignores case and reads each run of spaces and punctuation as one separator.** An exact name, `Main` written exactly, and a `Name#hex` reference add no warning. When a call omits `scenario`, the tool uses the Scenario in view: the one `_context.scenario` names, or Main when `_context` names none. Pass `scenario` on every write so the target does not depend on context. [Create and update formulas](/agents/write-formulas#write-in-a-scenario) quotes the sentence a table write adds when `scenario` was omitted.

The server resolves `_context.scenario` again on every call and keeps no Scenario between calls. After a Scenario is deleted, a call that still names it in `_context.scenario` is refused before any tool runs, so no later call reads or writes its parent in its place: name a Scenario that exists, or leave `_context.scenario` out to use Main. When an `edit_scenarios` `delete` removes the Scenario its own `_context.scenario` names, the receipt adds a `scenario_warning` that names the deleted Scenario and, when the user can read it, its parent, and ends **Writes require a named scenario until it is restored.**

## Shape each call as one action block

A tool with several actions takes exactly one block named for the action, with that action's fields inside it. There is no flat `action` field.

```json
{ "read": { "target": "Operating Plan", "rows": ["Revenue"] }, "scenario": "Main" }
```

- Each tool's input schema says, in its description, which blocks exist and which fields sit beside them: "Fill exactly one action block: create, update. Fields beside the block apply to it: scenario, validate, visual_review." A field only some blocks take names them in parentheses, as in "readback (create, reshape, update)".
- An empty block selects an action that needs no fields, such as `{"list": {}}`. A block set to `null` counts as not filled.
- A `null` written for an optional field means the field was not given, on every tool that takes action blocks and at any depth inside objects. So `{"read": {"target": "Operating Plan", "grain": null}}` reads as if `grain` were left out. Four kinds of `null` keep their meaning or are refused: a field whose schema accepts `null`, where `null` clears a saved value; a required field; a field the schema does not declare; and a field whose presence selects a different form of the call, such as `variables` on a table `delete`, where `null` is refused and nothing is deleted. A `null` item inside a list is never removed.
- Fields beside the block apply to it: `scenario` on most model tools, `as_of_point` on `inspect_scenarios`, `validate` and `visual_review` on `edit_canvas_blocks`, `readback` on the `create`, `update`, and `reshape` blocks of `edit_table_blocks`, `target` on `edit_dimension_mappings`, and `idempotency_key` on `edit_memory`. `scenario` and `readback` are also accepted inside a block that takes them; when both places carry the field, the two values must match. Every other such field is refused inside a block.
- A field of the filled block that is written beside it moves into the block: `{"read": {"target": "Operating Plan"}, "comparison": "none"}` reads as `comparison` inside `read`. The same value in both places counts once, and a different value inside the block is refused as a duplicate. A `null` the field accepts is a value of its own, so `after_page: null` inside a block and a Page beside it conflict. On `notify_user`, a field beside the one delivery block the call fills moves into that block, such as `channel` beside `slack`.
- Single-purpose tools take their fields directly at the root, as the table above shows. `notify_user` takes an `email` block, a `slack` block, an `in_app` block, or several of them.
- The schema root is a plain object, so every client can see the blocks. The rule that exactly one block is filled is enforced when the call runs.
- Unknown fields and retired request shapes are refused before anything runs. Nothing is translated from an older shape.

### Refusals for a wrong shape

A refused call changes nothing. Its message names the problem without repeating any value you sent.

| Mistake | Message |
| --- | --- |
| No block filled | `no action block is filled; the call takes exactly one of [...]` |
| Two blocks filled | `the call takes exactly one action block; [...] are filled` |
| A flat `action` field | `action "read" is the read block; the fields of that action belong inside it: {"read": {"target": ...}}` |
| `action` inside a block | `the read block takes no action field; the block name selects the action` |
| A block that is not an object | `read must be an object holding that action's fields` |
| A root field that is neither a block nor a field of the filled block | `<name> is not an action block; the blocks are [...]` |
| A field the block does not take | `<field> is not a field of the <block> block` |
| A beside-field inside a block that does not take it | `<field> belongs beside the <block> block, not inside it` |
| The same field beside and inside, with different values | `<field> is <value> beside the <block> block and <value> inside it; a call carries one <field>, in either place` |
| A value of the wrong type or shape | `<path> received <what>; it accepts <what>`, such as `/sections/0 received a string of 9 characters; it accepts an object whose section is one of …`. At an action's root, the path reads `the input`. |

A shape is described by type: a string by its length, an array by its item count, an object by up to 8 of its key names, and a number, boolean, or null by its type.

The refusal arrives with `isError: true` and this structure:

```json
{
  "error": {
    "code": "invalid_input",
    "message": "the call takes exactly one action block; [\"list\" \"read\"] are filled",
    "transient": false,
    "validation": {
      "issues": [{ "path": "", "code": "invalid_value", "message": "..." }],
      "accepted_fields": ["..."],
      "required_fields": ["..."],
      "truncated": false
    }
  },
  "state_changed": "no"
}
```

`validation` lists at most 20 issues; `truncated` is true when there were more. `accepted_fields` lists the chosen block's own fields plus the fields beside it. When a tool's own check refuses one section of a `read`, each issue's `path` names that section by its index, as in `sections/1/target`, including when two sections are of the same kind, and `accepted_fields` and `required_fields` list that section's fields.

`list_orgs` takes no input and returns the workspaces the user can use through MCP:

```json
{ "orgs": [{ "org_id": "4127", "name": "Example Co", "slug": "example-co", "role": "admin" }] }
```

Pass a returned ID or slug as `org_id` on later calls. A number, or a string of digits, always names a workspace ID; anything else is read as a slug.

### A user who cannot start Ari chats

A user can belong to a workspace without the admin role: a person who opened a share link and signed in keeps the Pages shared with them, and `list_orgs` returns that workspace with `"role": "user"`. Such a user cannot start an Ari chat there, so the server runs only these reads for them:

| Tool | Open actions and fields |
| --- | --- |
| `list_orgs` | Every call |
| `inspect_pages` | `list`, `read`, `share_links`, with `scenario` on `list` and `read` |
| `inspect_scenarios` | `list`, `read`, `subtree`, with `as_of_point` |
| `inspect_table_blocks` | `list`, `read`, with `scenario` |
| `inspect_canvas_blocks` | `target`, `page`, `scenario`, `include_source`, `source_offset`, `as_of_point` |

- Every other tool, and any other action or top-level field of these tools, is refused before the tool runs, with code `blocked` and `state_changed: "no"`. The message names the tool, or the tool and the first input that is not open, such as **inspect_table_blocks items is for people who may start Ari chats in this workspace, and the current user may not.** The hint reads **Every member of this workspace may call inspect_canvas_blocks, inspect_pages (list, read, share_links), inspect_scenarios (list, read, subtree), inspect_table_blocks (list, read) and list_orgs.** `_context` and `org_id` stay available on every call.
- The open reads return the Pages shared with the user, the tables and Canvas blocks on them, and the Scenarios the user can read, as they are saved now. A read at an earlier point is refused with `blocked`: `as_of_point.change_log_id: change <n> is an earlier revision than this workspace's latest change <m>; reading an earlier revision needs the version history permission, which the current user does not hold`. A cursor carries the point its first page read, so `after` or `source_offset` from a result returned before the workspace's latest change is refused the same way; start that read again.
- A table `read` returns the rows and columns the table saves. A row or column selector that names an item the table's saved filter leaves out gets the answer an unknown name gets.
- A chat's `resource_uri` is refused as `inspect_chats` is, on `resources/read` and on `subscriptions/listen`.

An admin of the workspace can make the user an admin, which opens every tool; see [Invite or remove teammates](/guides/invite-teammates).

## References and links

- Selectors accept readable names, returned references, or IDs, unless a field says it takes less. Copy references from inspection results instead of building IDs.
- A returned reference has the form `Name#hex`, such as `Revenue#a1b`. The suffix is a prefix of the object's identity, at least three hex digits, and unique among objects of its kind when the result was written. Later creates can lengthen it; an older reference keeps resolving while it stays unique, and a fresh inspection carries the current form. A formula's `Rule#` reference is the exception: it carries all 32 hex digits of the formula's ID, so no later write lengthens it. A reference also keeps resolving after its object is renamed, when exactly one object of its kind carries the suffix and the written name is one that object carried: `Gusto#940` names the connection now called `Acme Payroll#940`, and `Completion and final validation#6ca` names a text block after an `update_text` changed its first line, with or without a page named. A suffix with a name the object never carried is refused as not a reference, with the object's current reference. Scenario and Page references follow the same rule: `Plan#725` names the Scenario since renamed `Plan - No Series A#725`, and `SA26-18a#50c` names a Page after `edit_pages` `update` renamed it, in `edit_pages`, `inspect_pages`, and the `page` a table `create` names. `Main` with the base Scenario's suffix names the base Scenario. A table row or column reference, such as `Acquisition mix · R006-1#6e4`, keeps selecting its coordinate in reads and writes after the Variable it shows is renamed, when the written name is one the Variable carried and the digits select one coordinate; the same digits with a name the Variable never had are refused with `does not match a saved coordinate`.
- Words written in front of a whole reference, such as `Original Headcount#78e`, read the object the reference at the end names, when the longest run of its trailing words that any object under those digits ever carried is that object's own name. A shortened name such as `checks#1d5`, or text with no space before the name, is still refused with the object's reference as the candidate.
- A reference whose name only a hidden object carried, such as a deleted table, a table saved only in another Scenario, or one outside your access, is `not_found` with no candidate, even when one visible object shares its digits: **"Original vendor spend#72f" names no object this lookup can see. The one visible object under its suffix has no record of that name. Under that suffix the name belongs only to objects this lookup cannot see, such as a deleted object, one saved only in another scenario, or one outside this lookup's access.** The visible object's own references, including one issued before a rename, still resolve.
- A suffix with no name before it, such as `#199`, is not a reference, and a write does not accept it, with one exception: a block named on its Page. A call that names a block on a Page, such as `after_block` in an `edit_pages` reorder, accepts `#672` for the one block on that Page whose identity starts with those digits, when no block on the Page is literally named `#672` and no other object of any kind, live or deleted, carries those digits; a suffix two blocks share is refused. A read-only tool, such as an `inspect_*` tool, selects the object the suffix belongs to when three things hold: exactly one live object of the requested kind that you can read carries those digits, that object has a reference, and no other object of that kind carries them, counting deleted objects, objects saved only in another Scenario, and objects you cannot read. The read's result names the object by its full reference, such as `Signup exclusion checks#199`; use that reference from then on. A write that names one such object by its suffix alone, and a read where a hidden object shares the digits, is refused as `not_found` with the readable object's current reference as its one candidate: **"#199" is not a reference: it is a suffix with no name before it, and that suffix belongs to one table_block. A reference is an object's name and its suffix together.** When several readable objects of that kind carry the digits, every call is refused, and the candidates are the reference of each: **"#199" is a suffix with no name before it, and several table_block objects this lookup can read share it.** When no readable object of that kind carries them, the answer offers no candidates: **No table_block named "#199" was found. "#199" is a suffix with no name before it, and no table_block this lookup can read carries it.** Tables, charts, Canvas blocks, Pages, saved queries, connections, triggers, Variables, and Dimensions answer this way, and Variables and Dimensions count as one kind; Scenarios keep the plain not-found answer. A read that names several targets keeps the answer beside the targets it read: `inspect_pages` `read` lists it in `unresolved_answers`, `inspect_pages` `list` in `unresolved_page_answers` next to `unresolved_page_names`, and an `inspect_table_blocks` `list` in its `unresolved` notice under `answers`, each entry with `target` (the token as written), `message`, `candidates`, and the refusal's `hint`; when some answers do not fit one result, the tokens left out are listed in `unresolved_answers_omitted`, `unresolved_page_answers_omitted`, or `answers_omitted`.
- A name that is ambiguous or matches nothing is refused with `error.candidates` when alternatives are known: each with `display_name`, `ref` to pass back, `kind`, and, when ranked, `score` and `match`. A Variable or Dimension edit whose bare name two objects share lists their references, such as `Net Income#abcd1` and `Net Income#abcd2`, when the saved identity proves which object each names; a layout name whose suffix matches current objects, such as `Total OpEx#6c6`, is refused with the current references under that suffix, each labeled variable or dimension, with the requested kind first. A Date candidate's `display_name` carries its period and grain, such as `2027, YEAR grain` beside `2027-01, MONTH grain` when a day such as `2027-01-01` falls in both columns. In a table read rolled up to a coarser `grain`, it also names the saved axis the period comes from, such as `2027, YEAR grain, from the saved QUARTER axis` beside `2027, YEAR grain, from the saved MONTH axis`. When a table saves a year axis beside a month axis and a `YEAR` read shows the same year twice, a period selector such as `2027` or `FY2027` selects the column the table saves at that grain, the one the Page shows; two candidates that differ in Variable, item, or Dimension, or two rolled-up copies with no axis saved at the read's grain, stay ambiguous, and a `#suffix` that matches two columns keeps its refusal.
- A table's saved rows and columns print the same reference in a layout `list`, in a read whose calculation did not finish, and in a calculated `read`, so a reference copied from any table result selects its row or column in the next read.
- A result names each object with `ref`, the selector to pass back, and `url`, the address that opens it in cfo.ai.
- A write also returns a resource link for each thing it created or changed, described "Open in cfo.ai" and meant for the user. End your reply with the link a tool returned, exactly as printed; a link you assemble yourself will not open.

## Results

Every result is JSON text. A result that is a JSON object also arrives as `structuredContent`. A `validate_code_blocks` call with `visual_review` also returns the render as image content. An MCP call has no chat to save that picture in, so its `visualReview` carries `fileError` and no `file`; see [What `validate_code_blocks` reports](/agents/canvas-blocks#what-validate_code_blocks-reports).

### Write receipts

A write receipt opens with a shared head. Tool-specific sections sit beside it.

| Field | Values |
| --- | --- |
| `status` | `applied`: everything asked for is saved. `partially_applied`: some items are saved; `items` says which. `rejected`: nothing is saved because the request or every item was refused. `no_op`: nothing is saved because saved state already matched. `blocked`: nothing is saved because a dependency or a rule refused the write. |
| `state_changed` | `yes`, `no`, or `unknown` |
| `counts` | `requested`, and when nonzero `created`, `reused`, `applied`, `skipped`, `rejected`, `unchanged`, and `unknown` |
| `items[]` | One entry per requested item, in request order: `ref`, `display_name`, `status` (`created`, `reused`, `applied`, `skipped`, `rejected`, `unchanged`, or `unknown`), and `reason` when it did not land |
| `readback` | `status`: `complete`, `partial`, or `unavailable`, with `reason`. A write whose readback is unavailable still saved. A write that read nothing back carries no `readback` at all: a table, Variable, or Dimension delete, a rollup or calendar edit, and other edits of saved state. Those receipts report `coverage.values: "not_evaluated"`, except a rollup or calendar edit that saved nothing because the saved state already matched, which keeps `not_needed`. |
| `warnings[]` | `code`, `message`, and `ref`: things the saved write will not do as asked |
| `error` | Present exactly when `status` is `rejected` or `blocked` |

An item whose status is `unknown` may or may not have landed. Read current state before you repeat it.

### Refusals and failures

- A refusal carries `error` with `code`, `message`, `transient`, and, when known, `candidates` and `hint`, beside `state_changed`. Codes include `ambiguous`, `not_found`, `invalid`, `blocked`, `conflict`, `stale_target`, `selection_too_wide`, `file_too_large`, `result_unavailable`, and `browser_validation_unavailable`.
- `result_unavailable` reads **The call's outcome is unavailable. Read current state before repeating a write; repeating it could apply it again.**
- A `not_found` for a name or `Name#hex` reference that only a removed connection or a deleted table carried says so, with the day in UTC: `"Stripe#aa9" named a connection that was removed from this workspace on 2026-10-05.` or `"Vendor breakdown" named a table that was deleted on 2026-08-12.` The table fact appears only when you could read that table just before it was deleted. A Scenario reference whose suffix belongs to a removed Scenario says `"Disposable#a17" named a scenario that was deleted on 2026-10-19.` or `merged into its parent scenario`, only for a user who could see that Scenario just before it was removed. Any `candidates` are objects that exist now, and the `hint` says each is a different object.
- A table or mapping write that PostgreSQL rolls back for a deadlock is retried once by the server after 50 to 100 milliseconds; a second deadlock returns a `blocked` refusal that says the write saved nothing, with `transient: true`, so the same call can be sent again.
- A result with `ok: false` and an `error_kind` is an answer, not a crash. Use its message and `hint` to choose the next call.
- Refusals and fully rejected writes arrive with `isError: true`. A write that saved some items stays a success, with each item's status.
- `transient: true` means the same call can succeed later without changes. A failure that knows whether it is retryable adds `Transient: true.` or `Transient: false.` to its text and `{"error": {"message", "transient"}}` to its structured content. The server runs a call again for you in a few cases: the one deadlock retry above; a write that waited behind a save with a later change number, such as a table write or a `map` that creates its target Dimension; and the second attempt a `save_query` gets when another change saved first. A failure that reaches you is not retried any further.

## Pagination and truncation

A list cut short carries `truncation` and, when it can continue, `next`:

- `truncation.by` says what cut it: `response_budget` (the next item did not fit one result), `count_limit` (the page reached the `limit` you set, or the most items the read loads, such as 100 jobs of each kind in an `inspect_integrations` `jobs` list), `row_limit`, or `depth`.
- `truncation.shown` counts what came back, and `truncation.total`, when counted, what the selection matched. No `truncation` means the result is complete.
- `next` holds the values that continue the read. Pass a cursor back unchanged, with the same tool, action, target, filters, and snapshot. An `inspect_table_blocks` cursor passed back beside a Scenario spelled differently from the cursor's own, such as `Base` beside `Base#52f`, still continues when both name one Scenario at the read's saved version.

| Tool and action | Page size | Continue with |
| --- | --- | --- |
| `inspect_pages` `list` | `limit`. Without it, every page summary that fits one result; `truncation.total` counts all pages. | `next.after` as `after`, with the same `scenario` and `target` |
| `inspect_pages` `read` | No paging. A read larger than one result leaves out its largest parts whole and marks each one; see [A page read larger than one result](#a-page-read-larger-than-one-result). | — |
| `inspect_pages` `share_links` | Each read examines up to 100 links, newest first, and returns the ones the user may see, or as many of those as fit one result. A user who does not see every link can get an empty page with a `next`. `truncation.total`, the links from this read's starting place on, is stated only for a user who sees every link. | `next.created_at_or_before` and `next.skip_at_that_time`, both passed back under the same names |
| `inspect_scenarios` `list` | `limit`. Without it, every visible Scenario that fits one result. | `next.after` as `after` |
| `inspect_history` `changelog` | At most 100 entries per read; `limit` takes up to 100. Without it, as many of those as fit one result. | `next.before` as `before` |
| `inspect_history` `changelog` with `search` | Each read searches up to 1,000 entries, newest first, and reports how many it read in `entries_searched`. | `inspect_history` `changes_between_points` | No paging while the comparison fits one result. A larger comparison lists its changed objects, as many as fit, with full detail for as many of those as fit. | `inspect_dimension_mappings` | `limit` rows per lookup. Without it, every row of each lookup, or as many per lookup as fit one result. Each lookup's `row_count` is its true total. | That lookup's `next` as `after`, with the same `keys` |

Narrow the list with `status`, `kind`, or `query`. |
| `inspect_integrations` `queries` with one `query` | As many of the query's Variables and Dimensions as fit one result. A later page of an `inspect_table_blocks` `read` or `compare` is checked against its first page. A save takes its change number before it finishes saving, so a save with a lower number can finish after the first page was read and change what the read's snapshot shows. When that happens, the later page returns no rows and is refused as `blocked` with `transient: false`: **A save at or below change [n] committed after the first page, so this page was refused and returned no rows. This `after` value will never be accepted again; a read without `after` starts at the first page and shows the current saved table.** Start the read again without `after`. An `after` value issued before this check existed is refused the same way, with **This `after` value comes from an earlier version of table reads that did not record what the first page saw. It returned no rows and will never be accepted; a read without `after` starts at the first page.** A read that fits one page has no later page to check.

A table `read` that selects rows, columns, or periods, limits `depth`, continues from `after`, or stops early returns `partial: true` at its root. `coverage.delivery` says whether the response reached the end of that selection, and `coverage.calculation` whether its values finished calculating. A `period_range` that reaches past the table's window returns only the periods inside the window and adds one `read_note` issue that counts and lists the requested periods left out and names the window: `13 of the 20 requested periods are not in this read (2025-02 through 2026-01, 2026-09): they are outside the table's window, 2026-02 through 2026-08.` A table that saves no valid dates names the default window instead. The note appears on a table with one Date axis at month, quarter, or year grain. Period labels get the same note when that Date axis leads the columns, with or without a breakdown beneath it: on a table whose window is 2026-02 through 2026-12, `columns: ["2026-01", "2026-02", "2026-03"]` returns the 2026-02 and 2026-03 columns with `1 of the 3 requested periods is not in this read (2026-01): it is outside the table's window, 2026-02 through 2026-12.` A label outside the window is still refused, with the window's dates, when no other selector on its axis selects a coordinate, on a table that lists dates down its rows or by week or day, and in a write's target.

A changelog entry larger than one page keeps its place in the list. Without `include_details`, it comes back with an empty `changes` list and no `blocks` list, and `changes_truncation` and `blocks_truncation` beside them count what each list held. With `include_details`, it keeps every change, and a result larger than the allowance is replaced whole by the allowance marker.

### A page read larger than one result

An `inspect_pages` `read` that fits one result returns every block in full. A larger read fits itself, and it never returns part of a block or part of a Page's text:

- It leaves out the largest parts first, by size, until the read fits. A part is one block's settings and text, or one Page's own `markdown` on a read with `include_text`.
- A block left out stays in `blocks` with its `display_name`, `ref`, `type`, `createdAt`, `updatedAt`, and `guide_targets`, plus `detail_omitted_bytes`, the bytes left out. To read a table left out this way, pass its `ref` as `target` to `inspect_table_blocks` `list`.
- A Page whose own text is left out carries `markdown_omitted_bytes` and no `markdown` or `document_revision`.
- Each Page with a part left out carries `truncation` with `by: "response_budget"`, `shown` for its blocks returned in full, and `total` for its blocks. There is no `next`.
- When the block lists alone are larger than one result, every Page in the read returns `blocks: []` with `block_counts`, its block count by type such as `{"TABLE": 2990, "TEXT": 10}`, `blocks_omitted_bytes`, and a `truncation` whose `shown` is 0. Reading that Page alone returns the same counts; no call lists its blocks.
- One read names at most 50 Pages.

### A history comparison larger than one result

An `inspect_history` `changes_between_points` read that fits one result returns the whole comparison. A larger one keeps the comparison's own fields, such as its range and `inheritedChanges`, and never returns part of a changed object:

- `counts` counts every changed object by resource type and operation, keyed as `changes` is.
- The result lists as many changed objects as fit. `changes` holds the ones returned in full, the smallest first. `changes_without_detail` holds the others in the same buckets, each as `id` and `label`. An entry that holds nothing beyond its `id` and `label`, such as most deletes, stays in `changes`.
- `matched` counts the objects the read selects, `listed` the objects in this result, and `without_detail` the objects listed by `id` and `label` alone. `truncation` carries `by: "response_budget"`, `shown` for the objects in full, and `total` for the objects selected.
- To read listed objects in full, send the same `start` and `end` with `ids`, a list of up to 50 of the listed ids. The result holds only those objects, fitted the same way. An id that names no changed object comes back under `unresolved`, and so does the id of a change the user may not read.
- An object whose own detail is larger than one result carries `detail_bytes`, its size, on a read that names it. No read returns that detail.
- When the list itself does not fit, `next` holds `start`, `end`, and `after`. Send all three back with the same `scenario` and `ids`. `next.start` and `next.end` name the two changes the read compared, so the follow-up reads the same range even when the first read ended at `latest` or at a time. A page whose first object does not fit by `id` and `label` gives `label_bytes`, the label's size, in place of that label, so every page lists at least one object.
- A result that leaves out detail and lists every object carries `truncation` and no `next`: the follow-up is a read with `ids`.
- Counts and lists hold only the changes the user may read.
- When one call returns a comparison beside another history section, such as the changelog or a second comparison, each comparison gets an equal share of the result. A comparison that fits alone can then come back in this shortened form.

The read refuses these inputs as invalid:

| Input | Refusal |
| --- | --- |
| More than 50 `ids` | **ids names [n] objects; one read names at most 50** |
| An id longer than 64 bytes | **ids holds a value of [n] bytes; an id a comparison lists has at most 64** |
| An `after` that no comparison returned, or one from another workspace | **after is not a continuation a comparison returned; a valid after is the previous page's next.after** |
| An `after` sent with another Scenario, `start`, `end`, or `ids` | **after belongs to a comparison of another scenario, start, end, or ids; a continuation is valid only under the scenario and ids of the read that returned it and its next.start and next.end** |
| An `after` whose object the comparison no longer lists | **after names an object this comparison no longer lists; a read without after lists from the first object** |


## Read the Model at an earlier point

`inspect_pages`, `inspect_table_blocks` (every action except `bounds`), `inspect_canvas_blocks`, `inspect_dimension_mappings`, and `inspect_scenarios` take `as_of_point`. Without it they read the current state. It holds exactly one point type:

| Point type | Meaning |
| --- | --- |
| `change_log_id` | A change ID, as a write receipt or `inspect_history` reports it. The snapshot is the Model right after the workspace's latest change at or before that ID. Change ids are numbered across all workspaces, so an id between two of this workspace's changes can belong to another workspace; such an id reads the earlier of the two, and `inspect_table_blocks` and `inspect_canvas_blocks` report the change they read in `as_of`. It accepts the ID as an integer or as a string of digits, as do `before_change_log_id` on `inspect_table_blocks` `compare`, `at_change_log_id` on `edit_scenarios` `snapshot`, and `change_log_ids` and `to_change_log_id` on `edit_history`. Results print the ID in either form. |
| `timestamp` | An exact instant in RFC 3339 with a time zone, supplied by the user, the context, or a tool result. |
| `calendar_boundary` | `unit` (`day`, `week`, `month`, `quarter`, or `year`), `offset` (0 this period, -1 the previous, 1 the next), and `boundary` (`start` or `end`), in the user's time zone from `_context`, or UTC without one. Weeks start on Monday. Use it for "yesterday" or "last month". |
| `relative_duration` | `amount`, `unit` (`minute`, `hour`, `day`, or `week`), and `direction` (`ago` or `from_now`), from server time. A day is 24 hours and a week seven days. |

A `change_log_id` before the workspace's first change is refused with `not_found`: `as_of_point.change_log_id: change ID <n> is before this workspace's first change; this read accepts any ID at or after the first change. Change IDs are global across workspaces; gaps may belong to other workspaces.`, with the hint `This workspace's changes are the ids its write receipts and inspect_history report.` An ID after the workspace's latest change reads the latest change.

`inspect_history` `changes_between_points` takes a `start` point and an optional `end` point, which may also be `latest: true`. A `change_log_id` there resolves to the workspace's latest change at or before it. The range is the response's own `startChangeLogId` and `endChangeLogId`, so the parent's `changes_between_points` over the same points lists what a child Scenario's `inheritedChanges` counts.

## Safety annotations

Each tool carries standard MCP annotations, which clients use to decide which calls need the user's approval:

- `readOnlyHint: true` on every `inspect_*` tool, `inspect_chats` included, `validate_code_blocks`, and `list_orgs`.
- `openWorldHint: true` on tools that can reach outside cfo.ai, notify a person, send an invitation, or change an outside integration: `edit_pages`, `edit_triggers`, `edit_profile`, `edit_integrations`, `edit_team`, `edit_org`, `call_connected_api`, `notify_user`, `notify_engineering`, and `validate_code_blocks`.
- `destructiveHint: false` only on `notify_user` and `notify_engineering`. Every other write keeps the MCP default, which treats it as possibly destructive.

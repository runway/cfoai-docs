A **Skill** is a saved process that tells Ari how to handle a recurring situation: what steps to take, what conventions to follow, and when to activate at all. Once saved, Ari activates a Skill on its own when a request matches its trigger condition — you don't need to reference it by name.

## Built-in and saved Skills

cfo.ai ships with built-in Skills covering common workflows. Your workspace can also hold its own saved Skills, written for how your team specifically works. Ask Ari to list what's available, including a search by name, to see both together.

## Create a Skill

Ask Ari to save a new Skill and give it:

- **A name** — lowercase letters, digits, and hyphens, like `board-report`.
- **A trigger condition** — phrased as when it should activate, for example "Use when the user asks for a board or investor report."
- **Instructions** — the full workflow: the steps, structure, and conventions Ari should follow once the Skill activates.

A good trigger condition is specific enough that Ari doesn't activate the Skill for unrelated requests, but general enough to catch the different ways someone might phrase the same ask.

## Update or remove a Skill

Ask Ari to update a saved Skill's description or instructions, or to delete one you no longer need. Built-in Skills can't be edited or deleted — if a built-in Skill needs to work differently for your workspace, ask Ari to save a new one with a different name instead.

## Sample custom Skill prompts

These are complete, ready-to-save Skills. Each one gives the three things Ari needs: a name, a trigger condition, and the instructions to follow once the Skill activates. Every block below has a copy button — copy each field, then ask Ari to save a Skill with them.

### `driver-model-scaffold`

**Trigger condition**

```text
Build a driver-based, natively dimensional model — volume or capacity spine through unit economics, P&L, and headcount. Use when creating a new operating model, adding a dimensioned variable with a roll-forward, or debugging circular references, drill-in rows that read zero, or inflated first-period values in saved tables.
```

**Instructions**

````markdown
# Driver model scaffold

## Build order
Build and verify one layer at a time. Never stack a layer on an unverified one.

1. **Volume/capacity spine** — the physical unit the business scales on (stores, megawatts, seats, shipments). Roll it forward.
2. **Unit economics** — per-unit drivers (transactions, price, utilization) that produce revenue per unit.
3. **Revenue** — spine × unit economics.
4. **Costs** — rates against revenue, or per-unit costs against the spine.
5. **Headcount** — see `headcount-from-capacity`.
6. **P&L and capital structure** — opex, D&A, debt, interest.

After each table, read it back at `depth: 0` with `periods: "boundaries"`,
`formula_origins: "off"`, `source_health: "off"`, `format: "text"`. Confirm
`formula_errors: 0` and that the numbers are the right order of magnitude before
continuing.

## The four traps

### 1. Parent self-sum creates a cycle at the child
A rule on the parent's `[Date.Month in any]` condition does not constrain the business
dimension, so it **also matches every child**. A parent self-sum therefore makes each
child sum itself.

Symptom: `Circular reference` on every row of a variable, parent and children alike.

Fix — explicit rules at both scopes, in one write:
- Parent target `Variable`: `sum(`Variable`[Dim in any])`
- Each child target `Variable > Item`: the actual formula

Any variable that (a) has a breakdown and (b) needs a parent aggregate or has a
self-referencing recurrence needs both. Multiplicative chains (`A * B`) usually don't —
the parent computes correctly from parent operands.

### 2. Exact-reach seeds do not cross dimensions
A seed written via `cell_updates` lands as an **exact** condition:
`$[Channel = "In-Store", Date.Month = "2025-01"]`. It will not reach a cell that also
carries a Region coordinate. The recurrence then starts from nothing and the whole
drill-in reads 0.

Symptom: parent row is correct, every child under a *different* dimension reads 0. The
write receipt warns `every row drilled under "X" reads 0 while the row above it does not`.

Fix — when reading a variable that lives in a different dimensional space, drop the
foreign dimension and re-supply time:

    `Monthly Sales per Store`$[Date.Month = this.Date.Month]

Use this for every cross-space read: totals read from a segmented cell, rates read from
a dimensioned cell, any scalar consumed inside a breakdown.

### 3. First-period differencing artifact
`X - X[-1]` in period 1 has no prior value, so the entire opening balance registers as
period-1 activity. This silently inflates capex, hiring, and anything derived from them.

Fix:

    if(`X`[-1] > 0, max(0, `X` - `X`[-1]), 0)

### 4. Write budget
One request accepts **50 combined updates**, and each regime counts separately — so a
`row_updates` entry carrying both `actuals` and `forecast` costs 2. Practical ceiling:
**25 row_updates**, or fewer alongside `cell_updates`. Creation counts too: a new
variable plus its initial formula is 2.

Plan splits in advance. A rejection applies no writes at all.

## Conventions
- Set both `actuals` and `forecast` on every default. With no last-close configured,
  either regime may be selected.
- Seed roll-forwards at the first period via `cell_updates`; the recurrence carries the rest.
- Make every assumption a named variable, not a literal inside a formula. Literals aren't playable.
- Ratios use `iferror(a / b, NULL)` — never a bare division.
- Weighted-average parents: derive from two aggregates that are themselves sums
  (`total cost / total units`), never from an element-wise product across two wildcards —
  that does not pair up and silently returns a plain sum.
````

### `forecast-simulator`

**Trigger condition**

```text
Build a Canvas simulator whose scenario ties exactly to the model baseline at default settings, so every visible difference is attributable to the driver the user moved. Use when creating an interactive forecast tool, what-if page, scenario explorer, or any page with sliders over saved model variables.
```

**Instructions**

````markdown
# Forecast simulator

## The property that matters
At default slider settings the simulated series must sit **exactly** on the baseline. If
it drifts, every delta the user reads is contaminated by model error and the tool loses
credibility.

Two ways to achieve it, in order of preference:

**A. Re-run the recurrence.** Rebuild the series in component code using the model's own
inputs and the scenario driver. At the default driver value this reproduces the model
exactly because it is the same recurrence:

    const mwS = [];
    for (let i = 0; i < n; i++) {
      if (i === 0) { mwS.push(mwB[0] || 0); continue; }
      const contPrev = (contB[i-1] || 0) * Math.pow(live.contract, i-1);
      mwS.push(mwS[i-1] + Math.max(0, contPrev - mwS[i-1]) * live.act);
    }

**B. Ratio against baseline.** Where a recurrence is impractical, scale the baseline by
the ratio of scenario to default:

    const g = ((1 + live.traffic) * (1 + live.price)) / ((1 + D.traffic) * (1 + D.price));
    const sim = base[i] * Math.pow(g, i);

At defaults `g === 1`, so `sim === base`.

Read cost rates, life, and load factors from a `rates` dataset rather than hardcoding, so
the component stays in sync when the model changes.

## Dataset rules
- **One breakdown per dataset.** Multiple variables each broken down by the same dimension
  in a single dataset collapses the duplicate child labels — you get the totals and one set
  of children, and the rest render blank. Split into one dataset per variable.
- Max 8 datasets per block. Check `dataset_evidence` in the write receipt: `series_count`
  and `series_names` tell you what actually came back.
- A series with empty `segments` is the variable **total**; populated `segments` are
  breakdown members. Filter to `segments.length` before stacking, or the total
  double-counts against its children.
- `layout.rows` become series; `layout.columns` (Date) become plotted points.

## Component contract
- `Block({ data, state, emit })`. React and its hooks are lexical bindings — no imports,
  no `window.React`.
- `Slider` fires `onChange(v)` for a local draft and `onCommit(v)` for an accepted change.
  **Persist only on commit** via `emit({ type: "setState", patch: { key: v } })`.
- Sliders must never write to the model. The scenario is a local preview.
- Provide a reset that restores defaults and clears saved state (`patch` values to `null`).
- Show a status pill so the viewer always knows whether they're looking at baseline or a
  scenario.

## After writing
`add_canvas` leaves `render_verified: false`. Always run `validate_code_blocks` on the
block id — it renders in Chromium in light and dark and returns real runtime errors. Fix
anything it reports before calling the work done.

## Chart selection
Before shipping charts, check whether any two are the same curve rescaled. If per-unit
economics are uniform across a dimension, then "units by dimension", "revenue by
dimension", and "profit by dimension" are one shape drawn three times. Replace duplicates
with **ratios that diverge** — cost as % of revenue, support headcount per 100 units,
profit per employee. A quotient of two things growing at different rates carries
information a level chart cannot.
````

### `headcount-from-capacity`

**Trigger condition**

```text
Model headcount as a ratio to the business's physical driver rather than a compounding growth rate, so the plan stays anchored as the business scales. Use when building a hiring plan, workforce forecast, personnel cost model, or department-level org plan.
```

**Instructions**

````markdown
# Headcount from capacity

## Why not a growth rate
A monthly hiring rate compounds. Fitting one to a fast-growth year and running it 48
months produces absurd totals — a 7.7%/month rate that matches one year of real hiring
yields 30,000 employees four years out.

Anchor headcount to whatever the business actually scales on: megawatts, stores,
shipments, accounts, ARR.

## Structure

    `Headcount per Unit` [Department]  — driver, seeded at the first period
    `Headcount` [Department] = `Headcount per Unit` * `Total Units`$[Date.Month = this.Date.Month]
    `Average Salary` [Department]      — driver constants
    `Personnel Cost` [Department] = `Headcount` * `Average Salary` / 12 * `Payroll Load Multiplier`

`Headcount` needs no parent/child rules — the parent computes correctly as parent-ratio ×
units. `Personnel Cost` does: parent is a sum, children are the explicit product.

Note the `$[Date.Month = this.Date.Month]` on the units read. The unit total lives outside
Department space; without it, the exact-reach seed on the spine won't reach a
Department-coordinated cell and every row reads zero.

## Let the ratio move
A flat ratio understates early scaling and overstates late. Give the ratio its own
decaying trend:

    `Ratio Growth` = `Ratio Growth`[-1] * `Ratio Decay`        // seeded positive, decay ~0.94
    `Headcount per Unit` [Dept] = `Headcount per Unit`[-1] * (1 + `Ratio Growth`$[Date.Month = this.Date.Month])

This reproduces a hiring surge early and flattens into operating leverage later, without
exploding. Tune the seed to hit year-1 actuals and the decay to keep the terminal ratio sane.

## Diagnostics worth surfacing
- **Revenue per employee** — sanity check against comparables.
- **Units per employee** — the productivity trend.
- **Support ratio** (corporate heads per 100 units) — whether the org is outgrowing what
  it serves.
- **Profit per corporate employee** — returns on overhead headcount. This one often
  declines, and saying so is more useful than hiding it.

## Reconcile to the P&L
If the P&L carries labor as a % of revenue, either drive that line from this build
(`Units * Cost per Unit`) or add an explicit reconciliation row showing the implied
percentage. Never let a bottom-up headcount plan sit beside a top-down labor percentage
with no tie between them.
````

A read-only analysis starts from saved Model content. Inspect the existing Table blocks, Variables, Scenarios, and source information, and answer from them without creating a new calculation.

## Read a saved table

Use `inspect_table_blocks` with its `read` block and the table that holds the values:

```json
{
  "scenario": "Main",
  "read": {
    "target": "Revenue by Customer"
  }
}
```

To narrow a follow-up to a visible row, cell, or subtree, copy row and column references from the response into `rows` and `columns`, and use `depth` to include the items beneath a selected row. [Read and explain formulas](/agents/read-formulas) covers everything a read returns.

## Compare or rank existing values

- Use the saved table's existing Scenario or time comparison when it already answers the question.
- To compare Scenarios the table does not save, give the read a `comparison` object, as [Read a table that compares Scenarios or periods](/agents/read-formulas#read-a-table-that-compares-scenarios-or-periods) shows. The saved table stays as it is.
- For a top-items question, read the item rows and rank them from the returned values yourself; the read does not sort. Rank only once you hold every item row. A read returns at most 500 rows, and fewer when they do not fit one result. When the result carries `next`, read the next page with `next.after` as `after` before you rank; see [Pagination and truncation](/agents/mcp-tools#pagination-and-truncation).

## Read the Model as it was

- A historical read uses `as_of_point` against the same saved table and the same target, which keeps a before-and-after comparison tied to one stable artifact. [Read the Model at an earlier point](/agents/mcp-tools#read-the-model-at-an-earlier-point) lists the point types.
- The `compare` block shows how a table changed since a saved change. It takes the table as `target` and the earlier change as `before_change_log_id`, and returns the table's read with a `changes` object beside it. For the table, `changes.tables` holds `before` and `after` counts of rows, columns, non-empty cells, formula errors, and dependent tables, their difference under `value_delta`, the rows removed or added since then under `row_membership`, and the saved changes in between under `operations`.
- A `compare` does not return each cell's earlier value. To put numbers side by side, read the table once with `as_of_point` and once without.

## Checking a proposed formula means saving it

`edit_table_blocks` cannot check a proposed table or formula without saving it. No action takes `dry_run`, and a call that sends it is refused. A `create` either saves and returns a receipt, or is refused and saves nothing.

Checking a new table, or a change to an existing one, means making the change, which needs the user's authorization. When the user wants to see a change before adopting it, make it in a Scenario other than Main.

[Validate and verify formula writes](/agents/validate-and-verify#validate-before-you-save) has the details.

## Create a new result only when authorized

A new ratio, signal, or comparison that does not exist yet needs a saved, visible Model artifact. A request for the new result is the authorization to save it: use `edit_table_blocks` to add a row and its first formula, then inspect the saved result.

If the user asked for no Model changes, explain what you can answer from the existing information, and name the saved change a new calculation would require. If the user asked to review a change before it is made, describe the change and wait; when they want to see it working before adopting it, make it in a Scenario other than Main, as the section above says.

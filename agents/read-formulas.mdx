Use `inspect_table_blocks` with its `variable` block when a user asks how a Variable is calculated, or why it behaves differently by segment or period. Use its `read` block to see the numbers a table shows and, only where the table's saved formulas prove it, the formula a row or column uses.

## Read a Variable's saved formulas

```json
{
  "scenario": "Main",
  "variable": { "target": "Gross Margin" }
}
```

- The result lists every formula definition saved on the Variable, each with its condition and its Actuals or Forecast range. A formula the product's own level-default sync saved, such as a generated sum or `0` on a number or the line formula above a percentage's lines, carries `writer: "level_default_sync"`; a formula a person or Ari wrote has no `writer`. Treat a formula with that writer as the product's: the sync replaces or removes it when the tables or the line formula change.
- Add `conditions` only when the question needs one exact saved scope, such as `["[Department = \"Sales\"]"]`. Leave it out when the user wants every formula.
- A Variable with many formulas returns them in pages. To read the next page, copy the response's `next.after` into `after` in the same `variable` block, with the same `target`.
- Leave out `target` to list every readable Variable in the Scenario. The listing is described under [Find a Variable or Dimension by name](#find-a-variable-or-dimension-by-name).

Use the `dimension` block the same way to read a Dimension's saved definitions, and the `items` block to list its items.

### Find a Variable or Dimension by name

A `variable` or `dimension` block without `target` lists every Variable or Dimension you can read, one short entry each. Add `contains` to keep only the names that hold a piece of text, in any letter case:

```json
{ "scenario": "Main", "variable": { "contains": "fee" } }
```

- Each entry holds `variable` or `dimension` with `display_name`, `ref`, and `location`: one table that shows the object, with its Page, or `Model` or `Source` when no table you can read shows it. An entry carries no formulas, dependents, or source. Pass its `ref` as `target` to read the object in full.
- A page holds up to 500 entries, or as many as `limit` asks for, from 1 to 500. A page that stops early carries `truncation`, with `by` reading `count_limit` or `response_budget`, `shown`, and `total`, the count of every match, and `next`. Pass `next` back unchanged as the next call's input.
- Text that no name holds returns an empty `entries` list.
- `contains` belongs to a listing and `conditions` to a read with `target`. `contains` beside `target` is refused with **contains narrows the listing that a read without target returns; this read names target**, and `conditions` without `target` with **conditions selects the saved formula definitions that a read with target returns; a listing returns no definitions**.
- A cursor belongs to its listing. Sent back with a different `contains` or snapshot, it is refused with **after names no variable of this listing at the selected snapshot and contains; a listing's after is its next.after**.

### What reads each object

Each entry of a `variable` or `dimension` read that names `target` carries `dependents`, what reads the object at that snapshot. A listing entry carries none. `dependents` holds:

| Field | Meaning |
| --- | --- |
| `total` | Every dependent |
| `formulas`, `blocks`, `settings`, `manual_items` | Counts by kind |
| `inaccessible` | Dependents this user cannot read |
| `items` | Descriptions of up to 20 dependents |
| `formula_rules` | Up to 20 of the formulas that read the object, each with whether it can run and what a forced delete does to it |

A `delete` without `force` is refused exactly when `total` is above 0, and deletes at once when it is 0.

Each `formula_rules` entry describes one formula that reads the object. `formulas` still counts every reading formula, including ones the list leaves out.

| Field | Values |
| --- | --- |
| `dependent` | The reading formula, described as `items` describes it |
| `activity` | `dormant`: the saved formula cannot run in any affected Scenario at this snapshot. `potentially_active`: that is not proven. |
| `reason` | For a dormant formula: `outside_range` (the date it is pinned to is outside its range), `outranked` (a newer formula at the same scope wins), or `mixed_dormancy` (the reason differs across the affected Scenarios) |
| `force_effect` | What a delete with `force` does to the formula. `removes_rule` deletes the unused formula. `clears_expression` keeps its range and empties its expression, so the cell reads blank if its month enters the range later. `keeps_reference` leaves the saved reference, which then breaks, including when the user cannot edit the Variable that holds the formula. |

A refused `edit_table_blocks` `delete` and a refused `edit_pages` `delete_block` carry the same entries under `formula_rules`, and a table delete adds `formula_rules_omitted` when some did not fit the result.

### How each definition's scope is described

Each definition states its `time_grain` when it is dated, and its reach in words. [How results describe a formula's reach](/agents/formula-scope#how-results-describe-a-formulas-reach) explains the wording.

### Imported Variables and Dimensions

For a Variable or Dimension read from an imported source, the entry's `source_default` also states `order`, such as `last by MONTH` or `last by source order`. It says how a column that shows one row per record picks that row when a record has several: `by MONTH` orders the record's rows by the source's date column, and `by source order` says the source has no date column to order by. With no date column, the pick is the same in every calculation, but it is not the row's position in the source; [last](/reference/functions#last) states the rule. A column that sums its rows has no `order`.

A `variable` read marks a Variable's saved source read with `after_last_close`. The field sits on the Variable's only `[]` formula when that formula has no range and is exactly one aggregate over one source column, such as the `sum(<source column>)` an import saves. That formula reads source rows only through Last close, and the value is what the Variable reads in later periods where no other formula computes the cell: `"0"`, or `"null"` for a date or text Variable. Every other formula has no such field, including a `[]` formula of any other expression and both `[]` formulas of a Variable that has two; those compute every period. To read source rows dated after Last close, give the Variable a Forecast formula with the same read, such as `default_formulas.forecast: "sum(<source column>)"`.

### Read several at once

`target` on the `variable` and `dimension` blocks also takes a list of references:

```json
{
  "scenario": "Main",
  "variable": { "target": ["Amount#a4d", "Probability#058"] }
}
```

The response holds one entry per reference, in the order given, all read at one snapshot. Each imported source's query is stated once under `sources`, and an entry's `source.query_ref` names its key there. A reference that matches nothing is refused in its own entry while the others still answer: **No readable variable or dimension matches this target.** The refusal lists up to five `candidates` of the requested kind, each with its readable name, a reference usable as the next `target`, its kind, and a closeness score, so `Total Revenue` suggests the saved `Revenue`. A candidate never selects anything.

## Connect formulas to the values a table shows

Use the `read` block on the table that actually shows the result:

```json
{
  "scenario": "Main",
  "read": {
    "target": "Operating Plan",
    "rows": ["Gross Margin"]
  }
}
```

- A row or column carries its formula per range under `formulas` only where the table's saved formulas prove which formula its cells use, such as a row's own saved default. A cell that breaks its row's formula says so in the cell.
- When the saved formulas prove no formula for any cell of a row, the row carries the reason in place of a formula, as `formulas: {"unavailable": "Stored rules do not prove the selected expression"}`. A single such cell carries the reason as `formula_unavailable`. The cells are still calculated; read the Variable's saved formulas with the `variable` block.
- A read does not name the owner of a formula saved outside this table's rows and columns. `inherited_from` needs the engine's record of which formula each cell used, and the read does not ask for it.
- A `read` adds one `read_note` issue: **Cell formulas are not included in table reads for this workspace; a cell shown without a formula can still be calculated by a saved rule.**
- `formula_origins` returns no ranked formulas. A read that sends `"all"` or `"zeros"` returns the same rows and values, and adds two `read_note` issues: **Formula attribution is disabled for this workspace; missing formula-origin and input explanations do not mean that a cell has no formula or inputs.** and **formula origins are unavailable from the calculation service for this read**.
- `include_edit_rules: true` adds each returned row's and column's editing rules: the actions a write accepts there, its own Actuals and Forecast defaults with ownership and writability, and its formula roles.

Use the same Scenario for the formula read and the table read. The saved formula explains the intended calculation; the table read gives the values for the selected period, segment, and Scenario, and names a formula only where the saved formulas prove it.

### Select rows and columns

- Select rows and columns by the references a read prints, by unambiguous names or full paths, or by coordinate predicates. A name in backticks selects the same row as the bare name.
- An item row is selected by its path from its Variable or axis Dimension, one bracket per breakdown level, as a readback prints it: `Revenue[West]`, `Revenue[West][Enterprise]`, `Employee ID[E-207]`. The leading Variable may carry its reference suffix, `Revenue#a1b[West]`, which picks one of two same-named Variables; for rows made only of items, the first item's Dimension may lead the same way, `Employee ID#c2d[E-207]`. A selector that differs from exactly one saved coordinate only in whitespace or zero-width characters binds to it.
- A nested item written without the items above it, such as `Revenue[Enterprise]` for `Revenue[West][Enterprise]`, selects the one saved coordinate that ends in it. When several do, the read is refused as ambiguous and names each.
- A breakdown header's reference, as a read prints it, such as `Revenue[Region]#a1b`, selects the items the table shows at that level on the header's own side: rows for a row header, columns for a column header. Unlike a selector that names an item, a header reference follows the table's saved choice to hide empty items, so a level whose items are all hidden selects nothing. `depth` and pagination apply from the selected items. The same header on the other side is refused as not found, and items of the same Dimension under another row or column stay outside the selection. When the level is empty only because the table hides its empty items, the read adds one note that names the Dimension and the rule or saved filter hiding them, the same explanation a hidden item's own selector is refused with.
- A plain name that matches no saved coordinate is refused with **rows selector "[name]" does not match a saved coordinate** and a candidate list. When the name is a Variable shown elsewhere, the refusal adds **[Variable#ref] is shown on table [Table#ref]**, up to three readable tables; when it is the Dimension that groups the axis, it adds **[Dimension] is the dimension these rows break down by** and, where predicates are accepted, the predicate that selects its items. Case and punctuation do not matter for that match; a `Name#hex` reference or an ambiguous name keeps the plain refusal.
- The item that holds rows with no value displays as **None** and is written `empty:None` in a selector, such as `Region[empty:None]`.
- A text item is printed as written, even when it contains a colon. The read's `member` field, a receipt's `members` list, and a row reference such as `Cash Step[Expected in: open invoice #483]#c00` all write it `Expected in: open invoice #483`, and a formula matches that exact text.
- A read that names rows or columns by item holds every item of the layout, zero and empty items included, whatever the saved display hides; a header reference is the exception above and selects the displayed items. A read that names none shows what the app displays.

### Which targets take a write

Each rendered target's formulas say whether `formula` and `clear_formula` can be written there. A target whose cells a direct write would refuse, such as cells that show a source read the engine generates for a Variable with no saved formula, or cells whose origin the read cannot establish, does not offer those actions; that read-only target's formula carries a `readOnlyReason` instead, so a write is not attempted where it would fail. A Variable whose saved formula reads an imported column, such as `sum(<column>)` at `[]`, is writable: a cell formula saves at that cell's address and a column formula at the column's grain, beside the source read, which keeps supplying every other cell.

The field name differs by level: a rendered target's formula names it `readOnlyReason`, while a row or column that cannot be written names its own reason `read_only_reason` beside `writable: false`. Dated Actuals and Forecast defaults keep their own writability.

### Facts the read computed

A `read` result also carries `figures`, facts about the returned numbers that no row or column states. Each key appears only when its fact holds:

| Key | Present when |
| --- | --- |
| `signs_as_stored: "mixed"` | The outermost returned rows differ in sign, because every value keeps the sign it is stored with. |
| `currency` | The currency-formatted figures share no single saved code: `no saved code`, `some figures have no saved code`, or `saved codes differ`. |
| `window` | The table saves no valid date range and returns no period columns or rows, so every value aggregates over a defaulted range. It holds `start`, `end`, `granularity`, and `defaulted: true`. |
| `source_grain` | A source query holds several rows for one item of the Dimension that keys the rows. Each entry names the `query`, `dimension`, `rows`, `members`, and `max_rows_per_member`. |

Receipts from `edit_table_blocks` carry no `figures`.

## Read a table that compares Scenarios or periods

- A read of a table that compares Scenarios returns every compared Scenario's value when `columns` names periods: one column reference per Scenario and period, each labeled with its Scenario.
- A table that compares Scenarios in rows (`layout: ROWS`) returns each named row once per compared Scenario when `rows` names rows, each labeled with its Scenario.
- In such a table, a Variable, item, or period selector names the selected Scenario's row. A Dimension-led path such as `Employee ID[RW-1024]` is a selector of this kind. The result returns that row together with its copy for each compared Scenario.
- A compared row's own ref selects that row alone.
- When a compared Scenario returns no values, the result carries a `comparison_scenario_missing` issue, and coverage reads `incomplete`.
- `comparison` defaults to `"saved"`, the table's saved comparison. `"none"` reads the selected Scenario's own values and formulas.
- A `comparison` object compares the selected Scenario with each Scenario it names in this one read, whatever the table saves, and leaves the saved table unchanged: `{"scenarios": ["Budget"], "measures": ["VALUE", "DELTA"]}`. `measures` takes up to three of `VALUE`, `DELTA` (the compared Scenario minus the selected one), and `PERCENT` (`DELTA` over the selected Scenario's value); it defaults to `VALUE`.
- A column or row that is not the selected Scenario's own reads `writable: false`, with a `read_only_reason` that says what it shows: another Scenario's values, saved in that Scenario; another period's values, saved in that period; or the difference between two Scenarios or two periods, which is calculated and has no saved value.
- The comparison qualifier alone makes nothing read-only. The selected Scenario's own column or row is as writable under either reference the read prints, with or without the qualifier, as the same cells are in a read with no comparison.

## List tables and their layouts

- `list` without `limit` returns every table in the Scenario, and pages with `next.after` when the result ends early.
- With `target`, it returns each named table's full saved layout. A table whose layout is larger than one result comes back as the summary entry a list without `target` returns, with a `layout_problem` note that states why; a `read` of that table pages through its rows and columns.

## Read a monthly table by quarter or year

`read` takes `grain: "QUARTER"` or `"YEAR"` to read a table's Date periods at a coarser grain than the saved table's own, without changing the table:

```json
{
  "scenario": "Main",
  "read": { "target": "Operating Plan", "rows": ["Bookings"], "grain": "YEAR" }
}
```

- Each period holds what the Model calculates at that grain: the Variable's time rollup (its base periods summed, closed, or averaged), or a timeless formula recomputed there.
- A Variable with neither reads `#NO_ROLLUP` in those cells, explained as no formula computing it at that grain, with its values in the table's own periods. The app shows such a cell as 0, and a Scenario or time comparison read at a coarser grain also shows 0 there.
- The period columns come back `writable: false`, because their references name the date each period starts and would name the saved month column in a write. A read at the grain the table already shows is the table's plain read, with writable period columns.
- A finer grain, or a table with no Date axis, comes back as an `invalid` result rather than a tool error, with its reason: `grain QUARTER is finer than this table's YEAR periods; a read's grain shows the periods at their own grain or rolled up to a coarser one`, or `grain QUARTER sets the grain of a table's Date periods, and this table has no Date axis`.
- Continuation cursors carry the grain.

A period selector can be written the way people write it, and it is read under each column's own grain: `2027` or `FY2027` selects a year column, `Q3 2026` or `2026 Q3` a quarter column, and `Mar 2026` a month column. `2027` never selects January of a monthly axis. The stored form, such as `2027-01`, still works everywhere. On a table that shows a year, half, or quarter column beside monthly columns, a month selector such as `2027-01` or `Jan 2027` names the month column rather than the coarser column that starts in that month, and `2027` names the year column. The month wins only over coarser columns of its own period: a coarser column from another period that carries the same label, such as a cohort member labeled `2027-01` under the 2026 year row, is still ambiguous with it, and that refusal's candidates carry their grain, as `2027-01, YEAR grain` and `2027-01, MONTH grain`.

A plain read of a table whose only column axis is Date, with no comparison and no saved query, calculates each run of consecutive requested periods on its own and merges the runs, so `2027-01`, `2027-12`, and `2028-08` calculate three months, not twenty. Consecutive periods still make one calculation. A comparison read, a table with dates on rows or nested with another column axis, and a read with a `where` predicate calculate the whole span as before.

## When the table cannot calculate

When the calculation service cannot compute a table, `read` still returns the saved configuration: the rows, their default formulas and formatting, and the saved column axes. No cells come back.

- Each axis entry is marked `axis: true` and carries its Dimension, grain, and writability, such as `{"ref": "Date#10b", "axis": true, "dimension": "Date", "grain": "MONTH", "writable": true}`, so an empty `columns` list never stands in for a Date axis that exists.
- The result carries a `calculation_unavailable` issue. When the calculation service explained the failure, the message includes `The calculation service reported <code>: <message>`, such as `table_config/external_column_not_mapped: external column Class L1 is not mapped in table …`, so you can name the cause instead of guessing.
- The issue also carries `category` (`capacity`, `model`, `request`, `dependency`, or `internal`), a `transient` flag, and a sentence stating what the category means. Retry only a transient failure: a calculation that did not finish within its time limit is `capacity` and not transient, while a service that did not answer is `dependency` and transient. A calculation the service had to stop for crossing its memory or time limit answers `capacity/calculation_memory_limit` or `capacity/calculation_time_limit` after one attempt, with the limit it crossed in `details`; the memory failure is transient only when memory left from earlier calculations filled at least half the limit, so a fresh worker could fit the same request.
- A failure the calculation service did not classify carries the error as raised, clipped to 500 characters, with no `category` or `transient` flag, so assume nothing about a retry.
- When the read chose its own comparison, the message says which one the failed calculation used: `The failed calculation used this read's own comparison: scenarios "Main (Evidence)", "Plan+", measures VALUE.`, or `The failed calculation used this read's comparison none, with no compared scenario.` When the table saves a comparison, it adds `The comparison field lists the table's saved comparison.`, because the answer's `comparison` field shows the saved one, not the one requested.

A table whose saved comparison names a Scenario that no longer exists still reads. The comparison columns are dropped for the calculation only, and a `table_problem` issue names the former Scenario. An `edit_scenarios` `delete` lists the readable tables that compared against the deleted Scenario as `tables_comparing_against_it`.

A `read` can also carry a `mapping_warning` issue, the same one a table write's receipt reports. [Read the receipt](/agents/validate-and-verify#read-the-receipt) states when it appears and quotes its sentence.

## Explain one cell's inputs

To trace a cell, read its Variable's saved formulas with the `variable` block, then `read` each Variable a formula names by its own reference.

`include_inputs: true` returns no input rows and no account of what each read returned:

- The read returns the selected rows' calculated values and adds one `read_note` issue: **Input drill-ins are disabled for this workspace; contributing-input rows are unavailable, not absent.**
- `include_inputs` needs `comparison: "none"`. On a time or Scenario comparison, the read answers with an invalid-input refusal that names the option, not a tool error.

Every `read` also reports `calculation.source`. When a value is in doubt, [Verify the calculated values](/agents/validate-and-verify#verify-the-calculated-values) says when to read again with `recalculate: true`.

## Read the Model at an earlier point

Use `as_of_point` when the user asks about the Model as it was at a previous saved change; leave it out for the current state. [Read the Model at an earlier point](/agents/mcp-tools#read-the-model-at-an-earlier-point) lists the point types.

- `inspect_canvas_blocks` takes it too, and returns each block's `dataset_layouts` at that point.
- `inspect_table_blocks` `items` reads the source run the Model used at that point.
- `bounds` reads current source state and refuses `as_of_point` with `bounds reads current source state; as_of_point applies to items`.

## Explain the business meaning

Lead with what the formula does. Then explain its inputs, the Scenario, the Dimensions involved, and whether Actuals or Forecast changes the result. Include assumptions only when they matter to the user's question.

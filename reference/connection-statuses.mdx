A connection's status says whether its data is current and whether you must act. An integration or an upload shows one status; an MCP server or an API shows two, **Connection** and **Data sync**, as [Connected](#connected) describes. You see it on the connection's row in the sidebar's **Connections** section, on the card that opens when you point at the row, on the connection's page, and on the source's card in the connection manager. Ari reads the same status when you ask about a connection. To fix a problem step by step, see [Fix a connection that needs attention](/guides/fix-a-connection).

## Sidebar marks

The mark at the right end of a connection's row in the sidebar says whether anything needs you.

| Mark | Meaning |
| --- | --- |
| No mark | The data is in and current (**Synced**), an MCP server or API is ready (**Connected**), or a table too large for one sync is still being read (**Still loading**). |
| Blinking orange dot | A sync is running (**Syncing**). |
| Steady orange dot | Something is incomplete but usually needs nothing from you: the sync resumes by itself, cfo.ai must fix it, or someone else must act. Two cases do need you. A connected file that waits for a decision shows this mark, because nothing failed, and offers **Investigate with Ari**; see [Waiting for your decision](#waiting-for-your-decision). A **Partly synced** connection whose source refused access to a table offers **Reconnect**. |
| Red triangle | A problem you must act on. The card names it and offers the fix. |
| Gray dot | Setup was not finished, someone stopped the latest sync, or the source was added but not connected. |

With no connections, the section reads **No connections yet**. The **Connections** section shows one row per app. An app you connected more than once, such as one QuickBooks company per entity, gets a parent row with its connections nested under it, and the parent shows the mark of its most urgent connection. A connection you have not named takes its label from the system it connects: the integration's name, then the company or file that system holds, such as **Justworks — Acme** or **Google Sheets — FY26 Budget**. A bank keeps its bank name alone, such as **Chase**, and an uploaded file keeps its file name. A connection whose system has given no name yet, such as an unfinished setup, is named for its integration, and several such connections of one integration are numbered in the order they were created: **Stripe**, **Stripe (2)**. A name you give a connection always wins. Ari uses the same labels in its chat notes, and still finds a connection when you call it by the company name alone. Under a parent row, a nested connection leaves out the integration's name, so it reads **Acme UK**. Under a parent row, a nested MCP server or API that has only its app's name reads **MCP server** or **API**, with the same number. A group of APIs is named as the connection's own name spells the app, such as **Alpha Vantage**, or, when the connection is named differently or all in lowercase, by the app's name with a capital first letter.

## Statuses

### Synced

The data reached your Model, and the last sync finished. Mark: none. Action: none. The card also shows **Last synced** and **Used in**.

A connection with no saved query of its own also reads **Synced** when a saved query on another connection reads its tables, such as several QuickBooks companies whose tables are all read by the queries saved on one of them. Its line reads **Data synced. Read by queries on [connections].** and names the connections that hold those queries. Ari reads the same status and names the same connections. Only a connection you can see counts: when the queries sit on a connection you cannot see, the connection reads [**No queries yet**](#no-queries-yet) for you. A sync that is running, failed, or stopped keeps its own status.

### Connected

An MCP server or an API is ready for Ari to call. Mark: none. Its page and its sidebar card show two statuses: **Connection**, which reads **Connected** while Ari can call its tools or endpoints, and **Data sync**, which reads the state of the sync setups Ari saved for it, such as **Synced**, **Syncing**, **No queries yet**, **No data found**, or **Needs attention**. A working server can therefore read **Connection: Connected** beside **Data sync: Needs attention** when an import failed. A server with no sync setup has no **Last synced** time. When the data sync is failed or blocked, the **Data sync** section offers **Fix with Ari**, which starts a chat about that sync; someone who cannot edit the connection reads **Someone with edit access can fix this sync with Ari.** instead.

### Syncing

A sync is running, or a first sync is queued. Mark: blinking orange dot. The connection's page reads **A sync is running now.** No **Reconnect** or **Retry** is offered while it runs. A connection also reads **Syncing** while one of its saved queries is being saved, whether Ari is saving it or someone is editing its SQL or moving it in the app. Ari waits for that save before it reads the query's columns. A save that ran too long saves nothing, and Ari is told so. While cfo.ai waits on the provider, the line says how long it has waited:

- **Waiting [time] so far for [source]’s first sync to finish.** It may add what the provider last reported, then **cfo.ai keeps waiting while [source] reports the sync still running, and stops this sync if no such report comes by [date and time].** cfo.ai checks every 10 minutes. Each check at which the provider reports its sync unfinished moves that date and time to 20 hours after the report, so the wait lasts as long as the provider keeps reporting and ends only after 20 hours with no such report. For a source that syncs through Fivetran, the provider's report reads **Fivetran reports its first historical sync of the account still running**, or, when the source's API has stopped answering Fivetran for now, **Fivetran rescheduled its first historical sync of the account because the source's API allows no more calls for now; its next attempt is due at [time]**. cfo.ai keeps waiting through a rescheduled first sync and asks Fivetran to run it again once that time has passed. For a bank connected through Plaid, the report reads **Plaid is still preparing the initial transaction pull** or **Plaid's transaction update status is unavailable**. A bank waits only while Plaid has no transactions ready; once Plaid has recent transactions, the first sync loads them.
- **Waiting [time] so far for [source] to prepare the data this sync reads.** It may add what the provider last reported, then **cfo.ai keeps waiting while [source] reports it is still preparing the data, and stops this sync if no such report comes by [date and time].** A connection that has completed a sync before reads this line in place of the one above, so its wait is never called a first sync.
- **Waiting [time] so far for cfo.ai’s request allowance at [source] to reset. The allowance for this organization is used up or nearly used up, and the sync resumes on its own when it resets.** It ends with **If it hasn’t reset by [date and time], this sync stops at its next check after that.** That date and time is 20 hours after the wait began and does not move, because a refused request is no progress. Xero, for example, limits how many requests an app can make each day.
- **Waiting [time] so far for [source] to finish a sync it is still running. cfo.ai loads that sync once it finishes. cfo.ai keeps waiting while [source] reports the sync still running, and stops this sync if no such report comes by [date and time].** A source that syncs through Fivetran was still running its own sync 45 minutes after cfo.ai asked for one. cfo.ai starts no new sync and checks again about every 10 minutes, for as long as the source reports the sync unfinished; the wait ends only after 20 hours with no such report. The data from the last loaded sync stays usable meanwhile. A bank connected through Plaid reads this line during a full-history refresh while Plaid prepares the complete history: a full-history refresh loads nothing until then, because it replaces the stored transactions, and the bank keeps its stored transactions while it waits. The card shows the same line when Fivetran rescheduled a later sync because the source's API allows no more calls for now, although that sync is postponed and not running. cfo.ai asks Fivetran for no sync before the time Fivetran set for its next attempt, asks for one at the first check after that time, and loads the sync once it finishes. A check at which Fivetran reports the sync rescheduled counts as a report, so the wait goes on when that time is more than 20 hours away.

### Partly synced

The last sync finished without some of the source's tables. The data that arrived is usable, and the missed tables count as stopped until a sync refreshes them; see [When a source stops updating](/concepts/connected-data#when-a-source-stops-updating). Mark: steady orange dot. The line names up to three tables and counts the rest, and once cfo.ai has read why each table failed, it names the tables the source refused:

- Until cfo.ai has read the cause, for a moment after the page opens or for as long as cfo.ai cannot read the connection's sync outcome: **[Source]’s last sync couldn’t refresh [tables]. cfo.ai will try again on the next sync. Everything else is up to date.** Action: **Reconnect**, as for any connection that needs attention, until cfo.ai has read the cause. When the source refused no table, the line stays the same and **Reconnect** is no longer offered.
- The source refused this connection's sign-in or permissions for every missed table, such as a QuickBooks account that cannot read **accounts**: **[Source] refused this connection access to [tables], so the last sync didn’t refresh that data. A reconnect with an account that can read it lets the next sync refresh it. Everything else is up to date.** Action: **Reconnect**.
- The source refused some missed tables and not others: the refusal sentence, then **The last sync also couldn’t refresh [tables]. cfo.ai will try again on the next sync. Everything else is up to date.** Action: **Reconnect**, which repairs only the refused tables.
- The source refused none of the missed tables: **[Source]’s last sync couldn’t refresh [tables]. cfo.ai will try again on the next sync. Everything else is up to date.** The line names no cause. Action: none; the next sync retries the missing tables.

A refusal is the source answering a sync request with a sign-in or permission error, such as HTTP 401 or 403, or QuickBooks Online's **Permission Denied**. A rate limit, a timeout, or a failure in cfo.ai's own reader is not a refusal.

A table that is only [still loading](#still-loading) is not counted as missed. When the last sync missed one table and left another still loading, the connection reads **Partly synced**, and the line gives the missed table's sentences, then **Still loading [table] ([N] [records] read so far). Each sync picks up where the last one stopped.**, and ends once with **Everything else is up to date.**

### Still loading

The last sync finished, and the only tables it left unfinished are too large to read in one sync. Each sync reads on from where the last one stopped, so the table fills over several syncs and nobody needs to act. Mark: none. Line: **Still loading [table] ([N] [records] read so far). Each sync picks up where the last one stopped. Everything else is up to date.**, such as **Still loading payment methods (144,300 customers read so far).** The line names up to three tables and counts the rest. The number is how far the read has got, not the size of the table. Action: none; **Reconnect** and **Retry** are not offered.

Stripe (Direct) is the source that reads this way: Stripe lists payment methods one customer at a time, so an account with many customers needs several nightly syncs for that table; see [Stripe (Direct)](/reference/integrations#stripe-direct). Until the read finishes, Ari still treats the table as incomplete.

### Setup not finished

Someone started connecting the source and did not finish. The setup may have failed, been abandoned, or still be open in someone's tab. Mark: gray dot. Line: **Syncing won’t begin until setup is finished.** Actions: **Finish setup** continues the same connection, and **Cancel setup** removes it without asking, because it holds no data yet. **Send link**, beside **Finish setup** on the connection's page and its hover card, makes a link that continues the same setup for someone else who holds the source's sign-in; its tooltip reads **For someone else with the [source] sign-in**. See [Send a link so someone else can connect a source](/guides/send-a-connect-link).

A source whose setup cannot be resumed, such as Stripe (Direct), offers only **Cancel setup** on the card, with **Setup wasn’t finished. Cancel it and connect [source] again.** On the connection's page, the line says **Remove it** and the button is **Remove connection**. People who cannot manage connections see the line and no button.

### Connection failed

Setup failed before the source linked. Mark: red triangle. Line: the failure's reason, or **Retry to set it up again.** Action: **Retry**.

### cfo.ai lost access

The source revoked cfo.ai's access, for example after a password change or an expired authorization. Mark: red triangle. Line: **Reconnect to start syncing again.** Action: **Reconnect**, then sign in to the same company the connection already holds. **Send link** beside it makes a link for someone else to do that sign-in; see [Send a link so someone else can connect a source](/guides/send-a-connect-link).

The data the connection synced before it lost access stays in your Model. Ari can still read it and answer from it, and it tells you when that data was last synced; new rows arrive only after you select **Reconnect**.

A source that syncs through Fivetran, such as BigQuery, Maxio, or Ramp, also shows this status when Fivetran has paused its connector, which Fivetran does on its own after the connector stays broken for a long time. A paused connector runs no sync, so **Retry** is not offered. **Reconnect** opens Fivetran's Connect Card for the same connection, and finishing it resumes the connector. A Gmail connection made before cfo.ai stopped copying mailboxes follows a stricter rule: its reconnect must be for the mailbox it already copies, and a reconnect cfo.ai cannot confirm is refused and leaves the connection without syncs; see [Messages when a new connection is refused](#messages-when-a-new-connection-is-refused). The failed sync's record keeps Fivetran's own report of what the owner must fix, such as **The user cannot access BigQuery tables/project (BigQueryConnectorTask_ACCESS_DENIED)**, and Ari reads it when you ask why the sync failed; the connection's line reads **Reconnect to start syncing again.** The record keeps the report the same way when Fivetran marks a connector's setup broken and asks for a new sign-in. For that BigQuery report, see [BigQuery](/reference/integrations#bigquery).

When you return from Fivetran's Connect Card, cfo.ai asks Fivetran to run its setup tests before it counts the connection as reconnected. The page reads **Fivetran connected** and **Fivetran is connected. Returning to cfo.ai...** when they pass. When they still ask for a re-authorization, it reads **Finish setting up [source]** with **Fivetran still needs a few details before cfo.ai can read [source]. Go back to Fivetran to finish setting it up.** and a **Finish setup** button that opens the Connect Card again; the connection keeps **cfo.ai lost access** until the tests pass. A sync you start within 15 minutes of a reconnect runs the tests once more before it asks for another reconnect.

An HR or payroll connection that syncs through Merge, such as Justworks, BambooHR, or Hibob, shows **Reconnect required** when Merge has stopped syncing its account and asks for it to be linked again. The data from the last successful sync stays, and the nightly refresh leaves the connection alone until you select **Reconnect**.

### Missing access in [source]

The source is not sharing some tables the reports need, such as **Missing access in NetSuite SuiteAnalytics**. Mark: red triangle. Line on the card: **[Source] isn’t sharing some tables the reports need. Open the connection for the steps to fix it.** A connection whose saved query fails because it reads one of those hidden tables also shows this status, not **Sync failed**, because another sync cannot help until the access is fixed. The connection's page shows an **Access missing** badge and the steps. For NetSuite they read: **NetSuite isn't sharing some tables cfo.ai needs for your financial statements. Have your NetSuite admin create an access token for the Data Warehouse Integrator role, then reconnect NetSuite with that token. Changing only the role ID won't work. Missing tables: …** Action: fix the access in the source, then **Reconnect**.

### Sync failed

There are two kinds:

- The provider's own sync failed, often for a moment. Mark: steady orange dot. Line: **[Source]’s sync hit an error. cfo.ai will try again on the next scheduled sync.** When the provider gave a reason, its report sits between the two sentences, for example **BigQuery’s sync hit an error. Fivetran reports: Problem with view (BigQueryConnectorTask_VIEW_ERROR): [the view Fivetran could not read]. cfo.ai will try again on the next scheduled sync.** Fivetran's report gives each failing task as its message, its code in parentheses, and its details, which name what failed, such as the view or table; several tasks are separated by semicolons. Ari reads the same report. Action: none, or **Retry** to run it now. When the report names something to fix at the source, fix that first. For a source that syncs through Fivetran, a sync that you or Ari start, and the weekly sync of a connection whose [syncs are paused](#syncs-paused), asks Fivetran for a new sync once Fivetran's setup tests pass, even while Fivetran still shows the earlier failure. A fix made at the source or in Fivetran's own dashboard therefore takes effect with the next **Retry**, and the new sync's result decides whether the connection still fails. When Fivetran is already running a sync, cfo.ai waits for that sync instead of asking for another. A sync still ends without a request when the setup tests fail, when Fivetran asks for a new sign-in or has paused the connector, when Fivetran gives the earlier failure no time, or, on a connection that has never finished a sync, when the report names a problem that another try cannot clear, such as a BigQuery access refusal. When Fivetran reports the connector broken by a generic sync failure and nothing else, and its setup tests pass, the nightly refresh starts one ordinary sync on up to two later nights; a success clears the count, and a connector that needs a new sign-in or is paused is not retried this way. When every problem Fivetran reports carries the code `incident_in_snowflake`, the failure is in cfo.ai's own data warehouse, not at your source: the next scheduled sync, or **Retry**, has Fivetran run its setup tests again and syncs when they pass, however many nights it takes, and cfo.ai engineering is notified when that still fails. Ari says the same when you ask about the connection.
- cfo.ai could not tell why the sync failed. Mark: red triangle. Line: the source's own reason, or **The last sync couldn’t finish.** Actions: **Retry** and **Investigate with Ari**. When the reason names a table the source hides, the connection shows [Missing access in [source]](#missing-access-in-source) instead.

Two provider reports name a fix of their own:

| The provider's report | When | What to do |
| --- | --- | --- |
| **Merge reports employee data [FAILED, ERROR, or DISABLED]; Merge's linked account status is [status]; Merge's open issues for the linked account: [issues]** | Merge stopped syncing the employee data of an HR or payroll connection, such as ADP Workforce Now. The report lists up to three of Merge's open issues for the account, in Merge's words, such as **Missing Permissions (Missing employee permissions.)**, or reads **Merge lists no open issue for the linked account**. A part cfo.ai could not read from Merge reads **could not be read**. | Fix what the issue names in the HR system, such as the permissions of the account that connected it. The next scheduled sync tries again, or select **Retry**. When Merge's status for the account is `RELINK_NEEDED`, the connection asks for a reconnect instead; see [cfo.ai lost access](#cfoai-lost-access). |
| **Fivetran reports a source error, netsuite_internal_error, and names no table. This connection syncs tables that cfo.ai's reports do not read, and one failing table fails the whole first sync. The connection can be narrowed to the tables its reports read** | A NetSuite connection's first sync failed while NetSuite returned a table's rows, and the connection syncs tables that cfo.ai's statements do not read. When Fivetran names what failed, its details follow the code in place of **and names no table**. | Ask Ari to narrow the connection to the tables its reports read. Ari turns the other tables off and starts a sync; see [NetSuite SuiteAnalytics](/reference/integrations#netsuite-suiteanalytics). A NetSuite connection that syncs only those tables keeps Fivetran's own report, **Fivetran reports: Contact NetSuite support (netsuite_internal_error)**, because a table the statements need is failing. |

### Syncs paused

A connection that has never finished a sync failed its newest three nightly syncs with the same report from the provider, and the report names a problem that another try cannot clear, such as NetSuite's **Contact NetSuite support (netsuite_internal_error)**. The nightly refresh then starts a sync for it once a week instead of every night. Mark: red triangle. Line: **[Source]’s first sync failed the same way 3 times, so cfo.ai now tries it once a week, next on [date and time]. Fivetran reports: [the provider's report]. Retry starts a sync and resumes daily syncs.** Action: fix what the report names at the source or with the provider, then **Retry**. **Sync now** and **Reconnect** are not offered. When the report says the connection can be narrowed to the tables its reports read, ask Ari to narrow it instead; the sync Ari then starts ends the pause. [Sync failed](#sync-failed) quotes that report.

The weekly sync starts at the connection's first scheduled start on or after the same weekday one week after its newest failed sync, and the line gives that date and time. The date is counted in the time zone of the connection's own refresh time, or in UTC when it has none. A weekly sync that succeeds ends the pause, and nightly syncs resume. One that fails the same way keeps the pause, moves the next try a week on, and sends no new notice to the connection's chat.

Any sync that you or Ari start ends the pause, and so does connecting the source again. When Ari turns a table off on a paused connection, it starts a sync as well, because the table turned off may be the one the sync failed on. If that sync fails, the nightly refresh tries again each night, and three more identical nightly failures pause it again. Only a first sync pauses this way: a connection that has finished a sync before keeps its nightly retries, and so does one whose failures differ from night to night or can pass by themselves, such as a reset connection or an error Fivetran reports as a generic sync failure. Ari's notice in the connection's chat for the failure that starts the pause says that the nightly refresh now starts a sync only once a week. When no chat follows the connection, that failure starts Ari's background repair for the person who connected the source instead, once for each pause; see [When a source stops updating](/concepts/connected-data#when-a-source-stops-updating).

### First sync not ready

cfo.ai stopped waiting for the provider's own first sync of your account, because 20 hours passed with no report from the provider that the sync was still unfinished. While the provider keeps reporting its first sync unfinished, cfo.ai keeps waiting, so a first sync that takes longer than 20 hours does not get this status by its length alone. A bank connected through Plaid gets this status only when Plaid had no transactions ready when the wait ended. Its first sync loads recent transactions as soon as Plaid has them, and later syncs add the older history. Mark: steady orange dot. Line: **[Source]’s data still wasn’t ready when cfo.ai stopped waiting for its first sync, so this sync ended without data. The next scheduled sync tries again.** Action: none, or **Retry** to start a new wait.

A wait for a later sync that ends the same way, after 20 hours with no report that the sync is still unfinished, does not get this status. The connection reads **Sync failed** with a red triangle, and the line is the reason sentence **the provider reported no progress on its unfinished sync for 20 hours after its last report at [time], in a wait that began at [time]**, or, when the provider made no report during the wait, **the provider reported no progress on its unfinished sync for 20 hours after the wait for it began at [time]**, followed by what the source last reported. The next scheduled sync tries again, or select **Retry**.

### Paused until next sync

The source's daily request allowance ran out. Mark: steady orange dot. Line: **[Source]’s daily limit was reached. Progress is saved, and syncing picks up on the next scheduled run.** Action: none. Signing in again would not change the limit, so **Reconnect** is not offered.

### cfo.ai is fixing this

A problem on cfo.ai's own side stopped the sync. Nothing in your source, your sign-in, or your file caused it. Mark: steady orange dot. Line: **A problem on cfo.ai’s side stopped this sync. Contact cfo.ai support if it isn’t fixed soon.** Action: none. Only cfo.ai can clear it, so the connection offers no **Retry**, **Reconnect**, **Sync now**, **Update file**, or **Investigate with Ari**. Ari reads the same cause and is told that a retry cannot clear it.

A connection reads this status for one of these causes:

| Cause | What happens next |
| --- | --- |
| cfo.ai's data warehouse refused the data, because of the warehouse's own access or setup. An incident that Fivetran reports at the warehouse is a different case: it reads [**Sync failed**](#sync-failed) and is tried again at each scheduled sync. | The nightly refresh leaves the connection alone until cfo.ai repairs the warehouse's access or setup. |
| cfo.ai's store for query results had no disk space left for a saved query's result. | The saved query keeps the rows of its last finished load. The nightly refresh syncs the connection again. |
| The machine that ran the sync, or that loaded a saved query's result, ran low on memory. cfo.ai runs a sync or a load that stopped this way again by itself up to three times, after about 1, 2, and 30 minutes, and the status appears when the last run stopped too. | The nightly refresh syncs the connection again. |
| Ari's import of a Google Sheets or Google Drive spreadsheet stopped because its calculations ran past a time or memory limit. | The import waits; see [Messages about uploaded files](#messages-about-uploaded-files). |

For a full store or low memory, Ari can also start a sync when you ask, once no other sync of the connection is running. While the limit lasts, that sync stops the same way. The nightly refresh does not reload an uploaded file, so a file upload's data comes back only through a sync you ask Ari to start. That sync loads the file you already uploaded again. **Update file**, which loads a newer version of the file, is offered again once the status clears.

A saved query that fails for a reason of its own, such as SQL the warehouse rejects, reads [**Sync failed**](#sync-failed) and keeps **Retry**.

When several causes apply at once, this one is shown, because nothing else helps until it is fixed.

### Waiting for your decision

The last sync of a Google Sheets or Google Drive file finished, and the next step waits for a person, because no sync takes it. Nothing failed. A connection reads this status in two cases:

- The file changed, and no import or update of the new version started, because automatic updates are off for the connection or your Model holds no import of the earlier version.
- An import stopped on a question that only a person can answer, such as a decision of yours.

Mark: steady orange dot. Line: **The last sync finished. Ari is waiting for your decision in the chat about this import.** Action: **Investigate with Ari**, which opens a new chat that asks Ari what the import waits on and what each choice would do. Only the person who connected the file can record the decision. The connection's row adds **No import is running. Continue in the chat about this import.**; see [Messages about uploaded files](#messages-about-uploaded-files). An import that a limit on cfo.ai's side stopped reads [**cfo.ai is fixing this**](#cfoai-is-fixing-this) instead.

### Stopped

Someone stopped the latest sync. Nothing broke. Mark: gray dot. Line: **This sync was stopped before it finished.** Action: **Retry**.

### No queries yet

The source's data synced, but no saved query brings it into your Model yet: the connection has none of its own, and no saved query on another connection you can see reads its tables. Mark: red triangle, or a steady orange dot when someone else must set up the queries. Line: **Data synced. No queries saved yet.**, or **Data synced. Someone with access can set up queries with Ari.** Action: **Set up queries with Ari**, for people who can edit the connection.

### No data found

The sync finished, but neither the source nor its queries returned any rows. Mark: red triangle. Line: **The last sync finished but found no data.** Action: **Investigate with Ari**.

### Upload incomplete

A file upload connection has no file attached yet. Upload the file again.

### Needs attention

The general status for a connection that stopped short of your Model. MCP servers and APIs show it with a next step, such as **Reconnect this source to continue.** for a server whose saved sign-in no longer works.

### Not connected

A source was added, for example from a list Ari asked you to connect, but nothing was connected yet. Mark: gray dot.

## Statuses for MCP servers and APIs

In **Settings → Connections** and on the **MCP** and **API** tabs, a server or API reads one of these, followed by its next step when it has one.

| Status | Meaning |
| --- | --- |
| **Ready for Ari** | Ari can call its tools or endpoints. |
| **Synced** | A sync setup Ari saved has brought its data in. |
| **No queries yet** | A sync setup brought its data in, and no saved query reads it yet. On the connection's page, the line reads **Data synced. No queries saved yet.** with **Set up queries with Ari** for people who can edit the connection, or **Data synced. Someone with access can set up queries with Ari.** The page reads the status again each time it opens and when Ari saves a query. |
| **Connecting** | Setup is still in progress. |
| **Waiting for you** | Someone must finish setup, such as signing in. An MCP server in this state offers **Finish setup**; see [Sign-in incomplete](#statuses-for-mcp-servers-and-apis). |
| **Needs attention** | Something broke; the next step says what to do. |
| **Unavailable** | The status could not be read. |

An MCP server's row also shows the state of its saved sign-in. The state describes the saved credential, not whether the provider answered or how fresh its data is.

| Sign-in state | Meaning |
| --- | --- |
| **Sign-in saved** | The saved sign-in is current. |
| **Sign-in saved · expiry unknown** | The saved sign-in works, and the provider did not say when it expires. |
| **Access expired · renewal on next use** | The access token has expired, and cfo.ai renews it the next time it uses the server. Nothing to do. |
| **Reconnect required** | The connection holds no usable sign-in: the provider refused to renew it, or the access token expired and the provider gave cfo.ai nothing to renew it with. When a provider refuses a renewal, cfo.ai removes the saved sign-in. The server's status reads **Needs attention** with **Reconnect this source to continue.**, and until someone signs in again cfo.ai does not contact the server, so Ari cannot use its tools. Select **Reconnect**, which opens the provider's sign-in again and keeps the connection and its sync setups. |
| **Sign-in incomplete** | The server was added but its sign-in never finished. Its row in **Settings → Connections**, its details, and its sidebar card offer **Finish setup** to people who can add connections. It starts a new sign-in and replaces the unfinished attempt. When that sign-in fails, is declined, or stops before it finishes, the unfinished connection stays in the list with its name and address, so you can select **Finish setup** again. The sign-in finishes even when the cfo.ai tab that started it reloads before the provider sends you back: cfo.ai keeps the attempt until the sign-in ends, with no time limit, and the page the provider returns you to completes it. Switching workspaces cancels an unfinished attempt. |
| **Provider access not checked** | The server does not sign in with OAuth, so there is no credential state to show. |

A sign-in to an MCP server waits in the provider's window with no time limit. It ends when you finish it, when you stop it, when the provider refuses it, or when a newer sign-in to the same server replaces it. While it waits, **Reconnect** or **Finish setup** shows a spinner and stays selectable. Selecting the button again closes the waiting window and starts the sign-in over in a new one, so a window that never came back does not block you. A click while the sign-in is still starting, or while cfo.ai is finishing it after the provider sent you back, changes nothing.

Each server address has its own sign-in. Servers at different addresses sign in side by side, each in its own window, and each row shows its own spinner. Two sign-ins to the same server address in one workspace cannot run at once: the newer one takes over, whether it came from **Reconnect**, **Finish setup**, a catalog card's **Connect**, or **Add manually**. The older window closes, its button stops showing the spinner, and cfo.ai reports **A newer sign-in to this server took the place of this one.** for it, under **Reconnection failed** or **Setup not finished** when it came from a row's button.

### Statuses of a source Ari fetches

A source connection is for a system that has no integration: Ari fetches its data with a saved script, using a saved login or key when the system needs one; see [Bring in data from a source that has no integration](/guides/connect-other-sources#bring-in-data-from-a-source-that-has-no-integration). It is listed with your APIs and its **Type** reads **API**, but it is an exception to the two statuses other APIs show: its status follows its latest fetch, as this table lists.

| In **Settings → Connections** | On the connection's page | Meaning |
| --- | --- | --- |
| **Ready for Ari. Import data to continue.** | **Connected**, with **Ari can call this API directly.** | The connection is saved, and no fetch is running or has failed. The line is the one every API's page shows; Ari does not call a source connection live, and only fetches from it on its schedule or when you ask. It reads this before the first fetch and keeps reading it after a fetch that loaded its data. Once your data is in, **Import data to continue.** is only the line's wording: no import is pending, and it asks nothing of you. |
| **Connecting. No action is needed while setup finishes.** | **Setup not finished**, with **No action is needed while setup finishes.** | A fetch is running, or a table it delivered is still loading. |
| **Finish setup to continue** | **Setup not finished**, with **Finish setup to continue** | The fetch stopped for something only a person can give. When the source sent you a sign-in code, a field labeled **Code [source] sent you** appears under the line; see below. With no field, the fetch stopped with a question, such as a login the source rejected. A fetch you asked for puts that question in the chat that asked; for a scheduled fetch, ask Ari to fetch from the source again. |
| **Needs attention. Import data to continue.** | **Needs attention**, with **Import data to continue.** | The latest fetch ended without data: it failed, it finished without loading a table, or nobody entered the code in time. When the source texts or emails you a sign-in code, the fetch waits 15 minutes for it. People who manage connections see the field **Code [source] sent you** with **Continue fetch** on the connection's row, on its page, and on Ari's connect card for 30 minutes after the card saved the connection. An empty field reads **Enter the code first**. When cfo.ai takes the code, a **Code sent** notice appears and the fetch goes on. cfo.ai also sends one email for each wait, to the person who asked for the fetch or, for a scheduled fetch, to the person who made the connection. Its subject is **[Source] sent you a code**, and it reads **Ari is fetching data from [source] for your workspace, and the fetch is waiting for you.**, then **The source sent a code to you by text or email. Enter it on the [source] connection within 15 minutes, and the fetch continues.**, a link labeled **Open the connection** that opens your API connections, and **If the time runs out, ask Ari to fetch from this source again.** The email quotes nothing from the source's pages.

A source connection has no **Edit configuration**, so its saved login or key cannot be changed. When the password or key changes, ask Ari to connect the source again and remove the old connection. Removing a source connection keeps the tables it loaded, and they stop updating.

### Sync setup rows

Each sync setup of an MCP server or API has a row in the **Syncs** section. The row shows the setup's name, what it copies, how it keeps records, such as **Replace · Keeps the latest result**, and **Enabled** or **Paused**. **Details** opens the saved call. Under them the row lists three facts. Times are in your browser's time zone.

| Fact | What it reads |
| --- | --- |
| **Schedule** | **Daily at [time]**, such as **Daily at 2:00 AM**: the connection's own refresh time when it has one, and otherwise the time the workspace's connections start in the shared nightly run. **Not scheduled** when the nightly refresh does not cover the connection, such as one that needs a new sign-in. Every enabled setup of a connection runs in the same sync, so they share one schedule. |
| **Last synced** | The date and time of the setup's last successful sync, to the second, such as **Oct 23, 2026, 6:02:14 PM PDT**, or **Not yet**. |
| **Next run** | The date and time of the next scheduled start. A paused setup reads **Paused**. When the connection's latest sync failed in a way the nightly refresh does not try again, it reads **Stopped until the connection's failed sync is fixed**. When the setup's most recent run failed, the fact opens with **Last run failed [date and time].** An enabled setup with a next start then reads **Runs again [date and time]**; a paused one reads **Paused**, and keeps the failure until it runs again. The fact is left out when the connection is not scheduled and the setup is enabled with no failed run. |

**Next run** shows the scheduled start, and a sync can start later or be skipped. The nightly refresh skips a workspace with no active plan and a source cfo.ai has turned off, and it starts no second sync while one is running. A refresh time set or cleared since the last nightly run first applies at the next one, so until then the sync can start up to a day later than shown. To change the time, see [Change when a connection refreshes](/guides/refresh-data#change-when-a-connection-refreshes).

## Messages in a chat

When Ari syncs a connection, a line above the message box reads **Syncing** with the connection's name. Selecting it opens a card with the run's two steps, **Sync source data** and **Run saved queries**, its progress, such as **Step 1 of 2**, and **View connection** and **Stop**. A failed run reads **Couldn't finish** and keeps the connection's own status and action. A run you stopped reads **Stopped**.

When Ari tells you when a sync started, failed, or finished, it reads those times on your clock, so the date it gives is your date: a sync that failed at 02:04 UTC on November 21 failed at 6:04 PM on November 20 in Pacific time. In a chat you write in, your clock is the time zone your browser reports. In a chat that cfo.ai opened for you, in the notices Ari gets about a sync, and in a background repair of a source that stopped updating, it is the time zone of the newest message you wrote anywhere in the workspace, or, when you have written none, of a Trigger you set in a time zone other than UTC. A message that a teammate or cfo.ai support wrote in your chat does not change it. When cfo.ai knows no time zone for you, Ari gives sync times in UTC.

When a scheduled sync finds that a source you connected stopped updating and a repair needs you, cfo.ai opens a chat titled **[Connection name] stopped updating** in your chat list.

When a newer version of a connected file arrives while an earlier import of it is still running or waiting, the chat that handles the import reads **Superseded tasks withdrawn: [tasks]. Their earlier questions no longer need answers. The current task is "[task]".** The new version went to that import, and older duplicate imports were withdrawn. **Its question remains open: [question]** follows when the import is still waiting for your answer.

When a workspace has no active plan, a refresh you ask for answers **data syncing is paused for this workspace — choose a plan, or settle the outstanding payment, to resume syncing**, and the nightly refresh skips the workspace until it has a plan again.

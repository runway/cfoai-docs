---
title: "Read and explain formulas as an agent"
description: "Inspect saved Variable formulas and visible Table Block values, then explain their expression, scope, range, and Scenario."
---

Use `inspect_table_blocks` with its `variable` block when a user asks how a Variable is calculated or why its behavior changes by segment or period.

## Read the saved rules

For example:

```json
{
  "scenario": "Main",
  "variable": { "target": "Gross Margin" }
}
```

The result lists every formula definition saved on the Variable, with its condition and its Actuals or Forecast range. Add `conditions` only when the question requires one exact saved scope, such as `["[Department = \"Sales\"]"]`. Omit the filter when the user wants the complete set of rules. A Variable with many rules returns them in pages; to read the next page, copy the response's `next.after` into `after` in the same `variable` block, keeping the same `target`.

Each `variable` or `dimension` entry also carries `dependents`, what reads the object at that snapshot: `total`, counts for `formulas`, `blocks`, `settings`, and `manual_items`, `inaccessible` for dependents this user cannot read, and `items`, up to 20 descriptions. A `delete` without `force` is refused exactly when `total` is above 0 and deletes at once when it is 0. Omit `target` to list every readable Variable or Dimension in the Scenario as the same entries, in saved order; `next` continues the listing.

Each definition's scope states its `time_grain` when the rule is dated and its reach in words: `includes additional dimensions` for a `[...]` condition that also covers cells carrying more business Dimensions, or `this grain only` for an exact `$[...]` condition. The reach describes Dimension coverage only; time coverage is the separate `time_grain`, so a Month rule does not cover Day cells however far its reach extends.

Use the `dimension` block the same way to read a Dimension's saved definitions, and `items` to list its members.

For a Variable or Dimension read from an imported source, the entry's `source_default` also states `order`, such as `last by MONTH` or `last by source order`. It says how a column that shows one row per record picks that row when a record has several: the latest row by the source's date column when the source has one, or the last row in source order when it has none. A column that sums its rows has no `order`.

### Read several Variables or Dimensions in one call

`target` on the `variable` and `dimension` blocks also takes a list of references. The response holds one entry per reference in the order given, all read at one snapshot, and states each imported source's query once under `sources`; an entry's `source.query_ref` names its key there. A reference that matches nothing is refused in its own entry while the others still answer.

```json
{
  "scenario": "Main",
  "variable": { "target": ["Amount#a4d", "Probability#058"] }
}
```

## Connect rules to visible values

Use the `read` block for the table that actually shows the result. Each row and column already carries its formula per range, and a cell that breaks the row's rule says so in the cell. Request `formula_origins: "all"` when the explanation depends on which saved rule the engine ranked first for a row, or `"zeros"` to explain only the rows that show a zero, blank, or error.

```json
{
  "scenario": "Main",
  "read": {
    "target": "Operating Plan",
    "rows": ["Gross Margin"],
    "formula_origins": "all"
  }
}
```

A member row is selected by its path from its Variable or axis Dimension, one bracket per breakdown level, as a readback prints it: `Revenue[West]`, `Revenue[West][Enterprise]`. The member that holds rows with no value displays as **None** and is spelled `empty:None` in a selector, for example `Region[empty:None]`. A text member is printed as written, even when it contains a colon: the read's `member` field, the `members` list in a receipt, and a row reference such as `Cash Step[Expected in: open invoice #483]#c00` all spell it `Expected in: open invoice #483`, and a formula matches that exact spelling.

Each rendered target's rules say whether `formula` and `clear_formula` can be written there. A target whose cells the direct writer would refuse, such as cells read from an integration or cells whose provenance the read cannot establish, does not advertise those actions; its rule carries a `readOnlyReason` instead, so a write is not attempted where it would fail. The spelling differs by level: a rendered target's rule spells it `readOnlyReason`, while a row or column that cannot be written spells its own reason `read_only_reason` beside `writable: false`. Dated Actuals and Forecast defaults keep their own writability.

Use the same requested Scenario for both the saved-formula read and the table read. The saved rule explains the intended calculation. The visible table confirms which rule actually applies to the selected period, segment, and Scenario. A row computed by a rule saved outside the table names that rule's owner and condition in `inherited_from`.

A read of a table that compares Scenarios returns every compared Scenario's value when `columns` names periods, one column reference per Scenario and period, each labeled with its Scenario. When a compared Scenario returns no values, the result carries a `comparison_scenario_missing` issue and coverage reads `incomplete`. `comparison: "none"` reads the selected Scenario's own values and formulas, and `formula_origins: "all"` annotates such a read with the rule each cell used.

## Read a monthly table by quarter or year

`read` takes `grain: "QUARTER"` or `"YEAR"` to read a table's Date periods at a coarser grain than the saved table's own, without changing the table. Each period holds what the Model calculates at that grain: the Variable's time rollup (its base periods summed, closed, or averaged) or a timeless formula recomputed there. A Variable with neither reads `#NO_ROLLUP` in those cells, with one issue explaining that no rule computes it at that grain and that the values are in the table's own periods; the app shows such a cell as 0. A Scenario or time comparison read at a coarser grain still shows 0 there. The period columns come back `writable: false`, because their refs spell the date each period starts and would name the saved month column in a write. A read at the grain the table already shows is the table's plain read, with writable period columns. A finer grain, or a table with no Date axis, comes back as an `invalid` result rather than a tool error, with its reason: `grain QUARTER is finer than this table's YEAR periods; a read's grain shows the periods at their own grain or rolled up to a coarser one` for a finer grain, and `grain QUARTER sets the grain of a table's Date periods, and this table has no Date axis` for a table without one. Continuation cursors carry the grain.

```json
{
  "scenario": "Main",
  "read": { "target": "Operating Plan", "rows": ["Bookings"], "grain": "YEAR" }
}
```

A period selector can also be spelled the way people write it, and it is read under each column's own grain: `2027` or `FY2027` selects a year column, `Q3 2026` or `2026 Q3` a quarter column, and `Mar 2026` a month column. `2027` never selects January of a monthly axis. The stored spelling, such as `2027-01`, still works everywhere.

## When the table cannot calculate

When the calculation service cannot compute a table, `read` still returns the saved configuration: the rows, their default formulas and formatting, and the saved column axes. Each axis entry is marked `axis: true` and carries its dimension, grain, and writability, for example `{"ref": "Date#10b", "axis": true, "dimension": "Date", "grain": "MONTH", "writable": true}`, so an empty `columns` list never stands in for a Date axis that exists. No cells are delivered. The result carries a `calculation_unavailable` issue; when the calculation service explained the failure, the issue's message includes `The calculation service reported <code>: <message>`, such as `table_config/external_column_not_mapped: external column Class L1 is not mapped in table …`, so the cause can be named instead of guessed. The issue also carries `category` (`capacity`, `model`, `request`, `dependency`, or `internal`), a `transient` flag, and a sentence stating what that category means, so a retry is chosen only when the failure is transient: a calculation that did not finish within its time limit is `capacity` and not transient, while a service that did not answer is `dependency` and transient. A failure the calculation service did not classify carries the error as raised, clipped to 500 characters, and no `category` or `transient` flag, so a retry is not assumed either way. A table whose saved comparison names a Scenario that no longer exists still reads: the comparison columns are dropped for the calculation only, and a `table_problem` issue names the former Scenario. An `edit_scenarios` `delete` lists the readable tables that compared against the deleted Scenario as `tables_comparing_against_it`.

## Explain one cell's inputs

For a single cell, select one row and one column and add `include_inputs: true`. The result shows one level of the formula's inputs and where each value came from: lookup coordinates, aggregate units, the selected rule, and source dates. Read an input by its own reference to go deeper. `include_inputs` and `recalculate` need `comparison: "none"`; on a time or Scenario comparison the read answers with an invalid-input refusal that names the option, not a tool error.

Every `read` also reports `calculation.source`: `cached`, `promoted`, `derived`, `seeded`, `full`, or `recalculated`. A doubted value from anything but `full` or `recalculated` is worth one read with `recalculate: true`, which is described in [Validate and verify](/formulas/agent-docs/validate-and-verify#verify-calculated-behavior).

## Historical reads

Use `as_of_point` when the user asks for the Model as it existed at a previous saved change. Omit it for the current state. `inspect_canvas_blocks` takes it too and returns each block's `dataset_layouts`, and `inspect_table_blocks` `items` reads the source run the Model used at that point. `bounds` reads current source state and refuses `as_of_point` with "bounds reads current source state; as_of_point applies to items".

## Explain the business meaning

Lead with what the formula does, then explain the inputs, the Scenario, the relevant Dimensions, and whether Actuals or Forecast changes the result. Include assumptions only when they matter to the user's question.

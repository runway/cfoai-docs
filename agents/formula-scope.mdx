A formula's scope is the set of Model values it controls. Its condition says where it applies, and its formula range says whether it covers Actuals, Forecast, or both. A visible Table block target is the preferred authority for both, because the server derives the actual cell address from it, and a row or column update names the range as `actuals` or `forecast`. For the customer-facing explanation, see [How formulas work](/concepts/formulas) and [Actuals, Forecast, and Last close](/concepts/actuals-and-forecast).

## Start from the visible target

Inspect the saved table, and copy the returned row or column reference into `edit_table_blocks`:

- Use a row or a column for a formula that applies along that axis.
- Use a cell for one exact visible result.

The server derives the scope from the target. You do not invent Dimension IDs, array positions, formula-range IDs, or conditions for a visible edit. For a row or column formula limited to Actuals or to Forecast, you name the range: `default_formulas.actuals` or `default_formulas.forecast`. The periods the table shows do not choose it. A timeless `formula` applies in both ranges and names none; see [Where a timeless formula is written](/agents/write-formulas#where-a-timeless-formula-is-written).

## Write a condition

No `edit_table_blocks` field takes a formula's condition: the row, column, or cell you target sets it. You write a formula's condition yourself in the `condition` of an `edit_dimension_mappings` rule. You also pass conditions as a filter, in `conditions` on a `variable` or `dimension` read, to pick saved formulas by their scope. You read one on each saved formula a result describes.

When you write a condition yourself, use the readable Dimension and item names that inspection returns. Put backticks around names with spaces, and add a returned reference's short suffix only when needed.

A condition selects cells that exist; it never creates one. An item that only a condition names, such as `[Department = "New"]` when no Department is called New, is not added to the Dimension, and the formula applies to nothing until the item exists.

Items come from imported rows, a Dimension's own formula or item set, saved and manual declarations, mappings, and the configured calendar. So create the item first, with `dimensions[].add_items` on an `update` of `edit_table_blocks`. The same call can write values and cell formulas on the added item; see [Add items and write their values in one call](/agents/write-formulas#add-items-and-write-their-values-in-one-call). Save a row or column formula for the item in a later call, once the item exists.

The same holds for Date: a condition on a month outside the Model's calendar does not add that month.

| Scope | Condition | Use it when |
| --- | --- | --- |
| Model-wide default | `[]` | The same formula should apply across the Model, with no narrower business condition. |
| Every item of a Dimension | `[Department in any]` | The formula applies to each Department. It still applies when more Dimensions are present. |
| One segment | `[Department = "Sales"]` | The formula applies to one item. |
| A combination of segments | `[Department = "Sales", Region = "West"]` | The formula applies where both hold. |
| A segment across time | `[Department = "Sales", Date.Month in any]` | The formula is dated, in a monthly Model. |

A condition with no Date term, such as `[]`, can supply inherited defaults in both Actuals and Forecast.

## Exact and inheriting conditions

A condition without `$` can still match a richer cell address. A condition that begins with `$` matches exactly the set of Dimensions it names:

```text
[Department = "Sales"]
$[Department = "Sales"]
```

In a saved table, the exact form is what a cell write produces:

- A `cell_updates` entry saves one formula per selected cell at that cell's exact address, so one row across 60 period columns saves 60 formulas, and `clear_formula` removes them. When a formula already sits at that address, the write replaces its text and keeps its saved matching mode.
- A `row_updates` entry's `default_formulas` saves one inheriting formula that covers every period in its range. A formula the row already owns keeps its saved scope and matching mode.
- On a timeless row with one value column, the cell's coordinates are the row's own, so the edit writes or removes the row's formula.

The leading `$` belongs to the condition grammar. In an expression, an absolute reference puts `$` after the Variable's name instead: `Revenue$[Department = "Sales"]`. One expression form does start with `$`: a condition group followed by a dot lookup, such as `$[Department = "Sales"].Department`, which is the Dimension item Sales.

Use exact scope only when the user intends that narrower behavior. A formula that leaves out Date cannot fill dated cells when it matches only its exact set of Dimensions.

## How results describe a formula's reach

Formula reads and write receipts describe each saved default's scope the same way. A `variable` read carries it as `scope`, on each formula saved with a condition other than `[]`. A table `read`, and the readback in a write receipt, carry it on each row and column under `edits`, when the call sets `include_edit_rules: true`. The description holds:

- its condition and its range;
- its Date grain, when the formula is dated, in `time_grain`;
- its reach in words, in `reach`. `includes additional dimensions` means an inheriting `[...]` condition that also covers cells carrying more business Dimensions, at the same Date grain. `this grain only` means an exact `$[...]` condition.

Reach describes Dimension coverage only; time coverage is the separate Date grain. A Month formula never covers Day cells, however far its reach extends, so a daily forecast needs a Day formula of its own.

## Actuals and Forecast ranges

Formula ranges separate parts of the timeline that use different calculations. Actuals and Forecast are defined relative to a Scenario's Last close, and each Scenario has its own. Interpret a formula range against the boundary of the Scenario you read or write: the one `scenario` names, or the Scenario in view when the call leaves `scenario` out.

### Let the visible target choose the range

When the formula belongs to a visible row, column, or cell, inspect the saved table and use `edit_table_blocks` to target the actual result. You do not invent or fetch a formula-range ID. A row or column formula limited to Actuals or to Forecast goes in the range you name, `default_formulas.actuals` or `default_formulas.forecast`, whatever periods the table shows. A timeless `formula` applies in both ranges and names none.

### Dated formulas need Date at the base grain

A formula for Actuals or Forecast needs Date in its condition, at the Model's base grain. In a monthly Model:

```text
[Date.Month in any]
```

```text
[Department = "Sales", Date.Month in any]
```

The range is chosen by where the formula sits: `default_formulas.actuals` or `default_formulas.forecast` on a row or a column, or in a `variables` entry of `edit_table_blocks`. A formula saved through a `variables` entry gets one Date term at the Model's base grain automatically, whether or not the call also names a table, because the formula belongs to the Variable and not to a table. A formula written on a row or column of a table is saved at that table's Date grain instead. When the table's periods are coarser than the base grain, the receipt carries a `formula_warning` issue, or `creation_warning` on a `create`: the formula computes the table's coarser periods itself, and the base-grain cells do not read it. [Read the receipt](/agents/validate-and-verify#read-the-receipt) lists the warnings a receipt can carry.

### Read Last close when it matters

A `dimension` read of Date, and each Scenario in `inspect_scenarios`, returns the Scenario's `calendar`: `last_close`, its default `granularity`, and its default range. An `inspect_scenarios` page of more than 25 Scenarios leaves the calendars out and says so in `calendar_omitted`. A table grid `read` does not carry it. Read the calendar when you need to confirm Last close, because the boundary decides which dates count as Actuals and which belong to Forecast. `edit_table_blocks` `update_calendar` changes these settings for the Scenario; every table in the Scenario shares them.

If the Scenario has no Last close, explain the missing setting before you build a result that depends on the range.

### Keep the Model's time grain

Use the workspace's actual Date grain rather than assuming every Model is monthly. Date conditions, the table's selected periods, and the user's requested range must agree.

### Check both sides of the boundary

After a change, inspect one period in Actuals and one in Forecast. Confirm that the formula applies only where it should, and that the Scenario you meant holds the saved change.

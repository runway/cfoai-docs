---
title: "Validate and verify formulas as an agent"
description: "Use supported dry-run writes to validate formulas, inspect write outcomes, and verify the financial result on a saved Table Block."
---

Validation checks formula syntax and semantic references before a write. Verification checks whether the resulting values match the business rule.

## Validate

Use `dry_run: true` with the write that would own the actual change:

- Use `edit_table_blocks` `update` for a visible saved table target.
- Use `edit_table_blocks` `update` with a `variables` entry, and no table `target`, for a rule saved on the Variable itself.

Validation checks:

- Expression syntax
- Condition syntax
- Variable references
- Function names and arguments
- Semantic compatibility

Correct reported errors before applying the same intended change.

## Read after writing

Inspect the write result. A table write applies all requested changes together or applies none, and its receipt reports:

- Each row and column touched, with the formula it now carries per range.
- `formula_warning` issues for rules that saved but need attention: an imported Variable read in Forecast months, a constant that matches no Dimension item, a tie with an existing rule, a shared formula the write replaced, a read that lands on the generated default (0, or null for a date or text Variable) because the input lacks one of the read's coordinates, or a default saved at a grain coarser than the Model's base grain. A `create` reports the same cases as `creation_warning`. A date used as a lookup key against a Dimension of timestamps is not reported when a member sits at that day's midnight and every member of the Dimension comes from its source rows, because the engine then selects that member; a Dimension with its own member list or formula keeps exact matching, and the same date in a condition is still reported.
- One `read_note` per imported source that the written rules read, stating where that source's rows sit on the calendar and which rules read it, and one for the first Forecast month when the rule reads a prior period, a source, or a Variable with no value there, stating what the rule computed and what each read returned. A note describes the read the rules asked for, not a problem to fix.
- A `scenario_warning` naming the Scenario the write used when the call omitted `scenario`.
- A `default_rollup` issue naming the time rollup each new dated row received, and a statement of the level defaults a breakdown's save wrote or removed.
- Each default rule's scope: its condition, its range, `Date grain: <grain>` when the rule is dated, and its reach. `includes additional dimensions` means a `[...]` condition also covers cells that carry more business Dimensions, at the same Date grain; `this grain only` means an exact `$[...]` condition. A Month rule never covers Day cells, so a daily forecast needs a Day rule of its own.
- A refusal, with the field that caused it, when nothing was saved. A receipt whose `status` is `rejected` or `blocked` saved nothing and carries the same `error` object a refusal carries, beside `items[].reason`. A refusal that fits no branch of a union names the one field or shape that was wrong, and a refusal from the calculation service names the formula it was checking.

Ask for a readback in the same call with `readback.rows` and `readback.columns` to see the calculated values without a second read.

The receipt arrives before an optional readback can consume the caller's deadline. After the write commits, attribution and readback share one budget of at most 30 seconds that ends two seconds before the caller's deadline. A write whose readback did not finish reports the outcome `committed_with_readback_unavailable` with its saved revision: the change is saved and must not be sent again.

An `edit_table_blocks` write that does not answer within the runtime's deadline returns a message naming the call's `tool_call_id`. Every changelog entry the write commits records that id in the Scenario the call wrote, and `inspect_history` `changelog` entries carry `tool_call_id`, so the outcome can be read back. The server rolls back a write that has not committed within two minutes of receiving it, so two minutes after the timeout the write has either committed in full or saved nothing.

A call that repeats an earlier call exactly, after the earlier result already answered it, is refused by the runtime with the code `repeated_no_progress` and `state_changed: "no"`. The refusal is a result to act on, not a transport failure: change the request, or use what the earlier result returned.

## Verify calculated behavior

Use `inspect_table_blocks` on the relevant saved table after a material change. Check representative dates, segments, formula origins, and source information.

Every `read` result carries `calculation.source`, which says how its values were obtained: `cached`, `promoted`, `derived`, `seeded`, `full`, or `recalculated`. When a value disagrees with what the user sees, with another read, or with arithmetic you can check, and the source is anything but `full` or `recalculated`, read once more with `recalculate: true`. That read calculates the table from scratch, ignoring every cached or reused result, makes the fresh result the cached one so the page shows it too, and reports in `recalculated` whether the cached result differed and how many cells. It needs `comparison: none`, costs a full calculation, and is not for routine reads.

Examples:

- Compare Gross Profit with Revenue minus Cost of Goods Sold
- Check a Department formula for two different departments
- Check both sides of Last close for a formula-range change.
- Compare the intended Scenario with the Scenario that was written.

## Report clearly

State what was written and whether verification matched the request. Disclose any inferred table, Scenario, or business assumption that materially affects the result.

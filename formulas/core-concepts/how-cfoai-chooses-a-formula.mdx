---
title: "How cfo.ai chooses a formula"
description: "See how cfo.ai selects a matching formula based on its Scenario, Dimensions, segment, Date, and formula range."
---

A Variable can have several formulas. cfo.ai selects the matching rule for the cell address being calculated.

## Start with applicable formulas

A formula must match the current Scenario, applicable Dimensions, selected Dimension items, Date context, and formula range before it can be used.

## Specific formulas override broad formulas

When more than one formula applies, cfo.ai uses the rule that best matches the requested context.

A common pattern is:

1. A default formula covers the Variable broadly.
2. A Dimension-specific formula overrides it when the Variable is segmented by that Dimension.
3. A segment-specific formula overrides it for a particular Dimension item.

Formula ranges add a time boundary. An Actuals formula applies only inside Actuals, and a Forecast formula applies only inside Forecast.

## Example

Suppose Payroll has:

- A default formula for all departments
- A Department formula for departmental views
- A Sales formula for Department = Sales

When cfo.ai calculates Sales, it uses the Sales formula. When it calculates Engineering, it uses the Department formula. When Department is not part of the calculation, it uses the default formula.

## Breakdown totals add up the rows beneath them

When a table breaks a Variable down, for example Revenue by Product, then Customer, then Line, the save gives every level above the lines its own default that sums the level directly beneath it. Ari writes one rule for all of the lines, a rule for every product, every customer, and every line at once, as the deepest level's default when it builds the table. Where no rule of yours computes the lines of a number Variable, the save writes a generated rule of `0` on them instead, which every typed number overrides, so a breakdown you fill in by hand also gets its totals and a blank line counts as 0. The sums then follow: each customer row adds its lines, each product row adds its customers, and the Revenue row adds its products. These are ordinary saved formulas you can open from the row: the customer row's rule sums Revenue over its lines, and the product row's rule sums Revenue over its customers.

Because each level sums the rows shown beneath it, a value you set on any row reaches every total above it. Setting one line to 0 under one customer lowers that customer's total, the product's total, and the grand total. A line that appears under two customers is counted under each of them.

When a sum is the wrong arithmetic, write the parent's own formula. A ratio such as revenue per customer takes one rule of its own, and that rule replaces the default sum at its level. Editing a generated default the same way keeps your version. Removing a level from the table removes that level's default, and the level above then sums the next level that still exists.

The totals are written under a rule that covers every line: yours, or the generated `0`. A default you write for one parent's children by hand, such as **Default for every Customer** from the Customer header under one product, applies to that product's customers alone and writes no totals of its own. A rule you write above the lines, such as a value on the Variable's own row, gives the lines its value, so the generated `0` and the sums in its range are removed; a rule of 0 or a sum of the Variable's own children does not. Text, date, true/false, and ID Variables, and imported Variables, get neither the `0` nor the sums. Existing tables pick this up on their next save.

## A cell no rule covers

When no formula applies to a cell and nothing was entered there, the cell reads a default chosen by the Variable's type: 0 for a number, and an empty value for a date or text Variable. An imported Variable reads its source column in Actuals and the default in Forecast months unless a rule covers them. See [A date or text cell nobody filled in reads empty](/formulas/formula-reference/formula-errors-and-troubleshooting#a-date-or-text-cell-nobody-filled-in-reads-empty).

## Avoid overlapping exceptions

Several highly specific formulas can make a model difficult to reason about. Prefer one clear default and add overrides only for real differences in business logic.

If a result is unexpected, review the Variable's formulas, the selected Scenario, the visible table context, and the formula range before changing the expression.
